## L0 · 项目概述题（热身，5 分钟内答完）

### Q0.1 用一分钟介绍一下这个项目

**考察意图**：表达的结构化程度；能否抓住「问题—方案—结果」主线而不是报技术名词。

**参考回答**：
> 这是一个面向化工/法规领域的企业级 RAG 知识库问答系统，约 1.5 万行代码。它解决三个问题：让 LLM 只基于企业文档回答、让答案质量可度量、让每次回答可溯源。
> 架构上，后端 FastAPI + LangGraph 编排 7 节点工作流：查询优化 → 向量化 → Milvus+BM25 混合检索 → cross-encoder 精排 → 置信度检查 → 迭代补检索 → 带引用的生成。文档侧支持 7 种格式解析（含 OCR），自研了表格语义切分和 heading-aware 文本切分。
> 两个特色：一是**自动化评测体系**——8 指标加权 + 质量门禁 + RAGAS 子进程隔离评分，改动好坏用数字说话；二是**全链路追踪**——自研 ContextVar tracer + 前端火焰图，靠它定位过一个并发串数据的隐蔽 bug。
> 部署为 docker-compose 9 服务 + K8s Kustomize。

**评分要点**：✅ 有分层主线（问题/架构/特色/部署）✅ 至少一个量化结果 ❌ 只背技术栈清单无逻辑。

### Q0.2 项目里你最有成就感 / 最难的一个技术点是什么？

**考察意图**：真实参与度；能否把一个点讲出「现象—根因—方案—验证」的完整闭环。

**参考回答（推荐讲 RAGAS segfault，故事最完整）**：
> 评测引入 RAGAS 后，主进程 import 它就直接段错误，无 Python 异常无栈。排查发现根因在 C 层：主进程已加载 paddle/torch，RAGAS 间接拉起的 HF 栈与之运行时冲突——try/except 保护不了 C 扩展崩溃。
> 方案是把评分整体移进独立子进程，stdin/stdout 传 JSON，崩溃半径从「整个服务」缩到「一次评分」。子进程里还有个细节：RAGAS 初始化强制要求 embedding 对象，但我们要的三个指标（faithfulness/context_precision/context_recall）都是纯 LLM 指标，于是用全 0 向量的桩实现骗过初始化，再设离线环境变量阻止 torch 加载，省掉 1GB 内存。
> 外面包了三层防御：600 秒超时 kill、returncode 非 0 记失败、连续失败 3 次自动停用降级。最终评测端到端跑通，配合三阶段并发把 core 层评测从 45.3 分钟压到 17.7 分钟。

**备选（并发串数据侦探故事）**：trace 里发现 18% 的记录平级 span 时间重叠——LangGraph 节点串行执行物理上不可能重叠——定位到 threading.local 在 asyncio 下不隔离 Task，A 请求的 span 记进了 B 的 trace。改 ContextVar + 不可变 tuple span 栈 + token 精确 reset，用修复前的脏数据反向验证：新数据零重叠。

**评分要点**：✅ 有根因分析而非「重启解决」✅ 方案有权衡（为什么子进程而不是修依赖）✅ 有验证手段 ❌ 讲不出数字和细节。

### Q0.3 这个系统的完整数据流是怎样的？（文档进 + 问题进）

**考察意图**：全局图景是否清晰。

**参考回答**：
> **文档进**：上传 → 扩展名/scope 校验 → md5 判重（重传从 checkpoint 断点续传）→ RAGFlow 优先解析、失败降级本地解析器（PDF 走 PyMuPDF + 乱码判定触发 OCR）→ 表格语义分组 / 文本 heading-aware 切分（1024/100）→ 批量 embedding → 双写 Milvus + BM25 → 自动生成最多 10 条评测用例。

## L1 · 架构题

### Q1.1 为什么用 LangGraph 而不是自己写个函数串起来？

**考察意图**：是否理解编排框架的价值边界，还是「因为流行所以用」。

**参考回答**：
> 核心原因是工作流里有**两个非线性结构**：一是意图路由的条件边（general 直接跳 generate，跳过整个检索段）；二是 evidence_judge → vectorize 的**回边**（检索为空时补检一轮，且限制最多 1 轮防死循环）。函数串联表达条件跳转和受控循环会写成一堆 if + while + 标志位，图结构把这些变成显式声明。
> 另外 LangGraph 的节点粒度天然适配我们的可观测性需求：每个节点被 wrapper 统一包裹，自动开 span、生成前端预览、注入依赖——加一个节点就自动获得追踪和 SSE step 事件。
> 代价也承认：我们用的是 StateGraph(dict) 而非绑定 TypedDict，状态没有编译期校验，这是待改进项。

**评分要点**：✅ 指出回边/条件边这个不可替代的理由 ✅ 主动说出代价 ❌ 「LangGraph 是标准所以用」。

### Q1.2 画出检索链路，并说明每一级的输入输出规模变化

**考察意图**：漏斗设计意识——检索系统本质是「大规模粗筛 → 小规模精算」。

**参考回答**：
> 漏斗：查询 → 双路并行召回（Milvus HNSW top40 + BM25 top40，limit 传 top_k×2=40）→ RRF 融合去重截 top20 → cross-encoder 精排截 **top5** → 进 prompt。
> 规模设计的逻辑：召回层用便宜的操作（向量距离/倒排求和）处理大候选集；精排层贵（每对 query-doc 过一次 transformer），只处理融合后的几十条；prompt 层最贵（LLM token），只放 5 条。每级缩小一个数量级，成本递增、数量递减。
> 特殊分支：比较类查询会拆 sub_queries，主查询 top10 + 每子查询 top8 **并行 gather**；单查询结果 <3 条时用扩展查询（最多 2 个变体各 top5）补查。

**评分要点**：✅ 数字准确（40→20→5）✅ 能解释「为什么每级规模是这个量级」❌ 说不清 top_k 各是多少。

### Q1.3 系统的降级策略有哪些？单点故障会怎样？

**考察意图**：生产意识；是否系统性想过失败路径。

**参考回答**：
> 降级贯穿每一层：RAGFlow 挂 → 本地解析器兜底；reranker 挂/超时 → 返回空 dict 原样透传（等于退回融合排序）；embedding 挂 → query_vector=None，检索还有 BM25 一路；Redis 挂 → 会话回退进程内 dict；RAGAS 子进程挂 → 该指标记 0 并继续，连败 3 次进程内停用；graph 为 None 或异常 → 接口仍返回 200 + 兜底响应，不抛 500；Milvus 与 BM25 数据不一致 → 启动自检主动报 error。
> 设计原则：**问答主链路对任何单点故障都不返回 5xx**，宁可答案质量降级也要有响应。
> 2026-09-26 更新：resilience 层已接线——`executor.py` 统一执行器，LLM 调用走 `execute_async`（指数退避重试 + 熔断器），Milvus/BM25 搜索走 `execute_sync`（同上）。熔断器 CLOSE→连败5→OPEN→60s→HALF_OPEN→成功关闭，半开限流真实占用配额。API 暴露 `/resilience/status` 查看各 breaker 状态。剩余不足：timeout 上下文管理器是事后判断无法中断执行。

**评分要点**：✅ 列举 ≥4 层降级且有触发条件 ✅ 说明 resilience 已接线（LLM/Milvus/BM25 有熔断重试）❌ 声称「没有单点」。

### Q1.4 RBAC 权限是怎么贯穿检索链路的？

**考察意图**：安全设计能否落到数据层，而不是只做接口鉴权。

**参考回答**：
> 四层贯穿：① 认证层，JWT（HS256, 24h）解析 username，查库得角色 + 可见 scope（每请求查库，改权限立即生效）；② 上传层，非 admin 只能往可见 scope 传文档，doc_scopes 表绑定文档与 scope；③ **检索层**，用户可见文档集转成 allowed_doc_ids 注入 state，Milvus 查询表达式追加 `doc_id in [...]`（值经 `_milvus_escape` 转义防表达式注入），allowed_doc_ids 为空 set 直接短路返回空；④ 体验层，检索为空时做一次**不带权限过滤的探测**（top3），若命中越权文档，答案尾部提示「可能属于 X 部门的资料」——只泄露 scope 存在性，不泄露内容。
> 一个审查中发现并已修复的弱点（主动讲，是加分故事）：早期未入库的 username 验签通过后会回落默认 admin 上下文——本是给 eval_runner 服务 token 开的口子，但等于任何幽灵用户名都能拿到全量权限。修复方案：SERVICE_ACCOUNTS 显式白名单承载服务账号、幽灵用户 403、可见 scope 对未知角色返回空列表而非 admin 特权语义、CurrentUser 默认值改最小权限，并配了回归测试。

**评分要点**：✅ 说到「过滤下推到向量库表达式」这一层 ✅ 提到注入转义 ✅ 主动指出弱点 ❌ 只答「接口加了 JWT」。

## L2 · 原理题（考察底层理解）

### Q2.1 讲讲 HNSW。你们参数怎么设的，为什么？

**考察意图**：向量索引原理 + 参数是否有依据。

**参考回答**：
> HNSW 是多层跳表式近邻图：顶层稀疏长边快速定位区域，逐层下降到底层稠密图做精细搜索；查询复杂度近似 O(log N)。
> 我们的参数：M=32（每节点连边数）、efConstruction=256（建图候选队列）、ef_search=128（查询候选队列）、metric=COSINE。逻辑：知识库规模是万级 chunk 不是亿级，内存不敏感，所以把 M 和 efConstruction 都设得偏大换召回率；ef_search=128 > top_k×2=40，保证截断前候选充足。embedding 已归一化（normalize_embeddings=True），COSINE 与内积等价但语义上更直观。
> 加分点：HNSW 是近似索引，删除是标记式的，所以文档删除后我们同时用 query_iterator 全量重建 BM25，并对 Milvus 做物理 delete + flush，保持两库一致。

**评分要点**：✅ 分层结构+复杂度 ✅ 参数值与规模匹配的理由 ❌ 只背「高性能向量索引」。

### Q2.2 手写 BM25 的公式，解释 k1 和 b 的作用。你们实现和标准 BM25 有何不同？

**考察意图**：真写过（能说出自己的偏差）vs 背过（只会标准公式）。

**参考回答**：
> 标准式：`score = Σ IDF(t) × tf×(k1+1) / (tf + k1×(1-b+b×dl/avgdl))`，IDF 用 `log((N-df+0.5)/(df+0.5)+1)`。k1=1.5 控制词频饱和速度，b=0.75 控制文档长度归一化强度（b=0 完全不惩罚长文）。
> 我们的实现（自研倒排，非 rank_bm25 库）有两处偏差，都能说清理由：① 倒排表存的是**归一化 tf（count/doc_length）**而非原始词频，属 BM25 变体，简化了打分时的长度处理；② IDF 用的是 Robertson 非负变体（+1），避免 df>N/2 时出现负权重。
> 工程细节：jieba 分词 + 约 40 个中文停用词 + 过滤单字和纯数字；索引 pickle 持久化，**先写 .tmp 再 os.replace 原子替换**防写一半崩溃；`doc_stats` 冗余存 content 前 4000 字，向量库失效时 BM25 侧仍能回填正文。
> 已知缺陷（主动说）：同 doc_id 重复 add 不清理旧 posting，df/avgdl 会失真；删除是 O(词表) 全扫。

**评分要点**：✅ 公式+k1/b 语义 ✅ 能指出自己实现与标准的差异 ❌ 说不出 k1/b 含义。

### Q2.3 RRF 融合的公式和 k=60 的含义？为什么默认 RRF 而不是加权求和？

**考察意图**：融合策略的本质理解。

**参考回答**：
> `RRF(d) = Σ_各路 1/(k + rank_d)`，k=60 是原论文经验值。k 的作用是压制头部排名的分差：k 越小，第 1 名和第 2 名差距越大；k=60 时 1/61 vs 1/62 几乎持平，让「多路都靠前」比「单路第一」更重要——这正是融合的初衷。
> 选 RRF 的核心理由：**向量 COSINE 分和 BM25 分量纲不可比**，加权求和必须先归一化，而归一化对分布敏感（一路出现极端高分会把整路压扁）。RRF 只用排名，天然免疫。
> 我们也实现了 weighted（各路 max 归一化后 0.6/0.4）和 max 两种策略作可配置项，默认 rrf，未知配置兜底 max。

**评分要点**：✅ 公式 ✅ k 的语义（不是「随便 60」）✅ 量纲不可比这个核心理由。

### Q2.4 bi-encoder 和 cross-encoder 的区别？为什么召回用前者精排用后者？

**考察意图**：embedding 检索的基本功。

**参考回答**：
> bi-encoder：query 和 doc **独立**编码成向量，相似度是向量距离——doc 向量可离线预计算，在线只算一次 query 编码 + ANN 搜索，毫秒级；代价是交互信息丢失，精度有上限。cross-encoder：query 和 doc **拼接后一起**过 transformer，每层注意力都在做交互，精度高；但每个 pair 都要前向一次，无法预计算，只能用于小候选集。
> 所以标准两段式：bi-encoder（+BM25）从全库召回几十条，cross-encoder 精排出 top5。
> 我们的工程细节：精排模型 bge-reranker-base，输入截断 512 token、batch=16、doc 侧再截 4000 字符——前一版用 v2-m3 不截断时（支持 8192 token）CPU 上 20 条要 60s+，512 截断是拿一点精度换两个数量级的延迟。精排在 asyncio 里通过 `to_thread` 跑，不阻塞事件循环。

**评分要点**：✅ 「能否预计算」这个本质区别 ✅ 512 截断的实测依据 ❌ 只说「一个快一个准」。

### Q2.5 RAGAS 的 faithfulness / context_precision / context_recall 分别在测什么？

**考察意图**：评测指标的语义边界（很多人混用）。

**参考回答**：
> - **faithfulness**：答案中的每个论断能否被检索到的 context 支持——测「生成环节」的幻觉。
> - **context_precision**：检索回的 context 里有多少是与问题真正相关的（相关块是否排在前面）——测「检索环节」的噪声。
> - **context_recall**：回答所需的信息有多少被检索回来了——测「检索环节」的遗漏。需要 ground truth，我们缺失时回退用参考答案。
> 一句话：faithfulness 管「说的都有据吗」，precision/recall 管「据找得准不准、全不全」。三者组合能区分「检索差」还是「生成差」——context_recall 低是检索问题，faithfulness 低是生成问题，优化方向完全不同。

**评分要点**：✅ 三指标各归其位（检索 vs 生成）✅ 能说出组合诊断价值。

### Q2.6 asyncio 场景下 threading.local 为什么失效？ContextVar 凭什么行？

**考察意图**：并发模型理解深度（本项目真实踩坑）。

**参考回答**：
> 线程池里一个线程会被事件循环复用给成百上千个 Task，threading.local 以**线程**为隔离粒度，对这些 Task 来说是同一个存储空间——并发请求互相覆盖 trace_id 和 span 栈。我们线上真发生过：18% 的 trace 出现平级 span 时间重叠，就是 A 请求的 span 被记进 B 的 trace。
> ContextVar 以**执行上下文**为粒度：asyncio 创建 Task 时拷贝当前 Context，Task 内的 set 只影响自己的副本；`set()` 返回 token，`reset(token)` 能精确回滚——我们在 start_trace/end_trace 配对使用，保证上下文无残留。
> 另一个细节：span 栈用**不可变 tuple**，push 是 `set(stack + (span_id,))` 而非原地 append——原地修改会让拷贝了 Context 引用的子 Task 看到父 Task 的变更，不可变结构从根上杜绝。

**评分要点**：✅ 线程复用这个根因 ✅ token/reset 机制 ✅ 不可变栈的加分细节 ❌ 只答「官方推荐 ContextVar」。

### Q2.7 JWT 和 session 认证的区别？bcrypt 为什么不能直接用 passlib？

**考察意图**：认证基本功 + 真实踩坑验证。

**参考回答**：
> JWT 无状态：签名自校验，服务端不存会话，天然适合水平扩展；代价是**无法主动吊销**（只能等过期或上黑名单），我们设 24h 有效期折中。payload 只放 {sub, exp}，权限每请求查库拿最新值——token 管「你是谁」，DB 管「你能干什么」，改权限即时生效。
> bcrypt 的坑：passlib 1.7.4（最后一版）与 bcrypt≥4.1 不兼容，hash 时直接 ValueError，因为 passlib 探测 bcrypt 版本的内部接口变了。锁死 bcrypt<4.1 会绑住依赖树，所以直接弃 passlib 用 bcrypt 库：gensalt(rounds=12)，并注意 **bcrypt 只认前 72 字节**，长密码要显式截断避免行为不一致。
> 另一个部署级细节：JWT_SECRET_KEY 为空时进程内随机生成——单 worker 没问题，多 worker 部署各进程密钥不同，token 跨 worker 验证必失败，生产必须显式配置。

**评分要点**：✅ 无状态/吊销权衡 ✅ 72 字节细节 ✅ 多 worker 密钥问题（真实生产意识）。

## L3 · 实现细节题（区分「真做过」的分水岭）

### Q3.1 你们的置信度阈值是多少？为什么 reranker 分阈值低到 0.10？

**考察意图**：魔法数字是否有数据支撑。

**参考回答**：
> 双阈值：有 reranker 分时阈值 **0.10**，否则回退向量分阈值 **0.40**。
> 0.10 不是拍脑袋：表格类 chunk 和短文本在 cross-encoder 眼里天然低分（query 是自然语言问题，doc 是「| 张三 | 100 |」这种结构），用常规 0.5 阈值会把大量正确答案误判成兜底，评测数据逼出来的。
> 低分后还有两级救回再决定兜底：① 问题含指代词（「前面提到的那个」）→ 仍走知识库让 LLM 结合历史；② jieba 抽实体去掉疑问词后，实体在 top5 内容中逐字命中 → 仍走知识库。真兜底时强制尾注「来自通用知识，非知识库文档」——宁可承认没查到，不可假装查到。

**评分要点**：✅ 两个阈值都对 ✅ 能解释低阈值的数据原因 ✅ 说出两级救回。

### Q3.2 Milvus 的 collection 有哪些字段？为什么 status 默认 active 而不是直接物理删除？

**考察意图**：schema 设计思路。

**参考回答**：
> 15 个字段：chunk_id（VARCHAR64 主键，格式 `md5(source)[:8]_{idx}_{uuid6}`）、vector(768)、content(65535)、source_file/file_type/page_number/line_start/line_end/chunk_index/content_type/section_title/table_nl_description/created_at/doc_id/status。
> 检索相关的设计：status 支持软删除语义（查询恒带 `status=="active"`），doc_id 是权限过滤和整文档删除的锚点；source_file/content_type/doc_id/status 四个过滤字段建 TRIE 标量索引加速表达式过滤；table_nl_description 是表格的自然语言描述，生成时优先于 markdown 表格进 prompt，防止 LLM 对表格结构过度推断。
> 启动时自检 schema：缺 doc_id/status（旧版本）直接 drop 重建，并检查向量库与 BM25 数据量一致性。

**评分要点**：✅ 主键格式 ✅ 标量索引 ✅ table_nl_description 的用途。

### Q3.3 删除一个文档，系统里发生哪些事？如何保证两库一致？

**考察意图**：数据一致性处理（也是当前已知缺陷所在，敢不敢讲）。

**参考回答**：
> 链路：API 删除 → Milvus 按 `doc_id == "..."` 表达式 delete + flush → **BM25 全量重建**（query_iterator 分页拉取剩余全部 chunk，batch=1000——这里有坑：pymilvus 的 query 默认 limit 16384 且**静默截断**，直接 query 全量会悄悄丢数据）→ pickle 原子落盘 → 元数据 JSON 更新 → 关联评测用例标 stale。
> 重传场景：先 delete_by_doc_id 清旧向量，**删除失败必须中止索引**，防新旧 chunk 并存造成检索重复。
> 一个真实排障故事（主动讲）：代码审查中我曾发现删除表达式存在双重引号缺陷——转义函数已返回带引号字符串，调用点又包了一层，生成 `doc_id == ""x""` 非法表达式；更隐蔽的是异常被 catch 吞掉只记日志，删除**静默失败**，界面上文档删了、向量还在，检索会命中幽灵 chunk。修复是三层的：抽 `_build_eq_expr` 助手统一拼接防回归、删除失败向上抛、删除 API 失败即中止（不再继续删元数据），配了回归测试。教训：**吞异常的 catch 会把「响亮失败」变成「静默数据不一致」，后者贵得多**。

**评分要点**：✅ query_iterator/16384 截断这个深坑 ✅ 「删除失败中止」的幂等意识 ✅ 能讲出「发现缺陷→三层修复→回归测试」的完整闭环（大加分，证明真读过自己的代码）。

### Q3.4 SSE 流式接口怎么实现的？推的是什么粒度的事件？

**考察意图**：流式工程细节。

**参考回答**：
> `StreamingResponse(media_type="text/event-stream")`，事件格式 `data: {json}\n\n`，三类事件：**step**（每个 LangGraph 节点完成即推，携带该节点的输出预览——检索/精排取前 5 条、content 截 500 字符）、**done**（answer + citations + trace_id 一次性给出）、**error**。
> 实现上用 `graph.astream()` 逐节点拿状态更新。所以是**节点级流式而非 token 级**——用户在检索阶段就能看到「正在检索→命中了什么」，但答案是最后整段出现。token 级需要 llm_service 加 stream=True 透传增量，是明确的下一步。
> 细节：流式根 span 名叫 chat_query_stream 且打标 `includes_sse_flush=True`，因为它的耗时包含网络推送时间，和同步接口的 span 直接对比会失真——可观测性数据要注明口径。

**评分要点**：✅ 事件类型与粒度 ✅ 主动区分节点级/token级 ✅ span 口径标注的细节意识。

### Q3.5 评测的三阶段并发具体怎么并发？为什么 RAGAS 要攒批？

**考察意图**：并发设计的资源意识。

**参考回答**：
> 阶段1：用例级 `Semaphore(3)` 并发（受 LLM 供应商限额和 CPU 约束），单用例内幻觉/一致性/Judge 三个独立 LLM 指标再 `gather` 二层并发；单用例异常捕获转 error 结果，不拖垮整批。
> 阶段2：等阶段1 全部完成，收集 (question, answer, contexts) 按 **10 条一批**切块，块间 Semaphore(3) 并发，每块起一个 RAGAS 子进程。攒批的原因：子进程启动 + 环境初始化成本固定（约 1GB 内存/进程），10 条摊薄一次；并发上限 3 是内存约束（3×1GB）。
> 阶段3：合并加权出分。
> 一个不能并发的地方：多轮用例的 setup_questions 必须**串行**——后轮依赖前轮真实对话上下文，并发了上下文就乱了。识别「哪些能并行哪些本质串行」比堆并发原语重要。

**评分要点**：✅ 两层 gather + 攒批理由 + 内存账 ✅ 多轮串行的例外。

### Q3.6 长期记忆是怎么去重和遗忘的？

**考察意图**：记忆系统的细节完整度。

**参考回答**：
> 去重双保险：写入前算内容 md5 指纹取前 16 位精确去重（挡完全重复）；再查向量库相似度 ≥0.85 时触发 LLM merge——「用户喜欢简洁回答」和「用户偏好简短回复」语义重复但字面不同，靠 LLM 合并成一条。
> 遗忘：召回排序分 = `relevance × exp(-0.05 × 距上次访问天数) × importance`，时间衰减是乘性的；后台清理任务把 30 天未访问且 importance<0.3 的标 expired 并删 Milvus 向量。importance 由提取 LLM 分级（用户明确指令 0.9+、事实陈述 0.6+、闲聊 0.3+）。
> 存储是双份的：向量在 Milvus 专用 collection，元数据在 JSONL——这里有个已知一致性风险：JSONL 全量重写无锁，与 Milvus 可能失同步，属于待改进。

**评分要点**：✅ 两级去重各自的分工 ✅ 衰减公式 ✅ 主动说双存储风险。

## L4 · 设计权衡题（开放题，考架构判断）

### Q4.1 为什么自研 BM25 而不是用 Elasticsearch？部署里明明有 ES

**参考回答**：
> 部署里的 ES 是 RAGFlow 的专属依赖（版本和索引结构绑定 RAGFlow），共用会引入耦合。自研倒排索引约 300 行，换来三个定制能力：① `doc_stats` 冗余存 content 前 4000 字，Milvus 失效时 BM25 侧仍能回填正文，检索链路不断；② RBAC 的 chunk 级 post-filter 直接实现；③ 删除重建与 Milvus 的 query_iterator 分页逻辑精确同步。
> 代价也明确：单机 pickle 无法水平扩展、删除 O(词表)、多实例部署索引会分叉。当前知识库是万级 chunk 单机场景，这些代价可接受；如果规模到百万级或多实例，就该换 ES/OpenSearch 并把 RAGFlow 的 ES 独立出来。
> **权衡的本质**：在「规模可控的当下」用 300 行可控代码换掉一个重组件，同时写清楚升级到 ES 的触发条件。

**评分要点**：✅ 有明确代价清单 ✅ 有升级触发条件 ❌ 「ES 太重」一句话完事。

---

### Q4.2 评测体系为什么混合「规则指标 + LLM Judge + RAGAS」三套，不怕重复吗？

**参考回答**：
> 三套测的东西不同且互为校验：规则指标（违禁词、引用格式匹配）零成本、零噪声、确定性——能用规则的绝不用 LLM；LLM Judge 测表达质量（准确/完整/相关/清晰/引用/幻觉六维），灵活但有噪声；RAGAS 用不同的 prompt 工程测幻觉/检索质量，与自家 Judge 形成**交叉验证**——两套独立实现都给高分才可信。
> 抗噪声手段：Judge temperature=0.1、评分给五档细则而非笼统 0-10、失败指标剔除出加权不用中性分冒充、固定 seed 抽样保证两次评测同题可比（比较的是趋势不是绝对值）。
> 承认的问题：Judge 解析失败时静默给全 5 分不标 failed，与「失败剔除」哲学冲突，这是已识别待修的缺陷。

**评分要点**：✅ 「能规则不 LLM」的成本意识 ✅ 交叉验证视角 ✅ 主动讲缺陷。

---

### Q4.3 如果并发用户从个位数涨到 100，系统哪里先崩？怎么扩？

**参考回答**：
> 按瓶颈顺序：
> ① **CPU reranker 先崩**——现在评测并发 3 就 CPU 饱和，精排 512 截断后单批仍要秒级。方案：GPU 推理服务化（独立进程/节点，batch 聚合），或降级策略（低峰精排、高峰只融合排序——架构上已支持，reranker 挂了就透传）。
> ② **LLM 供应商限额**——mimo-72b 并发上限。方案：请求队列 + 语义缓存（高频问题答案缓存）。
> ③ **单进程 BM25 pickle / 内存 trace history / JSONL 记忆元数据**——多实例部署会分叉。方案：BM25 换 ES，trace 落 PG/ClickHouse，记忆元数据并库。
> ④ **JWT 临时密钥**——多 worker 必炸，先修配置。
> ⑤ Milvus standalone → 集群版，PG 连接池已具备。
> 关键是**扩容顺序跟着火焰图走**：我们有 span 级自身耗时统计，瓶颈不用猜。

**评分要点**：✅ 有优先级排序而非罗列 ✅ 每步有具体方案 ✅ 用可观测数据支撑判断。

### Q4.4 StateGraph(dict) 而不是 TypedDict，你怎么看？

**参考回答**：
> 这是个已知妥协。state.py 里定义了 RAGState TypedDict（含 Annotated reducer），但图绑的是 dict——所以 reducer 不生效，状态合并靠节点 wrapper 手工 `{**state, **updates}`。
> 当初这么做的原因：节点间字段是渐进加出来的（权限、迭代检索都是后加的），dict 迭代快不炸类型。
> 代价已经显现：① 无编译期校验，字段名拼错运行期才发现；② reranker 节点原地 sort/截断 state 里的列表，raw/filtered 共享 dict 引用产生副作用——强类型 + reducer 能系统性避免这类问题；③ 新人理解成本高。
> 重构方案明确：绑定 RAGState、需要累加的字段（messages/accumulated_results）用 Annotated reducer、节点返回值不可变化。属于「该还的技术债，知道怎么还」。

**评分要点**：✅ 知道债在哪、为什么欠、怎么还 ❌ 意识不到这是问题。

---

### Q4.5 表格切分为什么选「语义行分组」而不是「每行一条」或「整表一条」？

**参考回答**：
> 三个方案各试过的结论：整表一条——500 行表超 chunk 上限，截断后尾部信息永久丢失，且长表格 embedding 语义被稀释；每行一条——「张三 | 100 | 2026-01」脱离表头无法理解，检索命中了 LLM 也不知道 100 是什么，还会造成 top_k 被同表碎片刷屏。
> 语义行分组是中间态：按业务键（客户/类别/订单号）把相关行聚成一个 chunk，**表头重复注入**保证每块自解释，组标签写进 section_title 供检索和展示，超大组（>2048 字符且 >20 行）再按 20 行子切分并标「第 N 部分」。
> 分组键检测的降级链也重要：表头关键词匹配（懂业务语义）→ 最低基数启发式（基数 2~n/3 的列大概率是分类键）→ 放弃分组退固定行数——**检测不出就不硬猜**，宁可用平庸策略不用错误策略。

**评分要点**：✅ 三方案对比有失败模式分析 ✅ 降级链「不硬猜」的原则。

## L5 · 高频追问与压力题

### Q5.1 「你说的这些优化，效果怎么证明？」（压力：质疑数据真实性）

**参考回答**：
> 三类证据：① 评测报告——分层抽样固定 seed，同题可比，幻觉均分 6.1→9.2 有前后报告存 PG（eval_reports 表可查）；② 性能数字——评测耗时 45.3→17.7 分钟有运行日志；③ 反向验证——trace 修复用修复前 18% 脏数据率 vs 修复后 0 重叠做对照。

### Q5.2 「项目里哪些是别人做的 / 框架自带的，哪些是你做的？」（压力：参与度甄别）

**参考回答策略**：诚实划界 + 在边界内讲深。

### Q5.3 「如果重来一次，你会怎么设计？」（考反思深度）

**参考回答**：
> 四件事会不同：① 一开始就绑定 TypedDict state + reducer，dict 的债后来到处漏（副作用、无校验）；② resilience 层要么早接线要么不写——写了不接的框架代码比没写更危险（里面真埋过熔断器死锁，审查时才发现，幸亏没接线）；③ 评测体系应该在第一版检索上线时就搭好，我们是先有检索后补评测，导致切分策略调优靠人肉回归了一段时间；④ BM25 一开始就该定义清楚多实例语义，现在 pickle 单机是把扩展路堵死了。
> 不会变的：RRF 默认、RAGAS 子进程隔离、表格表头重注入——这三个被数据验证过。

### Q5.4 「LLM 幻觉你们到底怎么防的？能保证不幻觉吗？」（考边界认知）

**参考回答**：
> 不能保证，只能**多层压低概率 + 让幻觉可检测可追责**：① prompt 层——引用格式强制、查不到必须明说、法规必须带日期、表格用自然语言描述防过度推断；② 检索层——置信度不足走通用兜底且强制声明来源；③ 检测层——幻觉指标权重 1.5 全场最高 + 门禁 7.0 分硬卡 + RAGAS faithfulness 交叉验证；④ 溯源层——[来源N: 文件, 页码] 引用可点击回查原文。
> 本质认知：RAG 把幻觉从「不可知」变成「可度量可回归」，这是工程能做到的上限。

### Q5.5 「安全上你最担心什么？」（考诚实与安全意识）

**参考回答**：分「已修复」和「仍开放」两档说，展示安全审查是持续过程：
> 已修复（审查中发现）：① 未入库 username 验签通过即回落 admin 的越权通道——改为 SERVICE_ACCOUNTS 显式白名单 + 幽灵用户 403 + 最小权限默认值；② Milvus 表达式注入加固时引入的双重引号缺陷（删除静默失败）——统一拼接助手 + 失败上抛。
> 仍开放（主动报，不遮掩）：① compose 里明文弱密码 + 开发者个人路径挂载，需要 secrets 管理；② 部分历史/会话接口无鉴权且 session_id 只有 8 位可枚举，要统一挂 get_current_user + session 归属校验；③ JWT_SECRET_KEY 为空时进程内随机生成，多 worker 部署 token 互不认，生产必须显式配置。
