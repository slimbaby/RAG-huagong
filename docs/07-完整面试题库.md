## Part II · 架构、检索与框架配置（Q8–Q33）

**Q8 为什么用 LangGraph 而不是函数串起来？** `[03 Q1.1]`
> 两个非线性结构：条件边（general 意图直接跳 generate，跳过整个检索段）和 `evidence_judge → vectorize` 的回边（补检一轮，限最多 1 轮防死循环）。函数串联要写成一堆 if + while + 标志位，图把它变成显式声明。另外节点 wrapper 统一开 span、生成前端预览、注入依赖，加一个节点自动获得追踪和 SSE step 事件。**代价**：图虽绑定了 `RAGState` TypedDict，但节点 wrapper 仍手工 `merged = {**state, **updates}`（`graph.py:141`），且 reranker 节点原地 sort / 改写 `filtered_results`（`nodes.py:570-578`），共享引用仍有副作用风险 —— 见 Q27。

**★ Q9 画出检索链路 + 每级规模变化** `[03 Q1.2 / 05 速查 · 2026-11-12 校准]`
> 普通单查询：`RETRIEVAL_TOP_K=10` → 两路并行召回（Milvus HNSW + 自研 BM25），**每路取 `top_k×2 = 20` 条**（`hybrid_store.py:219-220`）→ RRF 融合去重后 `[:top_k]` **截 10**（`:225`）→ cross-encoder 精排 `RERANKER_TOP_K=5` **截 5**（`nodes.py:577-578`）→ 进 prompt。漏斗速记 **`20/20 → 10 → 5`**。
> 逻辑：**召回层用便宜操作处理大候选，精排层贵（每对 query-doc 过一次 transformer）只处理几十条，prompt 层最贵只放 5 条** —— 成本递增、数量递减。**特殊分支**：比较类查询拆 `sub_queries`，主查询 `COMPARISON_MAIN_TOP_K=8` + 每个子查询 `COMPARISON_SUB_TOP_K=5` 并行 `gather`（`nodes.py:170-175`），各路内部同样 ×2、各自融合后截 8 / 5 再合并；单查询命中 <3 条时用最多 2 个扩展变体各 `QUERY_EXPAND_TOP_K=5` 补查。

**Q14 HNSW 原理与参数** `[03 Q2.1]`
> 多层跳表式近邻图：顶层稀疏长边快速定位区域，逐层下降到底层稠密图精细搜索，查询近似 O(log N)。参数 `M=32`（每节点连边数）、`efConstruction=256`（建图候选队列）、`efSearch=128`（查询候选队列）、`metric=COSINE`。逻辑：知识库是万级 chunk 不是亿级、内存不敏感，M/efC 偏大换召回；`efSearch=128` 远大于最终要返回的 top_k，保证 ANN 搜索候选队列充足（这是 HNSW 图内的搜索宽度，与 RRF 融合后的截断不是一回事）；embedding 已归一化，COSINE 与内积等价但语义直观。**加分点**：HNSW 是近似索引、删除是标记式，所以删文档时同时用 `query_iterator` 全量重建 BM25，并对 Milvus 物理 delete + flush 保持两库一致。

**★ Q15 Milvus 索引优化怎么做？** `[03 C4 · 方法论级答法]`
> **不要从「选哪个索引」开场，从查询模式倒推**：① 先问三个约束 —— 数据能否全放内存？过滤率多少？召回与延迟底线？ → 内存足 + 过滤率低 + 要极低延迟用 **HNSW**；内存有限或过滤率高优先 **IVF 类**；数据远超内存上 **DiskANN**。② 参数分两段：建索引的 `nlist / M / efConstruction` 定索引质量与内存，查询的 `nprobe / efSearch` 在「召回平台期 vs 延迟预算」间取平衡（`nlist ≈ sqrt(N)~4√N`，`nprobe` 取 nlist 的 1%~5%）。③ **真正影响线上稳定的是混合查询**：高过滤率下 HNSW 有效近邻被大量标量条件剔除、搜索空间收缩，要么切 IVF，要么 **Pre-filter + 标量索引 / Partition Key** 先物理裁剪。④ 内存不够的递进杠杆：**SQ8/PQ 量化 + Refiner**（用部分全精度向量对粗排重排，回收量化损失的召回）→ 再不够上 **mmap / DiskANN**。⑤ **Flush 与 Compaction 节奏**要管住，Growing Segment 占比过高会把整体延迟拉上去。
> **锚回项目**：我们中小规模、过滤率不高、内存足，实际选 HNSW + COSINE，`hybrid_store.py` 给 `source_file/doc_id/status/content_type` 建了 **TRIE** 标量索引；没走到 IVF/DiskANN，但参数与架构留了可调口。
**三个防追问**：① 别说「HNSW 碎片化」（不精确），说「有效近邻被大量剔除 / 搜索空间收缩」；② 被问「你自己为什么用 TRIE 不用 Partition Key」→ 租户量级小、过滤率不高，TRIE 够用，多租户大规模再上物理分片；③ Refiner 讲清回收的是量化丢的精度。

**Q16 BM25 公式 / k1、b / 与标准的差异** `[03 Q2.2]`
> `score = Σ IDF(t) × tf×(k1+1) / (tf + k1×(1-b+b×dl/avgdl))`，`IDF = log((N-df+0.5)/(df+0.5)+1)`。`k1=1.5` 控制词频饱和速度，`b=0.75` 控制文档长度归一化强度（b=0 完全不惩罚长文）。**自研实现两处偏差**：倒排表存归一化 tf（`count/doc_length`）而非原始词频；IDF 用 Robertson 非负变体（+1）避免 df>N/2 出现负权重。工程细节：jieba + 约 40 个中文停用词 + 过滤单字纯数字；pickle 持久化**先写 .tmp 再 `os.replace` 原子替换**；`doc_stats` 冗余存 content 前 4000 字，向量库挂了 BM25 侧仍能回填正文。**已知缺陷**（主动说）：同 doc_id 重复 add 不清理旧 posting 导致 df/avgdl 失真；删除是 O(词表) 全扫。

**Q17 RRF 公式与 k=60** `[03 Q2.3]`
> `RRF(d) = Σ_各路 1/(k + rank_d)`，k=60 是原论文经验值。k 压制头部排名的分差：k 越小第 1、2 名差距越大，k=60 时 1/61 vs 1/62 几乎持平，让「多路都靠前」比「单路第一」更重要。**选它而非加权求和的核心理由：向量 COSINE 分和 BM25 分量纲不可比**，加权求和必须先归一化，而归一化对分布敏感（一路极端高分会把整路压扁）；RRF 只用排名，天然免疫。也实现了 weighted（各路 max 归一化后 0.6/0.4）和 max，默认 rrf、未知配置兜底 max。

**Q18 bi-encoder vs cross-encoder，为什么召回用前者精排用后者？** `[03 Q2.4]`
> bi-encoder 把 query/doc **独立**编码成向量，doc 向量可离线预计算，在线只算一次 query 编码 + ANN 搜索，毫秒级，代价是丢失交互信息、精度有上限；cross-encoder 把 query 和 doc **拼接后一起**过 transformer，每层注意力都做交互，精度高但每个 pair 都要前向一次、无法预计算，只能用于小候选集。所以两段式：**从全库召回几十条 → 精排 top5**。工程细节：`bge-reranker-base`，输入截断 512 token、batch=16、doc 侧再截 4000 字符 —— 前一版用 v2-m3 不截断（支持 8192 token）CPU 上 20 条要 60s+，512 截断是拿一点精度换两个数量级延迟；精排通过 `asyncio.to_thread` 跑，不阻塞事件循环。

**Q19 文本分块为什么不用 LangChain 的 splitter？** `[03 Q2.8]`
> 先纠正误解：LangChain 不止固定切分，有一整套家族（`RecursiveCharacterTextSplitter` 按 `\n\n→\n→空格→字符` 递归但不保证句子完整、`NLTK/SpacyTextSplitter` 按句子边界、`MarkdownHeader/HTMLHeader/LatexTextSplitter` 按结构、按 Token/语言切分）。仍自研 `SmartTextSplitter` 的三个原因：① 框架是**单一策略**，要「段落优先 + 超长句子兜底」得自己组合两个 splitter，我把级联写进一个类（`split_by_heading` → `_split_by_paragraph` → `_split_into_sentences`）；② 化工文档大量**表格和图片**，要识别 table/image chunk 并跳过字符切割，交给 `TableProcessor`/`ImageProcessor`（框架里那是 loader 职责，splitter 不管）；③ 长段落含公式，`chunk_size/overlap/min_chunk_size` 语义化控制更贴合。**一句话**：框架有零件没有「组合件 + 表图特殊处理」的成品。

**Q20 表格切分为什么选「语义行分组」？** `[03 Q4.5]`
> 三个方案都试过：**整表一条** —— 500 行表超 chunk 上限、截断后尾部信息永久丢失，长表格 embedding 语义被稀释；**每行一条** —— 「张三|100|2026-01」脱离表头无法理解，检索命中了 LLM 也不知道 100 是什么，还会让 top_k 被同表碎片刷屏。**语义行分组**是中间态：按业务键（客户/类别/订单号）聚行成 chunk，**表头重复注入**保证每块自解释，组标签写进 `section_title`，超大组（>2048 字符且 >20 行）按 20 行子切并标「第 N 部分」。检测降级链：表头关键词匹配 → 最低基数启发式（基数 2~n/3 的列大概率是分类键）→ 放弃分组退固定行数，**检测不出就不硬猜**。

**Q21 置信度阈值为什么低到 0.10？** `[03 Q3.1]`
> 双阈值：有 reranker 分时 **0.10**，否则回退向量分 **0.40**。0.10 不是拍脑袋：表格类 chunk 和短文本在 cross-encoder 眼里天然低分（query 是自然语言、doc 是「| 张三 | 100 |」这种结构），用常规 0.5 会把大量正确答案误判成兜底，是评测数据逼出来的。低分后还有**两级救回**再决定兜底：① 问题含指代词（「前面提到的那个」）→ 仍走知识库让 LLM 结合历史；② jieba 抽实体去疑问词后，实体在 top5 内容中逐字命中 → 仍走知识库。真兜底时强制尾注「来自通用知识，非知识库文档」——宁可承认没查到，不可假装查到。

**Q22 Milvus collection 字段 / 为什么软删除** `[03 Q3.2]`
> 15 个字段：`chunk_id`（VARCHAR64 主键，格式 `md5(source)[:8]_{idx}_{uuid6}`）、`vector(768)`、`content(65535)`、source_file / file_type / page_number / line_start / line_end / chunk_index / content_type / section_title / table_nl_description / created_at / doc_id / status。检索相关：查询恒带 `status=="active"` 实现软删除，`doc_id` 是权限过滤和整文档删除的锚点；`source_file/content_type/doc_id/status` 四个过滤字段建 **TRIE** 标量索引；`table_nl_description` 是表格自然语言描述，生成时优先于 markdown 表格进 prompt，防 LLM 对表格结构过度推断。启动自检 schema：缺 doc_id/status 直接 drop 重建，并校验向量库与 BM25 数据量一致。

**Q23 删一个文档发生什么？两库怎么一致？** `[03 Q3.3]`
> API 删除 → Milvus 按 `doc_id == "..."` delete + flush → **BM25 全量重建**（`query_iterator` 分页拉剩余 chunk，batch=1000）→ pickle 原子落盘 → 元数据 JSON 更新 → 关联评测用例标 stale。重传先 `delete_by_doc_id` 清旧向量，**删除失败必须中止索引**，防新旧 chunk 并存。**深坑**：pymilvus `query` 默认 limit 16384 且**静默截断**，直接全量 query 会悄悄丢数据。**真实排障故事**（大加分）：代码审查发现删除表达式双重引号（转义函数已返回带引号字符串、调用点又包一层 → `doc_id == ""x""`），更隐蔽的是异常被 catch 吞掉只记日志，**删除静默失败**，界面删了向量还在、检索命中幽灵 chunk；修复三层：抽 `_build_eq_expr` 统一拼接、删除失败上抛、API 失败即中止，配回归测试。教训：**吞异常的 catch 会把「响亮失败」变成「静默数据不一致」，后者贵得多**。

**Q24 SSE 流式怎么实现？推什么粒度？** `[03 Q3.4 · 2026-11-12 按当前代码校准]`
> `StreamingResponse(media_type="text/event-stream")`，`data: {json}\n\n`，**四类事件**：**step**（`graph.astream()` 每个节点完成推一次，带输出预览——检索/精排取前 5 条、content 截 500 字符，`chat.py:493`）、**token**（`chat.py:532`）、**done**（answer + citations + trace_id，`:565`）、**error**（`:583`）。
> **粒度是 token 级 + 节点级并存**：`llm_service.py:96-128` 的 `generate_stream` / `chat_stream` 用 `stream=True` 逐 `yield delta.content`；`nodes.py:414-454` 的 generate 节点检测到 state 里有 `_token_queue` 就走 `_stream_to_queue` 旁路把 token 塞进 `asyncio.Queue`，`chat.py:525-532` 并发消费队列推 token 事件；**同时**后台 `_run_graph` 用 `graph.astream()` 收集 step 事件。所以用户既能看到「检索命中了什么」，也能逐字看到答案。工具调用路径（`_chat_with_tools`）是非流式的、直接放哨兵。
> **细节**：流式根 span 打标 `includes_sse_flush=True`，因为它含网络推送耗时，和同步接口直接比会失真 —— **可观测性数据要注明口径**。⚠️ 旧文档说「只有节点级、token 级要加 `stream=True`」是早期状态，**已实现**，别再这么讲（Q68 的逐 token yield 是对的）。

> 结论先行：**不是更好，是在我们这个规模和耦合需求下更合适**，本质是权衡。**值的地方**：`query_rewriter` 单次 LLM 完成改写/路由/分解、general 短路省 ~26s（框架的 `MultiQueryRetriever` 做不到）；切分的表/图跳过贴合化工文档；BM25 的 RBAC post-filter + `doc_stats` 回填和权限/降级链耦合；tracer 零依赖直喂火焰图。**吃亏或已是债的地方**：成熟度（框架经大量边缘场景打磨，我们文档里就有实锤缺陷：BM25 重复 add、删除 O(词表)、reranker 原地改 state 列表、JSONL 无锁重写、pickle 不可扩展）；维护成本自付；生态上 tracer 无 OTLP 导出、BM25 无分布式聚合。**边界**：LangGraph 编排是真用的，自研替代的是 LangChain 积木；且写明了切换触发条件（BM25 到百万级换 ES、pickle/trace 落 PG）。

**★ Q29 项目用的 LangChain / LangGraph 版本？这版做了哪些改动？** `[03 C3 · 2026-11-12 按 uv.lock 校准]`
> **先给真实版本，别背下限**：`pyproject.toml:14-15,63` 下限写 `langgraph>=0.2.0` / `langchain-core>=0.3.0` / `langchain-openai>=0.3.0` / `langgraph-checkpoint-sqlite>=2.0`，但 **`uv.lock` 实际锁定 `langgraph 1.2.11` / `langchain-core 1.5.6` / `langchain-openai 1.5.1` / `langgraph-checkpoint 4.3.0` / `langgraph-checkpoint-sqlite 3.1.2`**（另有 `pydantic 2.13.4` / `fastapi 0.141.1`）。所以有效版本是 **LangGraph 1.x**，不是 0.2 也不是 0.3 —— `0.3` 只是 langchain-core 的下限，别把两个包搞混。

**★ Q30 你们上下文长度设了多少 token？** `[03 C5]`
> **不要报一个数**——项目没有统一 context window 参数，靠多层预算：生成上限 `max_tokens` **4096**（premium / mimo-72b）/ **2048**（standard）/ 1024（文档摘要）；工作记忆注入预算 `MEMORY_TOKEN_BUDGET=1000`；短期历史 Redis 只留 **60 条 / 24h TTL**；`build_context` 进 prompt 只取**最近 6 条** messages + **最近 12 条×200 字符**历史摘要塞 system；长期记忆按 1000 token 预算裁剪；检索上下文单独带。单问题上限 2000 字符、单表 chunk 2048 字符。模型自身窗口**代码没硬编码**，取决于接入的 mimo 模型（通常 32k/128k 级）——我们管的是「往 prompt 塞多少」，不是「模型能装多少」。
> **短板主动讲**：截断按字符数粗估（`content[:200]`）不是真实 tokenizer，中文 1 字符≈1–2 token；因为单轮 context 远小于模型窗口，精度不是瓶颈，严格上线会换真实 tokenizer 裁剪。

**★ Q31 温度、惩罚度之类的值设成多少？** `[新]`

**Q32 JWT vs session / bcrypt 的坑** `[03 Q2.7]`
> JWT 无状态、签名自校验、天然水平扩展，代价是**无法主动吊销**（只能等过期或黑名单），设 24h 折中；payload 只放 `{sub, exp}`，权限每请求查库 —— token 管「你是谁」，DB 管「你能干什么」。bcrypt 坑：passlib 1.7.4（最后一版）与 bcrypt≥4.1 不兼容、hash 直接 ValueError（passlib 探测版本的内部接口变了），锁 bcrypt<4.1 会绑住依赖树，所以弃 passlib 直接用 bcrypt 库：`gensalt(rounds=12)`，且 **bcrypt 只认前 72 字节**，长密码要显式截断。部署级细节：`JWT_SECRET_KEY` 为空时进程内随机生成，多 worker 各进程密钥不同、token 跨 worker 必失败，生产必须显式配置。

**Q33 你的 agent 有反思学习能力吗？** `[03 Q4.7]`
> 先界定：反思 = Reflexion 范式（跑完一轮 → LLM 自我批判 → 沉淀错在哪怎么改 → 下轮带教训重试），本质是答案级自我修正 + 跨轮经验积累。**当前诚实划界**：没有严格在线自反思闭环，但已落地两个落点 —— **离线批量反思**（`EvalReflector` 把低分 case 按维度归因，样本≥3 优先批量归纳找跨 case 模式，单条蒸馏兜底 → 写成系统级教训）、**教训存储与注入**（`LessonStore` 两级：系统级 `scope=__system__` 每次无条件带、会话级按 session 召回）。**未实现**：答案级自评节点、检索级反思（按优先级：先检索级，不打 LLM 调用直接打召回瓶颈；答案级有流式冲突——答案已 SSE 推出、事后改写无法撤回，得设计成「追加补充」）。
> **两个加分设计**：① **语义位隔离** —— 教训是「行为准则」不是「事实依据」，必须独立成段 `## 历史教训`，与 `## 长期记忆`（背景）、`## 参考资料`（事实依据）分开并显式约束「不要把教训当知识库内容引用」，混进去 LLM 会编出「根据知识库记载，法规类问题需注意发布日期」这种鬼话；② **系统级不走语义召回** —— 它记系统内部术语（「expanded_queries 没被利用」），与用户自然语言提问语义距离远，向量根本召不回来，所以每次直接带上。防护：置信度门槛 0.5、来源标记让 LLM 遇冲突自行权衡、上限淘汰（系统级 10 条）、三级独立开关可回退。**代价**：反思加延迟和 token，所以把「变好」主要放在离线评测 + 教训沉淀（零运行时成本），是主动裁剪不是短板。

## Part III · Agent / Workflow / Memory（Q34–Q51）

**Q34 你理解的 Agent Harness 是什么？和单纯调 API、固定 Workflow 有什么区别？** `[05-3]`
> **定义**：Agent Harness 是「大模型外面那一圈让它能真正干活的基础设施」—— 模型只负责「决策下一步」，harness 负责把决策**安全地落地**。拆成六件事，项目都有对应实现：工具注册与元数据（`TOOLS_SCHEMA` + `TOOL_REGISTRY`）、调度编排（StateGraph 条件边 + 回边）、上下文管理（三层记忆 + prompt 拼装）、失败兜底（熔断 + 重试 + 降级 + 超时）、记忆（短期 Redis / 长期 Milvus+JSONL）、观测（Tracer span 树）。
> **区别**：单纯调 API = 一次 `create()` 拿文本，无状态无副作用无兜底；固定 Workflow = 人定义好步骤和分支、模型只填空（我们的下单流程）；Agent = 模型在 harness 提供的工具集里**自主决定下一步**，harness 负责轮次上限、参数校验、执行、结果回写、可观测。三者不是优劣，是「决策权归谁」的取舍：确定性业务必须收归 Workflow，开放问答才交给 Agent。

**Q35 Agent 执行链路里 Java 后端负责哪一层？** `[05-4]`
> **先说清：本项目是 Python 后端，这五层全部在「Java 后端的角色位置」上**，只是实现语言不同。工具注册 = `TOOLS_SCHEMA`/`TOOL_REGISTRY` 两个字典 ↔ Spring `@Bean` + `Map<String,Tool>`；调度 = `_chat_with_tools(max_rounds=2)` + 条件边 ↔ 自研 Agent Loop / LangChain4j `AiServices`；上下文 = `build_context()` 拼「教训/记忆/参考资料」三段 ↔ `PromptTemplate` / `ChatMemory`；记忆 = `MemoryManager` + Redis + Milvus ↔ Redis + PG/ES + `ChatMemoryAdvisor`；观测 = Tracer span 树 → JSONL → 火焰图 ↔ Micrometer Tracing / OTel。**这题的题眼是别慌着说「我没用 Java」**，分层职责与语言无关。

**Q36 Function Calling 在你项目里怎么落地？** `[05-5]`
> 四步，全在 `app/agents/nodes.py::_chat_with_tools` 和 `app/tools/agent_tools.py`：① **工具元数据**用 JSON Schema 直接给模型（`TOOLS_SCHEMA`，8 个工具），描述里写清能力边界、排除危险操作；② **参数 Schema 跟业务槽位对齐，不跟实现对齐**（比如 `customer_name` 而不是 `db_field_1`）；③ **分发器**是「名字 → 执行器」字典，用 `inspect.iscoroutinefunction` 同时兼容 sync / async handler（这个兼容是我们后来补的，早期只支持同步工具）；④ **结果回写必须带 `tool_call_id`** 串成对话历史，否则模型对不上是哪次调用的结果。完整循环：`for _ in range(max_rounds+1)` → 模型返回 tool_calls → 分发执行 → 回写 messages → 再问；轮次用尽最后一次**强制无工具回答**防止无限循环。
**深挖** `[05-5.1~5.5 含完整循环代码 + Java 侧等价物]`。

**Q37 Agent 多轮推理怎么防死循环？** `[05-6]`
> **诚实说明是「部分实现 + 已知缺口」**。已实现：① `max_rounds=2`（最多 3 轮 LLM 调用，`_chat_with_tools`），轮次用尽强制无工具回答；② 底层调用重试 + 熔断（`executor.py` 指数退避 + 0.5~1.5 倍抖动；熔断阈值 5 次 / 恢复 60s / 半开试探 3 次 / 窗口 300s）；③ 整链路降级（单点故障不让请求 500）。**已知缺口**（主动说）：`agent_max_iterations` 和 `tool_max_retries` **只是配置、没接线**；**重复工具调用检测未实现**（同一工具同参数反复调没有拦截）；**连续失败降级未实现**。补法：把每轮 `(tool_name, args_hash)` 存进 state，命中 2 次就强制转文本回答。

**Q38 模型返回的工具调用 JSON 解析失败 / 参数非法，怎么兜底？** `[05-7]`
> 三层：① **JSON 解析失败 → 降级为空参数 `args = {}`**（⚠️ **这是缺陷，静默吞掉**，更好的做法是把解析错误作为 tool 结果喂回模型让它重试）；② **参数非法 → 交给业务侧校验**：`nodes.py` 的 `cast_value` 做 int/float/bool/date 转换，失败返回原值；闸门节点必填缺失不报错，写 `pending_question` 让上层追问；③ **工具执行异常 → 错误信息喂回模型**（`{"error": str(e)}` 作为 tool result），让它自己改参数或换工具。**额外坑**：模型返回 `content` 和 `tool_calls` **同时为空**时，既没答案也没调用，必须有兜底文本否则前端空白。

**Q39 Spring 里工具执行器怎么注册和生命周期管理？AOP 怎么统计每次 Agent 调用？** `[05-9]`
> 项目是 Python、没有 Spring/AOP，但有等价答案且有一点比 AOP 更合适：**注册**用装饰器 + 注册表（`workflows/nodes.py` 的 `HANDLERS: Dict[str, Callable]` + `register_handler(name, fn)`，模块导入时自动注册，5 个 workflow handler）。**埋点**不用 AOP：我们用 tracer 的**上下文管理器**（`with start_span(...)` / `@asynccontextmanager`），因为 AOP 只能切方法边界、拿不到「一次 Agent 调用里第几轮、哪个 tool、token 多少」这种**语义信息**，而 span 是有父子层级的业务语义单元。Java 侧等价做法是 `HandlerInterceptor` + Micrometer `Observation`，或 `@Around` 里手动开 scope 并绑 `trace_id`。

**Q40 手撕：实现一个简化版 Agent 工具调度器（注册 / 按名执行 / 超时中断 / 失败重试 / 调用记录）** `[05-16]`
> 项目里有简化版原型，但**生产用 LangGraph**。核心结构：`@dataclass ToolSpec(name, description, parameters: JSON Schema, fn, timeout)` + `Dict[str, ToolSpec]` 注册表；执行 `asyncio.wait_for(spec.fn(**args), timeout=spec.timeout)` 实现超时中断（注意 `wait_for` 只 cancel 协程，同步 CPU 密集函数 cancel 不掉，要 `to_thread` + 线程无法强杀，得靠进程）；重试用指数退避且**只对可重试异常**重试；调用记录 `ToolTrace(tool_name, args, result, duration_ms, error, round_no)` 追加。**五个要求逐条对应 + 三个设计取舍 + 12 个回归测试**见 `[05-16]`。**收尾一定要讲**：生产版为什么不用它 —— 没有状态持久化、没有断点恢复、没有条件路由、没有幂等，多步业务会退化为手写状态机，所以交给 LangGraph checkpoint。

**★ Q41 项目里的 memory 是怎么做的？（总答）** `[03 D1]`
> **没有「一套 memory」，是双轨**：把「多轮对话记忆」和「业务流程状态」用完全不同的存储语义分开管。对话记忆用自研 Redis + `memory_manager`；业务流程状态才用 LangGraph 原生 `AsyncSqliteSaver` checkpoint。**代码全程没用 LangGraph 的 `MemorySaver`/`InMemorySaver` 管对话（grep 零命中）** —— 这是这题的题眼，面试官默认「memory = 框架内置」，你要先把这个前提纠正。
> **60 秒版**：对话记忆用 Redis List（60 条 / 24h TTL）+ memory_manager 重建上下文，QA 图不挂 checkpointer、是无状态纯函数，高频问答不会把 SQLite 写爆、失败能直接重试；真正用 LangGraph checkpoint 的是下单 workflow，用 AsyncSqliteSaver 持久化槽位和挂起点做可恢复执行。我的判断是：多轮对话和业务状态机存储语义不同，不该都塞进框架 checkpoint。

**★ Q42 QA 图的 memory 具体怎么管？为什么不用 LangGraph checkpoint？** `[03 D1 / 新]`
> 存储：Redis List `session:{id}:messages`，写入一条 pipeline（`session_store.py:76-87`）：`RPUSH` + `LTRIM -60` + `EXPIRE 86400`。重建（`build_context`）：`LRANGE` 取最近 N 条 → **最近 6 条**当 messages、**最近 12 条×200 字符**当历史摘要塞 system prompt，长期记忆按 `MEMORY_TOKEN_BUDGET=1000` 注入。QA 图 `compile()` 无参、`ainvoke(initial_state)` 不传 config（`api/chat.py:338`），**无状态纯函数**。
> **四条理由**：① 高频问答每次写 SQLite 是性能瓶颈；② 无状态 → 请求失败直接重试、无副作用、不产生 checkpoint 膨胀；③ 多副本部署时 Redis 共享状态比本地 checkpointer 自然；④ 对话是短生命、要 TTL、要跨副本共享，Redis 天然合适，checkpointer 是给长事务状态机设计的，硬拿它存对话，TTL/淘汰/多副本都得自己再造一遍。

**★ Q43 Workflow 的 memory 怎么管？** `[03 D1 / 新]`
> 就是 LangGraph 的 checkpoint：`AsyncSqliteSaver` 落 SQLite（`checkpoints/workflows.db`），`engine.get_graph(flow_id, version, checkpointer=get_checkpointer())` → `compile(checkpointer=...)`（`engine.py:451`），进程内单例（`checkpointer.py` 用 `asyncio.Lock` 包住创建临界区），每个 run 一个 `thread_id`（即 run_id）隔离。**存什么**：`WorkflowState`（TypedDict）里的槽位（产品/数量/交期）、`step_results`、`interrupt()` 挂起点，每节点跑完自动落库。**恢复**：`Command(resume=...)` 按 thread_id 接着最新挂起点**线性续跑**（不是树、不能分支）。**两个防坑设计**：单次 interrupt + 条件边 + `_gate_retry`（Q44）；ERP 写入幂等键 `run_id:step_id`（Q45）。
> **双轨对照表**：介质 Redis List ↔ SQLite；编译 `compile()` 无参 ↔ `compile(checkpointer=...)`；生命周期 24h TTL ↔ 无 TTL 可重放；隔离键 `session_id` ↔ `thread_id`；断点恢复 否 ↔ 是；定位 短记忆跨副本 ↔ 长状态业务事务。
> **主动交代的短板**：对话层无回退/无 message id；token 预算字符粗估；Workflow 的 **time-travel 没开**（`checkpoint_id` 只用于 `/history` 展示，没接回 config，框架能力在、业务没用）；`run_id` 只在对话消息文本里（会话过期后挂起 run 会丢）。

**★ Q44 LangGraph 的 `interrupt` 恢复时，节点内部状态会保留吗？** `[03 Q3.7 · 全项目最值得讲的技术问题]`
> **不保留 —— 节点从头重跑、所有逻辑重新执行**。官方原话 "The graph resumes from the start of the node, re-executing all logic"。
> **我栽过的坑**：下单流程要抽 4 个槽位、必填产品和交期，我最初把闸门写成 `while True`，缺什么就 `interrupt()` 问一次。实测发现用户补了「产品=甲烷」之后，checkpoint 里的 `slots` **仍然是空的**，而且产品被重复追问——因为循环里第一次 `interrupt()` 之后写入的中间状态没被持久化，节点重跑又从空 slots 开始。这是个**静默的正确性 bug**：不报错，但数据没了。
> **解法**：把「提问」和「路由」拆开 —— 节点每次执行**只调一次 `interrupt()`**，恢复后拿到本轮值写进 state，再用 `add_conditional_edges` 读 state 里的 `_gate_retry` 标记决定回闸门再问还是往下走。这样恢复永远从干净的单次 interrupt 起点开始，中间状态全靠 state 落地，不靠节点内临时变量。**连带坑**：state 是合并语义，放行时必须**显式写 `_gate_retry=False`**，否则上一轮 `True` 残留会原地死循环。另一个反模式：`slot_extract` 这类抽槽位节点重入时重调 LLM 是可以的，但闸门这种纯判断节点必须拆开，否则恢复时 LLM 会被重复调用（还会覆盖已确认槽位）。
> **引申判断**：确定性的业务流转和非确定性的 LLM 必须分层 —— 「问什么」由 YAML 声明、state 驱动，「答了什么」才交给 LLM 抽槽位，checkpoint 恢复才确定可重放。
> **怎么发现的**（追问预案）：`tests/test_workflow_order.py` 模拟「先缺槽位 interrupt → resume 补值 → 再 resume」两轮，断言 Excel 落库的产品/数量/交期正确，跑出来发现第二次 resume 后第一次的值没了。并发安全：每 run 独立 thread_id，`_gate_retry` 是 per-state 不共享。
> **教训收尾**：用任何带 checkpoint/resume 的框架，第一步都得搞清「恢复到底重跑到哪」——很多人默认是协程式续跑，其实是节点级重跑，这个 mental model 错了，状态设计就全错。

**★ Q45 固定流程怎么保证不重复建单？框架不是会自动重试吗？** `[03 Q3.8]`
> **恰恰相反，框架的语义就是节点会重入**（恢复时从节点开头重跑，副作用节点会被重新执行）。所以幂等不是「防重复调用」，是「防重复执行产生重复业务数据」。做法：幂等键 `run_id:step_id`（流程实例 ID + 步骤 ID），写库时用它 upsert、命中返回已有单号不覆盖（`erp.py:132`）。**关键是幂等键要在业务侧落库**，不能只在内存判断 —— 我把幂等键作为一列写进待排产池 Excel（接真 ERP 就是一个唯一索引），读取时先查这个键。**边界**：通知类副作用与写库策略不同，写库必须严格幂等，通知是 best-effort、失败也不回滚业务（单子已落库），这种「业务已落地、通知可失败」要在代码里显式分开，不能一把 try/except 全吞。

**★ Q46 两张图为什么不能合并？「RAG 只能答问题，业务流程怎么办？」** `[03 Q5.0]`
> RAG 图是**无状态单轮问答**跑完就忘；业务需求是「下一个 5 吨甲烷订单、11.30 发货」—— 要填单、校验、审批、落库、等排产，跨好几天。**不能往 RAG 图里加节点**：生命周期根本不同，混在一起 checkpoint 会塞进 `query_vector`/`filtered_results`/`citations` 这些检索字段，既膨胀又语义污染。所以是**两张并列 StateGraph**，共享 deps（LLM client / tracer / 权限）复用能力、不重复建连接池。
> 技术形态 **YAML 声明骨架 + Python 只写 handler**：业务说流程多且常调整，骨架必须改配置不改代码；但写库、发通知有复杂逻辑逃不掉 Python。7 种节点类型里只有 `side_effect` 和 `notify` 需要写码，其余引擎通用。**两个最能体现想清楚的判断**：① **「等 8 点排产」没做成流程步骤** —— LangGraph 的挂起是「等人」不是「等时间」，把时间等待塞进流程，实例要在 checkpoint 里躺十几个小时，排产必须是定时任务；② **删掉了自己写的 178 行 Checkpointer** —— 查证后确认零调用点，且它想干的活 tracer 早就做得更好（duration_ms 写死 0、无父子层级、前端不消费），不是「改造成 LangGraph 的」，是分工不重叠所以删掉。

**★ Q47 项目的阶段回退与恢复是按「append-only JSONL + parentId 树」那套逻辑做的吗？** `[新]`
> **不是。** 那套是「每条消息带 id + parentId 构成树、恢复时从叶子沿 parent 回溯、回退到历史节点长出新分支」。本项目走三套互不相干的机制：**对话历史** = Redis List（`session:{id}:messages`，RPUSH + LTRIM 60 + 24h TTL），消息只有 `role/content/timestamp/citations`、**没有 id 没有 parent 指针**，纯线性；恢复就是 `LRANGE` 取尾部 N 条拼 prompt，**没有回溯**；`logs/*.jsonl` 是运行日志、`logs/traces/*.jsonl` 是 tracing 观测数据，都不是对话消息流。**Workflow checkpoint** 精神上像「从存档续」，但也是线性续跑不是树。**Tracing JSONL** 确实是 append-only，但只读、只用于观测。
> **没有任何回退 / fork / 编辑分支的实现**（全仓库 grep `rollback/rewind/fork/parent_id` 业务代码零命中），只有整会话清空（`DELETE /api/chat/history/{id}`）和新建会话 —— 那是**推倒重来**不是回退。
> **便宜的修法**：只要「回退」不要「分支」，不需要树也不需要 JSONL 重构，`LTRIM` 就够了 —— 后端加 `truncate_from(session_id, index)` 做 `ltrim(key, 0, index)`，前端加「从这条重新提问」传消息序号，十来行代码。要分支（保留旧问法对比）才需要 id/parentId + active_leaf。**按当前业务（下单→排产，对话只是入口），树结构加在对话层是优化错了地方**；更该补的是 `session_id → run_id` 索引表。

**★ Q48 任务执行一半断网，怎么恢复最新对话？** `[新]`
> 分三层，**最脆弱的是「流式问答断在中途」，下单那层最稳**：
> ① **客户端**（断网/刷新/关页）：能恢复，靠 `chatStore.ts` 的 localStorage —— `initSessions()` 取 `sessions[0].id`、`loadMessages()` 读回消息。代价是浏览器本地副本不是服务端权威，换设备/清缓存就没了，得靠 `GET /api/sessions` 列出来点进去。
> ② **服务端对话层（Redis）**：只能恢复到「上一个完整回合」。`save_turn` 在 SSE 生成器**最末尾**（`chat.py:556`），客户端中途断开 → 生成器被关闭 → `save_turn` 根本不跑 → **这一轮服务端零记录**。表现出来：用户问了、答了一半、网断了，刷新后 localStorage 还留着那句问话，但 Redis 里既没问也没答，再问一遍上下文是断的。两个隐患：`_run_graph` 是 `create_task` 起的（`:521`），断开后没人 await 也没人 cancel，图会白跑完白烧 token；外层 `except Exception` 兜不住断连抛的 `GeneratorExit`（`BaseException`）。
> ③ **Workflow 层**：最稳。每 step 自动 checkpoint 到 `checkpoints/workflows.db`，挂起时整份 state 落库；恢复只需 `POST /api/workflows/runs/{run_id}/resume` 或聊天里 `resume_order` 传 run_id；**ERP 写入已幂等**（`erp.py:129-137` 用 `run_id:step_id` 查重，命中返回已有单号），进程崩了重入也不重复建单 —— 这是 at-least-once 语义的正确处理。
> **永远不会丢**：`ERP待排产池.xlsx`、`checkpoints/workflows.db`、`logs/traces/`；真正易失的只有对话层。**该修**：请求进来先落问句、`finally` 里存已生成部分 + `status=interrupted`；前端 `onError` 分支补 `saveMessages`。

**★ Q49 当前这套会话方案有什么优势？** `[新]`
> 优势是**针对「企业问答型会话」这个业务形态**的，不是通用优势：① **写路径常数开销** —— `add_message` 一条 pipeline（RPUSH + LTRIM + EXPIRE + HSET），O(1)，无文件锁无 fsync 无全量重写；树结构一旦并发写就要处理 parentId 竞争，我们根本没有「树损坏」这个故障模式。② **天然适配多副本** —— 会话在 Redis，K8s 水平扩直接共享；JSONL 本地文件一扩副本就要挂共享存储或同步，项目 `k8s/` 那套部署会踩坑（图片方案的场景是本地 CLI 单机，正好绕开）。③ **存储和 token 都有硬上限** —— 60 条 + 24h TTL 常数封顶、`build_context` 只取 6 条 + 12×200 字符，单次请求 token 可算出来，不会随历史线性涨。④ **对话与图执行职责分离**（我认为最对的一点）：问答图不挂 checkpointer，是纯函数式执行、失败直接重试、不产生 checkpoint 膨胀；如果什么都塞进会话树，高频问答下 SQLite 写入会先成瓶颈 —— 长事务精准只放进需要它的 1% 场景。⑤ **排查一条命令**：`LRANGE session:xxx:messages 0 -1` 看全量。
> **代价**：换个问法重问会污染上下文（旧问答仍在 prompt）、不能 fork 对比、会话 24h 过期后挂起 workflow 的 run_id 就丢了、前端 message id 每次渲染重编做不了编辑交互。**判断标准只有一条：用户会不会回头看历史、会不会在同一处试不同问法**。查一次就走的问答 → 现在更省更稳；要做「对话式工作台」→ 才需要 id/parentId + active_leaf。

**★ Q50 这套 memory 设计跟市面 agent 方案比怎么样？** `[03 D2]` → 见 Q7（同一题的两个问法）。**追问预案**：「那你这算用了 LangGraph 的 memory 吗？」→ 严格说 QA 图没用，我们用的是它 compile 状态图的能力 + 自管 Redis 记忆，原生 checkpoint 只用在 HITL 状态机里，是刻意选择不是没用对。「为什么不干脆全用 checkpointer 统一管理？」→ 对话要 TTL、要淘汰、要跨副本共享，checkpointer 是给长事务设计的，强行存对话这些都得自己再造一遍。「多轮上下文会丢吗？」→ 24h / 60 条内不丢，超出滚出或过期清；且线性无 id、不支持回退分支（已知取舍）。

**★ Q51 项目里最值得分享的技术问题是什么？** `[新]`
> **主推 Q44 的 LangGraph `interrupt` 恢复语义坑**（对口 Agent 工程岗，最深、最反直觉、证明你理解框架恢复语义而不是会调 API）。完整 2 分钟口述稿见 Q44。
> **备选（偏 infra / 稳定性）RAGAS 子进程隔离**：RAGAS 直接在主进程（uvicorn + paddle/torch）里 import 会因运行时冲突 segfault；我把它整个丢进独立子进程 `ragas_worker.py`，stdin/stdout 传 JSON，崩溃/超时只影响当次评分、降级记 0 分不拖垮服务；还发现选的 faithfulness/context_precision/context_recall 都是纯 LLM 指标不依赖真向量，于是用全 0 的 768 维 `DummyEmbeddings` 桩（`ragas_worker.py:29-43`）骗过 embedding 初始化，**省掉 embedding 权重那约 1GB 的加载**（子进程因 torch / transformers 运行时本身仍常驻约 1GB，两个「1GB」不是同一笔内存）；3 个 worker 并发、超时 600s 自动 kill。
> **为什么主推前者**：状态化 Agent 执行是岗位核心，RAGAS 那个偏工程稳定性；但两个都能落到文件行号，被追问都不虚。

## Part IV · 评测体系（Q52–Q59）

**★ Q52 RAGAS 评估方法：你怎么对 Agent 做评测的？** `[新]`
> **不是只跑一个 RAGAS，是多层、可门禁的体系**，四块：
> ① **RAGAS 标准指标**（`faithfulness / context_precision / context_recall`，归一化到 0–10），但做了工程隔离：RAGAS 依赖 torch/uvloop/nest_asyncio，直接 import 会 segfault，所以评分丢到**独立子进程 `ragas_worker.py`**，主进程绝不 import ragas（`ragas_evaluator.py:4-5`），3 个 worker 并发、各约 1GB、超时 600s 自动 kill，崩溃只影响当次、降级记 0 分。
> ② **LLM-as-Judge 六维加权**：accuracy 1.5 / completeness 1.2 / relevance 1.0 / clarity 0.8 / citation 1.0 / hallucination 1.5，**幻觉与反幻觉权重最高**（`llm_judge.py:42-49`）；`temperature=0.1`。⚠️ **已知缺陷（别讲反）**：Judge 的 `_parse_scores` 解析失败时六维**各给 5 分中性值、只打 warning 不标 failed**，且 `runner.py:274` 无条件把它计入加权总分 —— 详见 Q56，旧口径说「标 failed」是错的。
> ③ **自定义业务指标**：反幻觉（`HallucinationFree` 逐条声明验证）、引用准确性（`CitationAccuracy` 正则查 `[来源]` + 期望来源匹配）、多轮一致性（`MultiTurnConsistency` 检查前后轮矛盾）。
> ④ **汇总与门禁**：单条 overall 加权融合，`metrics.py` 里标了 `failed=True` 的自定义指标会被 `runner._add_metric` **直接剔除、绝不用中性分冒充**（`runner.py:261-264` 的有意设计）；**但 Judge 解析失败不走这条路径**，5 分仍计入总分 —— 这正是 Q56 说的待修缺陷。门禁卡总分 ≥7.0、幻觉 ≥7.0、引用 ≥6.0、零单条失败、与上版比回归不超过 -0.5（`gate.py:17-21`）；`reflector` 把低分样本归因成系统级教训回灌优化。
> **60 秒版**：标准 RAGAS 三个指标走独立子进程隔离防 torch 冲突，加 LLM-as-Judge 六维加权（反幻觉权重最高），再加反幻觉/引用/多轮一致性三个自定义指标；汇总加权融合，`failed=True` 的自定义指标直接剔除不冒充（**Judge 解析失败给的 5 分仍计入，是待修缺陷**）；门禁卡总分幻觉引用和回归，配套 reflector 归因。

**★ Q53 最后评测出来的指标是多少？** `[新 · 诚实版，别编数字]`
> **目前没有跑出权威的生产级数字**。真实情况：评测集只有 **10 条用例**（`backend/evaluation/eval_dataset.json`）；翻 `backend/evaluation/reports/` 里的报告，**RAGAS 三个指标全是 0.0** —— 对照 `runner.py:255` `ragas_available = any(v > 0 ...)`，说明 RAGAS 子进程没起来（没 embedding / 模型），优雅降级成 0 后被**直接排除出加权总分**；那几份报告的有效分只来自 rule / hallucination / citation / consistency / judge，大致 judge 6 分左右、反幻觉 6.6–8、引用 7–8、多轮一致性 9+。另外报告 schema 里有 `ragas_answer_relevancy` 但当前代码根本不产出这个指标，且 `gate_passed=True` 配 `avg_score=4.82` 在现版门禁（总分 ≥7.0）下不可能成立 —— **印证是更早一版代码的产物**。
> **话术**：「这套评测要真接 embedding 模型和 LLM 才能出 RAGAS 分，我做这套时后端模型还没接，只做过 10 条用例的本地冒烟跑，那次 RAGAS 没起来、相关指标为 0 被自动排除；样本只有 10 条，我不把它当结论。我现在能交付的是评测体系和方法论，而不是一个写在简历上的漂亮分 —— 因为 RAG 不量化就没法迭代，我宁愿把数字留到接了模型、跑了足量样本之后再说。」
> **为什么这样反而加分**：把弱点翻转成「有工程纪律、不拿小样本糊弄人」。**编一个 8.x 的 overall，一被追问「多少条样本、badcase 长啥样、哪个维度最差」就露馅。**
> **追问「打算跑多少样本、怎么保证评测集质量」**：评测集用 `layer` 分层（core 层全量保底做回归基线，其他层按比例 20% 抽样、固定 `seed=20260828` 可复现），case 带 `expected_contains / expected_not_contains / expected_source / ground_truth` 多字段标注；计划先把 core 层扩到覆盖主要事故类型和规程条目，再靠 `reflector` 把线上 badcase 自动回流成新用例 —— 让评测集跟着真实问题长，而不是一次性人工编。

**★ Q54 一般化工园区，多少指标才算达到要求？** `[新]`
> **没有官方强制标准**（没有任何法规规定「化工园区 RAG 忠实度必须 ≥X」），「达到要求」本质是**按风险等级自定门禁**。化工园区是**安全关键 + 强合规审计**场景，答错安全条款可能误导应急处置、危化品操作，后果是物理性的，所以两类指标必须近零容忍：**忠实度/反幻觉**（答错=真出事）、**引用准确性**（出事要溯源到具体规程条款、审计要追责）；长尾更隐蔽的是「某次特定事故处置」「某个阀门操作」这类罕见查询，**召回不到比答错更难发现**，所以 recall 也要高。
> **建议达标线**（项目里 RAGAS 是 0–1 ×10 到 0–10，Judge 原生 0–10）：
> | 指标 | 可接受 | 良好 |
> |---|---|---|
> | faithfulness 忠实度 | **≥0.90 (9/10)** | ≥0.95 |
> | context_recall 召回 | **≥0.85** | ≥0.90 |
> | context_precision 精度 | ≥0.85 | ≥0.90 |
> | Judge accuracy / hallucination / citation | **8.5 / 9.0 / 8.5** | 9 / 9.5 / 9 |
> | 加权 overall | **≥8.0 才可上线** | ≥8.5 |
> **对照代码，当前门禁偏松**：`gate.py:17-19` 是 `min_overall_score=7.0 / min_hallucination_score=7.0 / min_citation_score=6.0`，对通用助手合理、对化工园区偏松。我建议直接调到 `8.0 / 9.0 / 8.5`，`max_single_fail=0` 保持零容忍；更进一步可以引入**「安全关键子集」**（涉及应急处置 / 重大危险源 / 毒性泄漏的 case 单独打标，走更严门禁、零例外），普通 FAQ 稍松 —— 这是「按风险分级」的思路。
> **面试话术**：「没有强制国标，所以我按风险定线。安全关键场景把忠实度和反幻觉卡到 ≥9、引用 ≥8.5，召回也要 ≥8.5；整体加权 ≥8 才允许上线。我们现在代码里门禁默认 7/7/6，我实际会往 8/9/8.5 调 —— domain 越敏感，门禁越要硬。」

**Q55 RAGAS 三指标分别在测什么？** `[03 Q2.5]`
> **faithfulness**：答案中每个论断能否被检索到的 context 支持 → 测**生成环节**的幻觉；**context_precision**：检索回的 context 里有多少真正相关、相关块是否排前面 → 测**检索环节**噪声；**context_recall**：回答所需信息有多少被检索回来了 → 测**检索环节**遗漏（需 ground truth，缺失时回退用参考答案）。一句话：faithfulness 管「说的都有据吗」，precision/recall 管「据找得准不准、全不全」。**组合诊断价值**：context_recall 低是检索问题，faithfulness 低是生成问题，优化方向完全不同。

**Q56 为什么混合「规则 + LLM Judge + RAGAS」三套，不怕重复吗？** `[03 Q4.2]`
> 测的东西不同且互为校验：规则指标（违禁词、引用格式匹配）零成本零噪声确定性 —— **能用规则的绝不用 LLM**；Judge 测表达质量六维，灵活但有噪声；RAGAS 用不同的 prompt 工程测幻觉/检索质量，与自家 Judge 形成**交叉验证**，两套独立实现都给高分才可信。抗噪声：Judge `temperature=0.1`、给五档细则而非笼统 0–10、失败指标剔除出加权、固定 seed 抽样保证两次评测同题可比（**比较趋势不是绝对值**）。**承认的问题（与 Q52 ④ 一起讲）**：Judge 解析失败时六维各给 5 分中性值，有 warning 日志但**不标 failed、分数仍计入总分**（`llm_judge.py:139-142` + `runner.py:274`），与「失败剔除」哲学冲突，是已识别待修缺陷；只有 `metrics.py` 那套指标才 `failed=True` 并被 `runner._add_metric` 排除。

**Q57 评测的三阶段并发具体怎么并发？为什么 RAGAS 要攒批？** `[03 Q3.5]`
> 阶段 1：用例级 `Semaphore(3)` 并发（受 LLM 限额和 CPU 约束），单用例内幻觉/一致性/Judge 三个独立 LLM 指标再 `gather` 二层并发，单用例异常转 error 不拖垮整批。阶段 2：等阶段 1 全完成，收集 `(question, answer, contexts)` 按 **10 条一批**切块，块间 `Semaphore(3)` 并发、每块起一个 RAGAS 子进程 —— **攒批因为子进程启动 + 环境初始化成本固定（约 1GB/进程），10 条摊薄一次；并发上限 3 是内存约束（3×1GB）**。阶段 3：合并加权出分。**一个不能并发的地方**：多轮用例的 `setup_questions` 必须串行，后轮依赖前轮真实对话上下文，并发了上下文就乱 —— **识别「哪些能并行、哪些本质串行」比堆并发原语重要**。

**Q58 长期记忆怎么去重和遗忘？** `[03 Q3.6]`
> 去重双保险：写入前算内容 md5 前 16 位精确去重（挡完全重复）；再查向量库相似度 ≥0.85 触发 LLM merge（「用户喜欢简洁回答」vs「用户偏好简短回复」字面不同但语义重复，合并成一条）。遗忘：召回排序分 = `relevance × exp(-0.05 × 距上次访问天数) × importance`，时间衰减乘性；后台清理把 30 天未访问且 importance<0.3 标 expired 并删 Milvus 向量；importance 由提取 LLM 分级（明确指令 0.9+、事实陈述 0.6+、闲聊 0.3+）。存储双份（向量在 Milvus 专用 collection、元数据 JSONL）——**已知一致性风险**：JSONL 全量重写无锁，与 Milvus 可能失同步。

**Q59 「你说的这些优化，效果怎么证明？」** `[03 Q5.1]`
> 三类证据：① 评测报告 —— 分层抽样固定 seed、同题可比，幻觉均分 6.1→9.2 有前后报告存 PG（`eval_reports` 表可查）；② 性能数字 —— 评测耗时 45.3→17.7 分钟有运行日志；③ 反向验证 —— trace 修复用「修复前 18% 脏数据率 vs 修复后 0 重叠」做对照。**同时说清口径**：LLM Judge 分数有噪声，我们看**趋势和回归**不看绝对值；reranker 换模型的延迟改善是实测（v2-m3 不截断 20 条 60s+ vs base 512 截断秒级）。⚠️ 与 Q53 一起记：**报告里的数字是本地冒烟/早期跑批，别当成生产权威值讲**。

**Q61 可变对象 vs 不可变对象？函数传参是值传递还是引用传递？** `[06 P1.1]`
> 不可变 `int/str/tuple/frozenset/bytes`，可变 `list/dict/set`。Python 既不是值传递也不是引用传递，是**传对象引用（pass-by-object-reference）**：函数内对可变对象原地修改会影响外部，重新赋值不会。`tuple` 的「不可变」指**元素引用不可改**，里面装个 list 照样能改。
**落点** `config.py:73` `CORS_ORIGINS: List[str]` 是可变默认值，但 Pydantic `BaseSettings` 会做校验复制、不会跨实例共享；`tracing/tracer.py:24` 用 `Tuple[str, ...]` 存 span 栈 —— `ContextVar` 的 default 必须是不可变对象，否则多个请求共享同一个栈（呼应 Q73）。

**Q62 `def f(lst=[])` 为什么是 bug？** `[06 P1.2]`
> 默认参数在**函数定义时求值一次**，不是每次调用。多次调用共享同一个 list，互相污染。正确写法 `lst=None` + 函数体内 `if lst is None: lst = []`。
**落点** 全仓库 grep `def .*=[] / ={}` **零命中** —— 项目统一用 `Optional[...] = None`（`workflows/checkpointer.py:32` `db_path: Optional[str] = None`、`api/auth.py` 的 Request 模型）。**主动说**：这类坑我们靠 Pydantic 模型 + Optional 默认值从写法上规避，而不是靠 code review 兜。

**Q63 浅拷贝 vs 深拷贝？** `[06 P1.3]`
> `copy.copy()` 只复制容器第一层，内部嵌套对象仍共享引用；`copy.deepcopy()` 递归复制。`a = b` 只是绑定同一个对象，连拷贝都不是。切片 `lst[:]`、`list(lst)`、`dict(d)` 都是浅拷贝。
**落点** 项目**没有** `deepcopy`（grep 零命中），因为 LangGraph 的 state 传递刻意走「返回新 dict 让框架 merge」的不可变风格，而不是原地改对象再传。**加分句**：「状态机里我更倾向于构造新 state，避免共享引用带来的隐式副作用」（呼应 Q44 checkpoint 恢复）。

**Q64 `*args` / `**kwargs` 是什么？定义顺序？** `[06 P1.4]`
> `*args` 收位置参数为 tuple，`**kwargs` 收关键字参数为 dict。定义顺序必须是 `必填 → 默认 → *args → 仅关键字 → **kwargs`。
**落点** `prompts/memory.py:40-43` `def format(self, *args, **kwargs)` 复写 `str.format` 做提示词模板；`resilience/circuit_breaker.py:134-136` `get_breaker(name, **kwargs)` 透传断路器配置；`services/llm_service.py:34,47` `_create_completion(**kwargs)` 把采样参数透传给 OpenAI 兼容接口。**这是个好例子**：`**kwargs` 最适合「我不想在一层里穷举下游所有参数」的透传场景。

**Q65 list / tuple / set / dict 的区别与复杂度？** `[06 P1.5]`
> list 有序可变可重复（`append` O(1) 均摊、按值查找 O(n)）；tuple 有序不可变、可哈希（能当 dict key）；set 无序不重复、查找 O(1)；dict 3.7+ 保持插入顺序、键查找 O(1)。set/dict 底层是哈希表，所以 key 必须可哈希。
**落点** `vectorstore/hybrid_store.py` 里 `allowed_doc_ids` 用 **set** 做 O(1) 权限过滤（Q106）；`session_store.py` 用 Redis List 而非 Python list 是因为要跨进程 + TTL —— **顺带讲一句「数据结构选型先看生命周期，再看复杂度」**。

**Q66 `is` 和 `==` 的区别？** `[06 P1.6]`
> `is` 比较对象身份（`id()`），`==` 调用 `__eq__` 比较值。小整数 / 短字符串有缓存池，`is` 偶然为 True 是坑，**判断值一律用 `==`**；判断 `None / True / False` 用 `is`（单例）。
**延伸（项目里的同源坑）** BM25 打分里 `NaN` 是 truthy，`score or 0.0` 挡不住，必须显式 `math.isfinite` 判断（Q116 判别式细节）—— 都是「Python 对象的真值 / 身份不等于业务语义」。

**Q67 闭包是什么？装饰器本质？** `[06 P1.7]`
> 闭包 = 内部函数引用了外部函数的变量、且外部函数已返回，变量仍被留住（存在 `__closure__` 里）。装饰器是「接受函数、返回函数」的闭包，`@deco` 等价于 `func = deco(func)`。写装饰器务必 `functools.wraps` 保留 `__name__/__doc__`，否则链路追踪和日志全乱；带参装饰器是三层函数。
**落点** `api/chat.py:28-40` `_spawn_background` 里的 `_on_done` 是闭包（捕获了 `name`）；用得最多的装饰器是 FastAPI 的 `@router.post(...)`（`api/chat.py:274`），本质是「注册路由 + 包装 handler」；`core/config.py:234` 的 `@lru_cache()` 用标准库装饰器做单例。
**追问「写个计时装饰器」** → 三层结构 + `wraps` + `*args/**kwargs` 透传 + `try/finally` 保证异常时也打日志。

**Q68 生成器 / 迭代器 / 惰性求值？** `[06 P1.8]`
> 迭代器实现 `__iter__ + __next__`；生成器是带 `yield` 的函数，自动实现迭代器协议，**惰性产出、常数内存**。`return` 一次性返回全部，`yield` 每次挂起并保留栈帧；适合大文件 / 流式 / 无限序列，**生成器只能遍历一次**。
**落点（强证据）** `api/chat.py:467-583` SSE 流式接口本身是个生成器，逐 `yield "data: ...\n\n"`；`services/llm_service.py:113,128` 逐 token `yield delta.content`；`api/checkpoints.py:116-117` `history = [h async for h in graph.aget_state_history(...)]` —— **异步生成器必须 `async for` 消费，不能 `await`**（真踩过的坑）；`services/session_store.py:139,181` `async for key in redis.scan_iter(...)` 用 SCAN 替代 KEYS 避免阻塞，也是惰性迭代思想。
**追问「只能遍历一次、要复用怎么办」** → 需要复用就物化索引而不是重扫文件（Q108）。

**★ Q69 `yield from` / `send()` / `close()` / `GeneratorExit`？** `[06 P1.9]`
> `yield from` 委派子生成器；`gen.send(v)` 把值送回挂起点；`gen.close()` 在挂起点抛 `GeneratorExit`，生成器应借 `finally` 释放资源。**`GeneratorExit` 继承自 `BaseException`，不是 `Exception`** —— 所以 `except Exception` 兜不住客户端断连。
**落点（诚实短板，主动讲很加分）** `api/chat.py` SSE 生成器外层是 `except Exception`，断网时抛的是 `GeneratorExit` → **兜不住、没有清理逻辑**；且 `save_turn` 在生成器最末尾（`:556`），断在中途这一轮服务端零记录。正确修法：请求进来先落问句，`finally` 里存已生成的部分答案 + `status=interrupted`；`_run_graph` 是 `create_task` 起的（`:521`），断连时要 cancel。**这题能同时证明「懂生成器协议」和「知道自己系统的缺口」**（业务版见 Q112）。

### 并发与异步（Q70–Q76 · 本项目最强区）

**★ Q70 GIL 是什么？多线程能不能并行？怎么绕？** `[06 P2.1]`
> CPython 的全局解释器锁保证同一时刻只有一个线程执行字节码，简化了引用计数的内存管理，但让 **CPU 密集型多线程无法用多核**；**IO 密集型不受影响**（等待 IO 时释放 GIL）。绕开方式：CPU 密集用多进程 / 进程池 / C 扩展（numpy、torch 底层在 C 里释放 GIL），IO 密集用 `asyncio` 或线程池。
> **项目是混合策略**：① 本地 embedding / CrossEncoder 重排 / 文档解析 / BM25 这些 **CPU 密集**，统一 `asyncio.to_thread(...)` 丢线程池；其中 embedding / reranker 走 numpy / torch 等 **C 扩展、内部释放 GIL 能真正并行**，**但 BM25 是纯 Python 计算，`to_thread` 只解决「不阻塞事件循环」，并行度仍受 GIL 限制**（被追问别一概说「都并行」）；② Redis / PG / LLM HTTP 用 async 客户端（`asyncpg` 连接池、`redis.asyncio`、`httpx.AsyncClient`、LLM 是 `openai.AsyncOpenAI`）走事件循环、不占线程；**但 Milvus 用的是同步 `pymilvus` ORM**（`hybrid_store.py:59`），靠 `asyncio.to_thread` 包两路检索（`:218-220`）+ `execute_sync`（`:285`）变成非阻塞 —— 所以别说「全用 async 客户端」，准确说法是「能异步的异步，只有同步 SDK 的用线程池包」；③ RAGAS 这类会 segfault / 抢运行时的重活，直接**独立子进程** `ragas_worker.py`，连 GIL 都不在同一个进程里。
> **收尾必背**：「GIL 不是『要不要用多线程』的问题，是按任务类型选 **线程池 / 事件循环 / 子进程** 的问题。」
**落点** `embedding_service.py:37,47`、`reranker_service.py:59`、`api/documents.py:407-418`、`api/tracing.py:75,96,104`、`memory_manager.py:260,273,475`（to_thread）；`backend/ragas_worker.py`（子进程隔离）。**追问「那为什么不用线程池做工具并发」** → 见 Q96。

**Q71 协程、事件循环、`async/await` 原理？** `[06 P2.2 · 2026-11-12 校准]`
> `async def` 返回协程对象，**不调用就不执行**；`await` 把控制权交还事件循环，事件循环在 IO 就绪时恢复。是**单线程协作式并发**、不是并行，切换点只有 `await`，所以协程里**绝不能有同步阻塞调用**（会卡死整个 loop）。
**落点（追问「第三方库只有同步 API 怎么办」）** 项目里最好的例子**不是 LLM** —— `llm_service.py:27` 用的是 **`openai.AsyncOpenAI`**，本身就是异步客户端，`_create_completion` 直接 `await` 并交给韧性执行器（`:34-47`）。真正需要包装的是 **Milvus**：`hybrid_store.py:59` 用同步 `pymilvus` ORM，于是 `:218-220` 用 `asyncio.to_thread(self._vector_search, ...)` / `to_thread(self._bm25_search, ...)` 把两路同步检索丢进线程池，再 `asyncio.gather` 并发 —— **这才是「同步 SDK 不阻塞事件循环」的标准解法**；同类还有 `get_executor().execute_sync("milvus", ...)`（`:285`）。
**追问「`AsyncOpenAI` 和把同步 SDK 包 `to_thread` 有什么区别」** → 前者 IO 等待时由事件循环调度、不占线程；后者仍要占线程池里的线程，只是不卡 loop，CPU 密集的同步调用还会受 GIL 限制（Q70）。

**★ Q72 `asyncio.create_task` 有什么坑？** `[06 P2.3]`
> `create_task` 后事件循环**只持弱引用**，不保存强引用的话任务可能在跑完前被 GC 回收；另外没被 `await` 的任务里抛的异常会**静默丢失**（只在 GC 时打一行 "Task exception was never retrieved"）。正确做法：模块级 `set` 存引用 + `add_done_callback` 里 `discard` 并读 `t.exception()` 记日志。
**落点（现成答案，背下来）** `api/chat.py:23-40`：
```python
# fire-and-forget 后台任务引用集合：create_task 只持弱引用，
# 不保存引用的任务可能执行中途被 GC，且异常静默丢失
_background_tasks: set = set()

def _spawn_background(coro, *, name: str) -> asyncio.Task:
    task = asyncio.create_task(coro, name=name)
    _background_tasks.add(task)
    def _on_done(t: asyncio.Task):
        _background_tasks.discard(t)
        # 读 t.exception() 记日志，避免异常被吞
    task.add_done_callback(_on_done)
    return task
```
记忆提取这类「不阻塞响应」的活走这里；`:521` 的 `_run_graph` 也是 create_task。**追问「为什么断网会白烧 token」** → 断连后无人 await / cancel，图会白跑完（Q112）。

**Q90 手撕：两数之和 / 最大子数组和** `[06 P6.1 / P6.2]`
> **两数之和**：一次遍历，用 dict 存「见过的数 → 下标」，边查 `target - x` 边存，O(n) 时间 / O(n) 空间。**最大子数组和**（Kadane）：维护 `cur = max(x, cur + x)` 与 `best = max(best, cur)`，O(n) 时间 / O(1) 空间；空数组返回什么要主动问清。
```python
def two_sum(nums, target):
    seen = {}
    for i, x in enumerate(nums):
        if target - x in seen:
            return [seen[target - x], i]
        seen[x] = i
    return []

def max_subarray(nums):
    if not nums:
        return 0
    cur = best = nums[0]
    for x in nums[1:]:
        cur = max(x, cur + x)      # 要么接着前面的段，要么从 x 重开
        best = max(best, cur)
    return best
```
**边界 / 项目化包装** 重复元素、无解、全负数（Kadane 用 `nums[0]` 起手才对）；从 chunk 分数列表凑阈值、找最优连续高分片段。**诚实**：项目里没有这段实现，只是用场景帮助记忆。

**Q91 手撕：LRU 缓存** `[06 P6.3]`
> 哈希 + 双向链表，`get/put` 都 O(1)；Python 里最省事的是 `collections.OrderedDict`：命中后 `move_to_end(key)` 表示最近使用，容量满时 `popitem(last=False)` 淘汰最久未用。
```python
from collections import OrderedDict

class LRU:
    def __init__(self, cap):
        self.d, self.cap = OrderedDict(), cap
    def get(self, k):
        if k not in self.d:
            return -1
        self.d.move_to_end(k)
        return self.d[k]
    def put(self, k, v):
        if k in self.d:
            self.d.move_to_end(k)
        self.d[k] = v
        if len(self.d) > self.cap:
            self.d.popitem(last=False)
```
**边界 / 项目化包装** `cap=0` 直接不缓存、重复 `put` 同一 key 要更新并刷新顺序、`get` 不存在返回 -1；配置缓存 / 模型实例缓存（呼应 `config.py:234` 的 `@lru_cache`）。**注意**：`functools.lru_cache` 是简化实现，不做 TTL、不做跨进程共享，别把它说成完整缓存层。

**Q92 手撕：扁平化嵌套列表 / 大文件逐行读取不爆内存** `[06 P6.4 / P6.5]`
> **扁平化**：递归 + `yield from` 惰性产出，不先构造完整 list。**大文件**：生成器逐行 + `with` 管理句柄，**绝不 `readlines()` 全量读入** —— 50MB PDF / Excel 解析同理，逐页 / 逐块处理。
```python
def flatten(xs):
    for x in xs:
        if isinstance(x, list):
            yield from flatten(x)
        else:
            yield x

def iter_lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:            # 文件对象本身就是迭代器，惰性
            yield line.rstrip()
```
**复杂度** 时间 O(n)、空间 O(递归深度) / 逐行 O(1)。**项目化包装** 文档树 → chunk 列表、园区规程动辄上百页（Q108）。**诚实**：项目文档解析走 RAGFlow / PyMuPDF，不是这段通用代码。

**Q93 手撕：RRF 融合** `[06 P6.6]`
> `score(doc) = Σ 1 / (k + rank_i(doc))`，`k=60` 是经验常数，用来压低头部 rank 的权重差。按 **rank** 融合而非按分数，天然免疫向量 / BM25 两路量纲不一致的问题。
```python
def rrf(rank_lists, k=60):
    scores = {}
    for lst in rank_lists:
        for rank, doc_id in enumerate(lst, 1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)
```
**复杂度** O(总条数 + 去重后条数 × log 去重后条数)（排序），空间 O(去重后条数)。**项目落点（这题真有实现）** `vectorstore/hybrid_store.py` 的 RRF / weighted / max 三策略，见 Q17；融合后按 `top_k` 截 **10** 再进 cross-encoder 精排 **5**（Q9）。

**Q94 手撕：限流器（滑动窗口）/ 拓扑排序** `[06 P6.7 / P6.8]`
> **滑动窗口限流**：`deque` 存时间戳，每次请求先弹出窗口外的旧戳，再看长度是否超阈值，O(1) 均摊 / O(窗口内请求数) 空间；令牌桶则存「剩余令牌 + 上次补充时间」，按时间差补桶。**拓扑排序**：入度表 + BFS，入度 0 入队、出队时把邻居入度减 1、新变 0 再入队；结果长度 < 节点数说明有环。
```python
from collections import deque

class Limiter:
    def __init__(self, limit, window):
        self.q, self.limit, self.window = deque(), limit, window
    def allow(self, now):
        while self.q and now - self.q[0] >= self.window:
            self.q.popleft()
        if len(self.q) >= self.limit:
            return False
        self.q.append(now)
        return True

def topo(n, edges):
    indeg, adj = [0] * n, [[] for _ in range(n)]
    for u, v in edges:
        adj[u].append(v)
        indeg[v] += 1
    q = deque(i for i in range(n) if indeg[i] == 0)
    out = []
    while q:
        u = q.popleft()
        out.append(u)
        for v in adj[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)
    return out if len(out) == n else None    # None = 有环
```
**项目化包装 / 诚实** `PREMIUM_MODEL_MAX_CONCURRENT=10` 的并发闸门 —— 但项目**限流其实没做**（Q97 列为应做未做）；拓扑排序对应 LangGraph `StateGraph` 的节点调度，但图里有条件边和补检索回边，**不是纯 DAG、不能直接用拓扑序执行**。

**Q95 手撕：反转字符串 / 去重保序 / 线程安全单例 / 生产者消费者** `[06 P6.9 / P6.10]`
> **反转** `s[::-1]`（O(n)）；**去重保序** `list(dict.fromkeys(xs))`（dict 3.7+ 保插入序，O(n)/O(n)）；**线程安全单例** 双重检查 + `threading.Lock`（Python 里更常用模块级导入或 `@lru_cache`，由 GIL 保证导入只执行一次，见 Q79）；**生产者消费者** `queue.Queue` + `put/get/task_done/join`，或 `asyncio.Queue` 配 `create_task`。
```python
from queue import Queue
import threading

def worker(q):
    while True:
        item = q.get()
        try:
            if item is None:      # 毒丸：优雅退出
                return
            handle(item)
        finally:
            q.task_done()

q = Queue(maxsize=100)            # maxsize 就是背压
threading.Thread(target=worker, args=(q,), daemon=True).start()
```
**追问** 线程安全单例为什么要防 `__init__` 重入（Q79）；有界队列满时的 `RejectedExecutionHandler` / CallerRuns 背压（Q96）；`task_done()` 必须放在 `finally` 否则异常会让 `join()` 永远阻塞。**项目化包装** 排产定时任务的队列模型 —— **诚实**：这些是送分题，项目里没有对应实现，30 秒清掉即可。

## Part VI · 后端工程 / Java 侧等价（Q96–Q103）`[05 后半]`

**Q96 线程池在 Agent 并发调用工具场景怎么设计？** `[05-10]`
> **项目没有用线程池做工具并发，但原因值得说**。两个并发场景用的都不是线程池：RAG 评测用 `asyncio.Semaphore(3)`（`runner.py`）；CPU 密集的 embedding / rerank 用 `asyncio.to_thread`（**这里有个真实坑**：同步 CPU 密集操作直接放进 async 会阻塞 event loop，我们踩过才统一包 `to_thread`）。工具调用本身是 IO 密集（HTTP / DB），async 客户端就够了，线程池反而是多余的一层。**Java 侧怎么答**（面试官问的是 Java）：核心参数 `corePoolSize` 按 CPU 核数或 IO 等待比定、`maxPoolSize` 与 `LinkedBlockingQueue` 容量联动（有界队列才会在满时触发扩容）、`keepAlive`、`RejectedExecutionHandler`（CallerRuns 做背压优于 Abort）、线程池按工具类型隔离避免一个慢工具拖垮全部；超时用 `Future.get(timeout)` + cancel；熔断作为拒绝的上一级。**结论**：「用不用线程池」取决于任务是 IO 还是 CPU，不是 Agent 场景的标配。

**Q97 Redis 在 Agent 系统里能承担什么角色？** `[05-11]`
> **项目只用了一个角色：短期会话状态**（`SessionStore`，`session:{id}` List 存轮次 + 60 条 LTRIM + 24h TTL）。其他三个**都没用，且有两个我判断在 Agent 场景下应该避免**：① **限流**：没做但应该做（LLM 供应商并发限额，滑动窗口或令牌桶）；② **工具结果缓存**：慎用、大多是错的 —— Agent 调工具往往带副作用或依赖实时状态（查订单、写 ERP），缓存会把「这次的结果」当成「永远的结果」；③ **分布式锁**：Agent 场景更该用**幂等**而不是锁 —— 我们用 `run_id:step_id` upsert 写 ERP，命中返回已有单号（`erp.py:132`），比抢锁 + 解锁简单且崩溃安全。踩过的坑：Redis 挂时会话回退进程内 dict，多副本下会串会话。

**Q98 Kafka / RocketMQ 在 Agent 任务里怎么用？** `[05-12]`
> **没引入 MQ，是刻意选择**，三个常见理由逐个否掉：① 「异步化」不成立 —— 记忆抽取用 `asyncio.create_task` fire-and-forget、文档解析用进程内异步 + 文件 checkpoint 断点续传，引入 MQ 会带来消息丢失/重复/乱序三个新问题，收益只有「解耦」，而我们本来没有跨服务解耦需求；② 「事件驱动」需求不存在 —— 我们的事件流是单请求内的（一个 trace 7 个节点），span 树表达更直接，MQ 适合的是跨系统长流程编排，而真正的长流程（固定流程引擎）已用 LangGraph checkpoint 解决，比 MQ 更合适；③ 「削峰」—— 当前没有峰值场景。**什么时候该上**（`k8s/kustomization.yaml` 里有 Eval CronJob 是轻量替代）：跨系统长流程编排、多消费者、要重放、峰值明显。**更实用的中间态**：不用 MQ，用「任务表 + 轮询」就能拿到持久化和重试，不引入运维成本。

**Q99 MySQL 里 Agent 对话 / 任务 / 工具调用记录怎么建表、索引、分区？** `[05-13]`
> **我们先说清用的是 PostgreSQL**（不是 MySQL），再给表设计：PG 存业务数据、Redis 存会话、Milvus 存向量和长期记忆、SQLite 存流程 checkpoint。`eval_cases(id VARCHAR(64) PK, data JSONB, layer VARCHAR(16) DEFAULT 'core', ...)`、评测报告表、用户/角色表、工具调用记录表（审计用）。**一个设计选择**：用 `JSONB` 存整个 payload —— Agent 的工具参数/结果 schema 会随业务变，宽表加列代价高，JSONB + GIN 索引兼顾灵活与查询。**对话记录的取舍**：原始轮次在 Redis（TTL 自动回收），PG 只存评测与审计需要的结构化记录，不全量落库（否则高频问答把库写爆）。**索引原则**：高频过滤列（`layer`、`created_at`、`session_id`）建 B-tree，JSONB 用 GIN，联合索引按最左前缀；**分区**按时间（月）做范围分区，配合 TTL 归档。MySQL 差异：JSONB→JSON（无 GIN，用生成列 + 索引）、分区语法不同、无原生数组类型。

**Q100 大文件喂给 Agent，上传→切片→解析→向量化怎么工程化落地？** `[05-14]`
> 完整链路：`上传 → 哈希去重 → 解析(RAGFlow→本地兜底) → 切分(文本/表格分治) → 向量化 → 混合检索`。① 上传先算文件 md5 判重，重传走 checkpoint 断点续传；② 解析 RAGFlow 优先（要它的版式/表格结构化输出），失败降级本地 PyMuPDF + 乱码判定触发 OCR（`OCR_ENGINE` 可切 tesseract 轻量）；③ 切分文本 1024/100 heading-aware、表格语义行分组 + 表头重注入；④ 批量 embedding（`bge-base-zh-v1.5`, 768d, 归一化）；⑤ 双写 Milvus + BM25，pickle 原子替换。文件上限 50MB。**Java 侧映射**：分片上传 + `MessageDigest` 去重、对象存储暂存、解析走独立服务/线程池、批处理用 `Batch` + 背压、向量化结果批量 upsert，全程带 trace_id。

**Q101 Agent 调用敏感工具（删数据、发消息、查订单）怎么鉴权、审计、回滚？** `[05-15]`

**Q102 依赖锁文件生产构建验证过吗？** `[03 Q5.6 / 06 P5.4]`
> 命中真实踩过的坑：审查发现 `uv.lock` 过期于 `pyproject.toml`（声明 44 个主依赖、锁文件只收 42 个，缺 `asyncpg` 和 `tabulate`）。因为 `Dockerfile` 用 `uv sync --frozen --no-dev` 构建，**生产镜像里 `import asyncpg` 直接 ModuleNotFoundError**，`database.py` 和 `auth.py` 启动即崩 —— 本地开发是手动装包，**完全测不出来**。我用干净临时 venv 跑 `uv sync --frozen --no-dev` 完整复现（不是靠推断），修复用 `uv lock` 重生成锁文件并**逐包解析比对确认变更范围**：新增 2 包、移除 0、**版本变化 0**（langgraph 1.2.11 / langchain-core 1.5.6 / fastapi 0.141.1 全部未漂移），避免「修一个缺包顺带升一堆版本」。教训：锁文件是生产构建单一事实来源、CI 应加 `uv lock --check`、**验证必须在干净环境做**。**口径区分**（别和 Q29 混）：这里的「版本变化 0」指**重生成锁文件前后**版本号没动；Q29 说的「下限 0.2 → 锁定 1.2.11」是 **pyproject 声明 vs 锁文件**的差距，两件事。

**Q103 线上出问题怎么定位？** `[03 P5.5 / 05-9]`

### A · 语言基础与内建库（Q124–Q133）

**Q124 `str` 和 `bytes` 有什么区别？乱码是怎么来的？** `[新]`
> Python 3 里 `str` 是 **Unicode 码点序列**、`bytes` 是 **0–255 整数序列**，两者不自动互转：`.encode(encoding)` 走 str→bytes，`.decode(encoding)` 走 bytes→str，默认 utf-8。**乱码本质是用错了 codec 去解码**（比如 GBK 文件按 utf-8 读），`errors='replace'/'ignore'` 只是兜底吞掉错误字节、会把数据悄悄改坏，不是修复。文本 IO 必须显式 `open(..., encoding='utf-8')`；二进制（图片、pickle）必须 `'rb'/'wb'`。
**落点** 项目 `vectorstore/bm25_index.py:110-111` 用 `with open(tmp_path, "wb")` + `pickle.dump` 写索引、`:125` 用 `open(pickle_path, "rb")` 读回，`text/plain` 与二进制模式不能混；文档解析（PyMuPDF/PaddleOCR）产出 str、写 JSONL 追踪日志统一 utf-8。**追问**：`len('中')` 是 1 而 `len('中'.encode())` 是 3；中文按字符截断和按字节截断不是一回事（呼应 Q123 里"上下文按字符粗估 token"的短板）。

**Q125 列表推导、生成器表达式、`map/filter` 怎么选？** `[新]`
> `[x*2 for x in xs]` 一次性建好整个 list（快、占内存、可重复遍历）；`(x*2 for x in xs)` 返回生成器，**惰性、常数内存、只能消费一次**；推导通常比 `for + append` 快，因为循环在 C 层且避免反复查 `append` 名字。经验：数据量大或只遍历一次 → 生成器；要复用/索引/求 len → 列表；嵌套超过两层就拆开写，可读性优先。海象 `:=`（3.8+）能在推导里复用中间结果，典型 `while chunk := f.read(8192)`。
**落点** 项目走的是**异步生成器**这一支：`chat.py:467-583` 的 SSE 生成器、`llm_service.py:96-128` 逐 token yield、`api/checkpoints.py:116` 的 `async for`。**项目零命中**：海象 `:=`、`map/filter` 派生式写法（诚实答"我们统一用推导 + 生成器，风格一致"）。**追问**：生成器表达式作为唯一实参给函数时可省括号；生成器抛 `StopIteration` 由 for 自动吞掉，手动 `next()` 会看到它。

**Q126 `collections` 里常考的几个容器？** `[新]`
> `defaultdict(factory)` 给不存在的键自动造默认值，比 `dict.setdefault` 干净；`Counter` 一行统计可哈希对象、`.most_common(k)`；`OrderedDict` 在 3.7+ 普通 dict 已保序后，只剩 `move_to_end()` / `popitem(last=False)` / 手写 LRU 时才需要；`deque` 双端 O(1)，而 `list.pop(0)` 是 O(n) 搬移；`namedtuple` / `dataclass` 替代裸元组。
**落点** `vectorstore/bm25_index.py:22` 用 `defaultdict(list)` 存倒排表、`:65` `defaultdict(int)` 算词频、`:79` `defaultdict(float)` 累加 BM25 打分；`resilience/error_logger.py:129-131` 用 `Counter` 统计错误 severity/category 分布；**`tools/table_processor.py:6,124` 有一处 `OrderedDict[str, List[List[str]]]` 用于表格行分组**（要保序的可读分组，3.7+ 普通 dict 其实已够，属于可替换的历史写法）。**项目零命中**：`deque`（Q91 手撕 LRU 用 `OrderedDict` 是答题代码，不是项目实现）。**追问**：`defaultdict` 的 factory 必须无参可调用（`list`/`int`/`lambda: []`），且读 `d[k]` 也会**插入**默认值，这是常见副作用。

**Q127 `sorted` 的稳定性、topK、有序序列插入怎么答？** `[新]`
> `sorted(key=...)` 用 Timsort，**稳定**（相等元素保持原顺序），所以多条件排序可以 `key=lambda x: (-x.score, x.id)` 一次搞定，不必排两遍。求前 K 大用 `heapq.nlargest(k, iterable, key=)` O(n log k)，比全排 O(n log n) 更省；`heapq` 是**小顶堆**（要第 k 大就维护 k 个元素的堆，堆顶即阈值）。`bisect_left/right` 在有序序列上 O(log n) 定位插入点，区别在遇到重复值时插在左边还是右边，但 list 插入本身仍是 O(n)。
**落点** 项目当前是「先全排再截断」：`vectorstore/hybrid_store.py` RRF 融合后排序取 `[:top_k]=10`、`agents/nodes.py` reranker 再截到 5。**项目零命中**：`heapq` / `bisect`（诚实答"候选只有 20 条，全排开销可忽略；真到单路召回上千条，我会换成 `heapq.nlargest(5, ...)`"——这是个能主动抛出的优化点）。**追问**：`sort()` 原地返回 None、`sorted()` 返回新列表；`key` 函数只对每个元素算一次。

**Q128 `itertools` / `zip` / `enumerate` / `any` `all` 有什么坑？** `[新]`
> `itertools` 常用 `chain`（拍平多个可迭代）、`islice`（对生成器切片）、`groupby`（**必须先按同一 key 排序**，只分组相邻项）、`product`/`combinations`。`zip` 以**最短**的可迭代对象为准、多出的被丢弃，要补齐用 `zip_longest(fillvalue=...)`；`enumerate(it, start=1)` 比手动计数器干净。`any/all` 短路求值，**`all([])` 是 True**、`any([])` 是 False —— 空列表判断是经典坑。
**落点** 项目 `agents/nodes.py:175` 用 `asyncio.gather(*tasks)` 并发跑比较类子查询，本质就是手工版的"把多个结果对齐再处理"。**项目零命中**：`itertools`、`zip_longest`（诚实答"并发结果聚合用 gather 解决的，没引入 itertools"）。**追问**：`zip(*matrix)` 是转置的惯用写法；Python 3 的 `zip/map/filter` 都是惰性迭代器，`list(zip(...))` 才物化。

**Q129 循环里拼字符串为什么慢？f-string 好在哪？** `[新]`
> `str` 不可变，朴素 `s += x` 每轮都要复制已累积的内容，整体 O(n²)；正确做法是攒进 list 再 `''.join(parts)`，一次分配 O(n)。（CPython 对引用计数为 1 的局部变量有原地扩容优化，但那是实现细节，别依赖。）f-string（3.6+）在编译期直接构建、比 `%` 和 `str.format` 都快，还支持 `f"{x=}"` 调试输出。
**落点** 项目里 prompt 拼装、Milvus 过滤表达式拼接都走 f-string / join（`prompts/`、`hybrid_store.py` 的表达式助手）；`tracing/tracer.py` 写 JSONL 是逐行 append 而非整文件字符串累加。**追问**：`join` 要求元素全是 str，数字要先 `map(str, ...)`；`+` 拼两个短串无所谓，问题只出在循环里。

**Q130 切片 `a[::-1]` 的原理和易错点？** `[新]`
> 语法 `a[start:stop:step]`，step 为负时从右往左取，`a[::-1]` 即反转（返回**新对象**，不改原列表）。切片是**浅拷贝**：容器是新的，元素引用仍共享，所以嵌套列表改内层会互相影响（呼应 Q63）。切片越界**自动夹紧不报错**，而 `a[100]` 索引越界抛 `IndexError` —— 这是常被问的区别。`slice(start, stop, step)` 对象可复用，自定义类实现 `__getitem__` 时可接收它。
**落点** 项目 `memory_manager.py` 的历史截断 `messages[-6:]`、`content[:200]` 都是切片；`hybrid_store.py:225` 融合结果 `[:top_k]` 同理。**追问**：`a[:] = b` 是原地替换全部元素、`a = b[:]` 是浅拷贝后重新绑定，两者对外部引用影响不同。

**Q131 什么叫可哈希？为什么 list 不能当 dict 的键？** `[新]`
> 可哈希 = 有 `__hash__` 且生命周期内哈希值不变，并且与 `__eq__` 一致（`a == b` 必须 `hash(a) == hash(b)`）。`list/dict/set` 可变所以默认 `__hash__ = None`；`tuple`/`frozenset` 只有**元素全可哈希**时才可哈希；自定义类默认按 `id()` 哈希，**一旦重写 `__eq__` 而不重写 `__hash__`，Python 会自动把它置成 None**（经典坑）。CPython dict 用开放寻址、3.7+ 保证插入顺序，平均查找 O(1)，最坏 O(n)（哈希冲突）。
**落点** `vectorstore/hybrid_store.py` 把 `allowed_doc_ids` 转成 set 做 O(1) 权限过滤；BM25 的 `doc_id` 用 str 作键。**追问**：`dict.get(k, default)` 不抛 KeyError 也不会插入；`setdefault` 会插入；`defaultdict` 连读都会插入（Q126）。

**★ Q132 闭包晚绑定（循环里建 lambda）是什么坑？`nonlocal` 和 `global`？** `[新]`
> 闭包捕获的是**变量本身不是当时的值**，函数体在**调用时**才去查外层作用域。所以 `[lambda: i for i in range(3)]` 三个函数全返回 2。修法：① 默认参数固化 `lambda i=i: i`；② `functools.partial`；③ 再包一层工厂函数让每次调用有独立作用域。`nonlocal` 声明修改**外层函数**变量，`global` 修改**模块级**变量；不声明就赋值会创建新的局部变量（`UnboundLocalError`）。
**落点** `api/chat.py:28-40` 的 `_on_done` 是闭包捕获 `name`，但它定义在函数内、每次调用参数 `name` 是独立作用域，所以**不会**踩晚绑定 —— 正好拿来讲"为什么这个闭包是安全的"。**追问**：这是市面 2026 题库里出现频率最高的 Python 陷阱之一；对比 Q67 讲闭包的 `__closure__` 和 `functools.wraps`。

**Q133 Python 3.10 之后有哪些新特性？你们用了哪个？** `[新]`

### B · 函数、面向对象与协议（Q134–Q141）

**Q134 带参数的装饰器怎么写？多个装饰器叠加什么顺序？** `[新]`
> 带参装饰器是**三层嵌套**：最外层收装饰器参数、中间层收被装饰函数、最内层是 `wrapper`；`@retry(n=3)` 等价于 `func = retry(n=3)(func)`。类装饰器实现 `__call__` 即可，适合要保存状态（计数、注册表）的场景。叠加时**装饰自下而上应用、调用自上而下执行**：`@A` 在 `@B` 上面，则 `A(B(func))`。**每一层都要 `functools.wraps`**，否则 `__name__`、`__doc__`、签名全被覆盖，日志/tracing/FastAPI 依赖注入都会出问题。
**落点** `api/chat.py:274` 的 `@router.post("/query", response_model=ChatResponse, summary=...)` 就是带参装饰器（注册 + 包装）；`config.py:234` 的 `@lru_cache` 既可裸用也可带 `maxsize` 参数。**追问**：Q67 讲闭包本质、Q135 讲 `wraps` 保了什么。

**Q135 `functools` 家族常考哪些？** `[新]`
> `wraps`（复制元数据、留 `__wrapped__` 便于 introspection）、`partial`（冻结部分参数造新函数，比闭包晚绑定更安全）、`lru_cache(maxsize)`（记忆化、**参数必须可哈希**、无 TTL、`maxsize=None` 无上限；装饰实例方法会把 `self` 一起缓存住导致实例无法回收）、`singledispatch`（按第一个参数的类型分派实现，泛型函数）、`cached_property`（3.8+ 首次访问计算后写进实例 `__dict__`，之后不再算）。
**落点** `config.py:234` 用 `@lru_cache` 实现配置单例（无参、安全）。**项目零命中**：`partial` / `singledispatch` / `cached_property`（诚实答"没有按类型分派的需求，工具调用分发是显式 dict 映射"）。**追问**：`lru_cache` 的 `.cache_info()` 看命中率、`.cache_clear()` 测试间清理；线程安全（有锁）但不代表被缓存函数可重入。

**Q136 描述符协议是什么？`property` 底层怎么实现？** `[新]`
> 实现了 `__get__` / `__set__` / `__delete__` 任一方法的对象叫描述符；**数据描述符**（有 `__set__`）优先级高于实例 `__dict__`，**非数据描述符**（只实现 `__get__`，如函数、`staticmethod`）会被实例字典覆盖。`@property` 就是典型数据描述符，`classmethod`/`staticmethod`/普通函数本身也都是描述符 —— 这就是 `obj.method` 能自动绑定 self 的原因。3.6+ 的 `__set_name__(owner, name)` 让描述符自动知道自己的属性名，不用手工传。
**属性查找链**（高频）：`__getattribute__` → 数据描述符 → 实例 `__dict__` → 非数据描述符/类属性 → `__getattr__`（仅兜底）。
**落点** 项目**零自定义描述符**（诚实答"我们靠 Pydantic 的字段校验，不需要手写描述符"），但 Pydantic `BaseModel` 内部正是用描述符/元类管理字段的 —— 属于"框架用了、我是使用方"。**追问**：这题和 Q138、Q139 是同一条链，能连着讲会显得体系化。

**Q137 实例方法 / `@classmethod` / `@staticmethod` 区别？类变量有什么坑？** `[新]`
> 实例方法首参 `self`，通过实例访问时借描述符绑定成 bound method；`@classmethod` 首参是 `cls`（子类调用时传子类，常用于替代构造器 `from_xxx`）；`@staticmethod` 无隐式参数，就是放进类命名空间的普通函数。**类变量被所有实例共享**，若类变量是可变对象（list/dict），一个实例 `.append()` 会影响全部实例 —— 应放 `__init__` 里做实例变量。
**落点** `core/model_config.py:10,17` 的 `class ModelProvider(str, Enum)` 用类属性定义枚举项并继承 str（配合 `use_enum_values=True` 可直接当字符串用）；`tests/conftest.py` 用工厂 fixture 而非共享类变量，正是避开共享状态。**追问**：`super()` 按 MRO 找（Q80）；`__slots__` 会禁掉实例 `__dict__`（Q83）。

**Q138 `__getattr__` 和 `__getattribute__` 差在哪？常用魔术方法？** `[新]`
> `__getattribute__` **每次**属性访问都触发，在里面再用 `self.x` 会无限递归，必须用 `object.__getattribute__(self, name)`；`__getattr__` **只在常规查找失败后**触发，适合做懒加载/兼容别名。其他常考：`__str__`（给人看）vs `__repr__`（给开发者看、最好无歧义可重建）、`__len__`/`__bool__`（没 `__bool__` 时用 `__len__` 判真值）、`__call__`（实例可调用）、`__eq__`（重写会置空 `__hash__`，Q131）、`__enter__/__exit__`（Q76）。
**落点** `tracing/tracer.py:89-90` 手写 `__enter__/__exit__` 让 span 自动进出栈；`core/logging_context.py` 用 ContextVar 而非属性魔法做上下文隔离。**追问**：`__getattr__` 里抛 `AttributeError` 而不是别的异常，否则 `hasattr()` 行为会错。

**Q139 元类是什么？什么时候该用？** `[新]`
> 元类是"创建类的类"，默认是 `type`；用 `class X(metaclass=M)` 指定，M 的 `__new__` 在类对象创建时执行，可检查/改写类属性、自动注册子类、实现 ORM 字段收集。但它会显著增加理解成本，**能不用就不用**：3.6+ 的 `__init_subclass__(cls, **kw)` 是更轻量的子类创建钩子，`__set_name__`（Q136）和装饰器通常也能替代。
**落点** 项目**零自定义元类**（诚实答"我们用 Pydantic `BaseModel` 和 `TypedDict`，字段收集交给框架"）。**追问**：`type('X', (Base,), {'a': 1})` 动态建类；元类冲突（多继承时多个元类不兼容）是常见报错；单例元类写法常和 Q79 的四种单例一起问。

**Q140 `abc.ABC` 和 `typing.Protocol` 有什么区别？** `[新]`
> `ABC + @abstractmethod` 是**名义子类型**：子类必须显式继承（或 `register`）并实现抽象方法，实例化时强制检查。`Protocol`（PEP 544，3.8+）是**结构子类型 / 静态鸭子类型**：只要对象有对应方法和属性就满足，无需继承，适合给第三方实现或多种 LLM provider 定接口；默认只能被静态检查器使用，加 `@runtime_checkable` 才能 `isinstance`（且只检查方法存在、不检查签名）。
**落点** 项目**有真实的 ABC 用法**：`tools/base_tool.py:5,67` 定义 `class BaseParserTool(ABC)`，`:71,75,79` 三个 `@abstractmethod` 强制所有文档解析工具实现同一接口 —— 工具种类固定、必须强制实现，正是名义子类型的正确用场。**项目零命中 `Protocol`**：LLM provider 目前配置驱动 + OpenAI 兼容 SDK，没有需要结构化接口的第三方实现。**追问**：被问"多模型适配为什么不定义 Protocol" → 好答案："所有 provider 走同一 SDK，没必要再抽一层；如果接非兼容协议的厂商，我会抽 `LLMProvider(Protocol)` 让静态检查兜住签名，而工具层保持 ABC 因为要强制实现。"

**Q141 positional-only `/`、keyword-only `*`、解包怎么写？** `[新]`
> `def f(a, /, b, *, c, **kw)`：`/` 之前的参数**只能按位置**传，`*` 之后**只能按关键字**传，中间两者皆可。好处是重命名参数不破坏调用方、强制调用处写出语义清晰的关键字。解包：`a, *rest = seq`、`[ *l1, *l2 ]`、`{**d1, **d2}`（后者键冲突时**右边覆盖左边**）、`f(*args, **kwargs)`。单独的 `*` 只作分隔符。
**落点** `services/llm_service.py` 的 `generate/chat/chat_with_tools` 把采样参数透传给 OpenAI 兼容接口；`prompts/memory.py:40` 复写 `str.format` 处理模板里不存在的占位符；`resilience/circuit_breaker.py:134` 透传配置。**追问**：顺序题 Q64 已覆盖；`*` 解包生成器会先全部消费，别对无限生成器用。

### C · 并发与异步进阶（Q142–Q148）

**★ Q142 `gather` / `wait` / `as_completed` / `TaskGroup` 怎么选？** `[新]`
> `asyncio.gather(*aws)` 并发跑、**按输入顺序返回结果**；默认任一失败立即把异常抛给调用方（其余任务**不自动取消**，仍在跑），`return_exceptions=True` 可把异常当结果收下。`asyncio.wait(aws, return_when=FIRST_COMPLETED)` 返回 `(done, pending)` **集合**（无序），适合"谁先回来就先处理 / 还剩几个没完"。`as_completed` 按**完成先后**逐个 yield，适合进度条。`TaskGroup`（3.11+）是**结构化并发**：任一子任务失败就取消同组全部，异常聚合成 `ExceptionGroup`。
**落点** 项目**大量用 gather**：`agents/nodes.py:175` 比较类子查询并行、`evaluation/llm_judge.py:83` 多样本并发打分、`evaluation/runner.py:145,227` 多指标并发。**项目零命中**：`wait`（注意 grep 命中的是 **`wait_for`**，那是超时包装、完全不同）、`as_completed`、`TaskGroup`（3.10 没有）。**追问**：`gather` 传空列表返回 `[]`；取消 gather 本身会取消所有子任务；`wait_for` 超时会 cancel 内部协程（Q144）。

**Q143 `Semaphore` / `asyncio.Queue` / `Event` 分别解决什么？** `[新]`
> `asyncio.Semaphore(n)` 限并发数（比 `threading.Semaphore` 协程安全），`BoundedSemaphore` 还能防止 release 次数多于 acquire；`asyncio.Queue(maxsize)` 是协程版生产者消费者，`put` 满时/`get` 空时都 **await 阻塞而不占 CPU**，配 `task_done()` / `join()` 等消费完；`Event` 一对多广播唤醒（`wait()` / `set()` / `clear()`）。
**落点** 三个都有真东西：`evaluation/runner.py:128`、`llm_judge.py:74`、`ragas_evaluator.py:174` 用 `Semaphore` 压住评测并发；**`api/chat.py:474` 建 `asyncio.Queue`、`agents/nodes.py:338` 的 `_stream_to_queue` 往里推 token** —— 这就是 Q24 里 SSE token 级流式的旁路线，`agents/state.py:14` 把 `_token_queue` 声明在 state 里。**项目零命中** `asyncio.Event`（用 Queue 就够传递信号了）。**追问**：Queue 的 `get_nowait()` / `put_nowait()` 非阻塞版抛异常；`join()` 的计数靠 `task_done()` 配对，漏调用会永久挂住。

**Q144 任务取消、`CancelledError`、`shield()` 怎么处理？** `[新]`
> 取消是**协作式**的，只在 `await` 点生效。`asyncio.CancelledError` 从 **3.8 起继承 `BaseException`**（不是 `Exception`，呼应 Q85），所以 `except Exception` 抓不到它 —— 清理逻辑必须放 `finally`。`wait_for(aw, timeout)` 超时会 cancel 内部任务并抛 `TimeoutError`；`asyncio.shield(inner)` 让内层**不被外层取消波及**，但外层仍会收到 CancelledError（保护的是 inner 不是调用方）。
**落点** `resilience/executor.py:102` 显式 `except asyncio.CancelledError`；**`services/llm_service.py:41` 有句很值钱的注释**：用 `wait_for` 硬掐 SDK 调用会留下悬挂连接、得不偿失 —— 可以直接讲成"我们评估过超时取消的代价，选择不在这一层硬掐"。`timeout_controller.py:57` 用 `wait_for` 做超时包装（Q123 提过它是事后判断、无法中断执行）。**项目零命中** `shield`。**追问**：取消时 `finally` 里再 `await` 可能被二次取消，要用 `uncancel()`（3.11+）或 `shield` 兜；和 Q69 的 `GeneratorExit` 是同一类"BaseException 兜不住"的坑。

**Q145 线程池和进程池怎么选？项目用了哪个？** `[新]`
> `ThreadPoolExecutor` 共享内存、无序列化开销，适合 **IO 密集**或**内部释放 GIL 的 C 扩展**（numpy/torch）；纯 Python CPU 循环受 GIL 限制，多线程反而因切换更慢。`ProcessPoolExecutor` 真并行绕开 GIL，代价是进程启动 + **pickle 序列化**（lambda、局部函数、DB 连接传不过去）+ 内存翻倍。
**落点** `tracing/tracer.py:109` 是 `ThreadPoolExecutor(max_workers=1, thread_name_prefix="trace-persist")` —— **单 worker 是有意设计**：把 JSONL 落盘的阻塞 IO 挪出事件循环，同时保证写入顺序、省掉文件锁（呼应 Q123 里"JSONL 全量重写无锁"那个短板）。**项目零命中** `ProcessPoolExecutor` / `multiprocessing`；RAGAS 走的是 `subprocess` 独立进程（Q75），不是进程池 —— 目的是**崩溃隔离**而非并行加速，这个区分很能显深度。**追问**：`asyncio.to_thread` 底层就是默认线程池，Q70/Q71 已讲。

**Q146 多进程怎么通信？pickle 有什么限制和风险？** `[新]`
> `multiprocessing.Queue` / `Pipe` 底层靠 **pickle 序列化**跨进程传对象，`Manager` 用代理对象共享状态但慢；`Value`/`Array` 走共享内存。限制：**只有可 pickle 的对象能传** —— lambda、闭包、局部函数、打开的文件句柄、DB 连接、线程锁通常都不行；跨进程异常也要能被序列化。安全上 **pickle 反序列化不可信数据可执行任意代码**（`__reduce__`），绝不能拿它接外部输入。
**落点** 两处正好对照：`evaluation/ragas_worker.py` 用 **stdin/stdout 传 JSON** 而不是 `multiprocessing.Queue`，正是为了绕开 pickle 和运行时冲突（torch/uvloop）；`vectorstore/bm25_index.py:111` 用 `pickle.dump` 存本地索引、`:118` 用 `os.replace` 原子替换（自己写自己读，风险可控）。**追问**：JSON 只传基础类型、语言无关、可读，代价是不能传自定义对象；`os.replace` 原子写避免半文件（呼应 Q48 的断网/崩溃恢复）。

**Q147 `asyncio.run()` 做了什么？为什么不能在协程里调？** `[新]`
> `asyncio.run(main())` 每次**新建一个事件循环 → 跑完取消所有残留任务 → 关闭循环**，只能作为同步顶层入口；在已有 loop 运行的地方调用会抛 `RuntimeError: cannot be called from a running event loop`。`get_running_loop()` 拿当前 loop、`await` 只挂起当前协程（把控制权还给 loop，不阻塞线程）、`loop.run_in_executor` / `asyncio.to_thread` 把阻塞活儿丢线程池。
**落点** 项目有个很特别但讲得通的真实写法：**`api/documents.py:407,413` 在 `asyncio.to_thread` 里调 `asyncio.run(...)`** —— 因为要复用一段只提供 async 接口的文档解析代码，而工作线程里没有事件循环，于是先在线程里新建 loop 再跑完关掉。顶层脚本 `eval_runner.py:112`、`migrate_documents.py:110` 则是标准 `asyncio.run(main())`。**追问**：为什么不用 `nest_asyncio`？—— 它靠打补丁嵌套 loop，是给 Jupyter 的权宜之计，生产会引入难查的调度问题；RAGAS 那条链路我们干脆用子进程隔离（Q75）。

**Q148 `Lock` / `RLock` / `Condition` 区别？有 GIL 还需要加锁吗？** `[新]`
> `threading.Lock` **不可重入**，同一线程二次 `acquire()` 会死锁；`RLock` 记录持有线程和计数、可重入；`Condition` 在 Lock 之上提供 `wait()/notify()` 做等待-通知；`Semaphore` 限并发数。**关键认知：GIL 只保证单条字节码原子，`x += 1` 是 LOAD/ADD/STORE 多步，切换可能发生在中间** —— 所以共享可变状态仍必须加锁，别把"有 GIL"当成线程安全。用 `with lock:` 保证异常时也能释放。
**落点** `resilience/circuit_breaker.py:49` 用 `threading.Lock()`，且 **`:55` 注释明确写"避免对不可重入的 Lock 二次加锁导致死锁"** —— 这是能直接甩代码的题；`workflows/handlers/erp.py:24` 用 `_excel_lock` 保护 Excel 并发写，`workflows/loader.py:36,109` 保护 YAML 注册表。协程侧另用 `asyncio.Lock`（`checkpointer.py:27-49`，Q74）。**项目零命中** `RLock`/`Condition`（诚实答"锁的粒度都很小，重入需求用拆分方法规避了"）。

### D · 解释器、内存与性能（Q149–Q154）

**Q149 `import` 到底做了什么？循环导入怎么解？** `[新]`
> `import x` 先查 **`sys.modules` 缓存**（命中就不重复执行），找不到才定位模块、编译/加载 `.pyc`、**执行模块体**并把名字绑到当前命名空间 —— 所以模块级代码只跑一次，也解释了为什么模块级副作用要小心。循环导入的根因是 A 执行到一半去 import B，B 又回头 import A 里**尚未定义**的名字；解法：函数内延迟导入、把公共部分抽到第三个模块、只用于类型标注时放 `if TYPE_CHECKING:`。`__init__.py` 标记常规包，PEP 420（3.3+）允许无它的命名空间包。`from x import y` 绑定的是**对象引用**：之后 `x.y = 新值` 不会更新已绑定的 `y`（`import x` 再取 `x.y` 则会）。
**落点** `backend/app/` 各子包用 `__init__.py` 组织；`if __name__ == "__main__":` 在 5 个脚本里（如 `tools/generate_manufacturing_data.py:240`），让文件既能被导入又能单独跑。**追问**：`importlib.reload` 只重建模块对象、不更新已有的 `from ... import` 绑定，热更新容易踩。

**Q150 循环引用、`__del__`、`weakref` 怎么讲？** `[新]`
> 引用计数归零立即释放，**循环引用**归不了零，靠 gc 的标记-清除兜底；分代回收把对象分 0/1/2 代、新对象在 0 代、存活越久越往上升，减少扫描频率（Q82）。`__del__` 依赖 gc 时机、在循环引用里历史上会导致"不可回收"（PEP 442 / 3.4+ 已大幅改善），所以**关键资源清理一律显式 `close()` / `with`，别写在 `__del__` 里**。`weakref` 持对象但不增加引用计数，适合缓存、观察者、避免父子双向引用成环。
**落点** 项目**零命中** `weakref` / `gc` / `__del__`（诚实答"没有长生命周期的双向引用结构，Q72 的 `create_task` 弱引用是理解它的同族概念"）；资源释放统一走 `@contextmanager`/`__exit__`（`tracer.py:171`、`checkpointer` 的 `close`）。**追问**：`Q72` 里事件循环只持 task 弱引用导致任务被 GC，正是引用计数规则的直接后果；`conftest.py:11` autouse fixture 关全局 checkpointer 也是"显式清理胜过析构"的实践。

**Q151 线上内存涨了怎么排查？** `[新]`

**★ Q152 让你优化一段慢代码，你的顺序是什么？** `[新]`

**Q154 GIL 深挖：为什么存在？3.13 无 GIL 能上生产吗？** `[新]`
> GIL 存在是因为 CPython 用**引用计数**管理内存、且早期大量 C 扩展假设"同一时刻只有一个线程执行 Python 代码"；解释器每 `sys.getswitchinterval()`（默认 5ms）或遇阻塞 IO 时释放锁。**它不阻止 IO 并发，只阻止纯 Python CPU 代码并行**，且纯 Python CPU 多线程还会因抢锁切换比单线程更慢。绕法：多进程、C 扩展内部释放 GIL（numpy/torch）、asyncio、PyPy。3.13 的 PEP 703 提供**可选** free-threaded 构建，但代价是单线程性能回退、大量 C 扩展（torch/paddle/ragas）尚未适配，**生产别当升级项**。
**落点** 项目 3.10，实际策略是 Q70 的"线程池（C 扩展释放 GIL）+ 事件循环（异步 IO）+ 子进程（RAGAS 崩溃隔离）"三层混合。**追问**：被问"那你们为什么不用多进程加速 embedding" → C 扩展（sentence-transformers / torch）内部已释放 GIL，`to_thread` 就能并行，再上进程只是多一份模型权重内存（每个进程 ~400MB BGE + torch），不划算。

**Q155 WSGI 和 ASGI 有什么区别？FastAPI 为什么能流式输出？** `[新]`
> WSGI 是同步的"一请求一响应"调用约定，没有长连接 / WebSocket / 流式的标准表达；**ASGI** 是异步协议，事件驱动（`http.request` / `http.response.body` 分块）、原生支持 lifespan、WebSocket 和 SSE。uvicorn 是 ASGI server，Starlette 是 ASGI 框架，FastAPI 在其上加了 Pydantic 校验 + 依赖注入 + OpenAPI 生成。FastAPI 快主要不是框架本身，而是 **async IO 不阻塞 + Pydantic v2 校验在 Rust/C 层**，别答成"因为用 C 写的"。
**落点** `api/chat.py` 的 `StreamingResponse(media_type="text/event-stream")` 就是 ASGI 才自然的 SSE（Q24 的 step/token/done/error 四类事件）；`main.py:116` 挂 CORS 中间件。**追问**：ASGI 里 `async def` 路由跑在事件循环上，同步 ORM 必须 `def` 路由或 `to_thread`（下一题）。

**★ Q156 `Depends` 依赖注入的原理？`yield` 依赖呢？** `[新]`
> FastAPI 在请求进来前解析路由签名里的 `Depends(...)`，按**依赖树**递归求解并注入返回值；**同一请求内默认缓存**（`use_cache=True`，同一个依赖被多层引用只执行一次，所以鉴权不会重复查库）。依赖可以是函数、类、`__call__` 对象；写成生成器（`yield` 而非 `return`）时，`yield` 之前是 setup、请求处理完（含异常）后在 `finally` 做 teardown —— DB session 就是这么关的。`dependencies=[...]` 可做路由级/应用级全局依赖。
**落点** `api/auth.py:38` `get_current_user(username: str = Depends(verify_token))` 是**嵌套依赖链**，`chat.py:275`（同步问答）和 `chat.py:455`（流式问答）都挂 `Depends(get_current_user)`，`documents.py` 十余处同理。**追问**：⚠️ 主动呼应 Q119/Q123 —— **部分历史/会话接口没挂鉴权、session_id 只有 8 位可枚举**，正是"依赖没有全局挂"的真实缺口，修法是 router 级 `dependencies=[Depends(get_current_user)]` + session 归属校验。讲这题能同时秀"懂框架"和"知道自己系统哪里漏了"。

**Q157 `async def` 和 `def` 路由有什么区别？中间件 / lifespan / `response_model`？** `[新]`
> **最关键的坑**：FastAPI 里写成 `def` 的路由会自动丢进 **anyio 线程池**（默认约 40 线程）执行，写成 `async def` 则**直接在事件循环上跑**。所以同步阻塞代码要么声明 `def` 路由、要么显式 `asyncio.to_thread`；写成 `async def` 却在里面 `time.sleep()` / 同步 SDK，会**卡死整个 loop**（Q71）。`@app.middleware("http")` 基于 BaseHTTPMiddleware，`lifespan`（或 startup/shutdown）管启动加载模型、关闭连接池，`response_model` 用 Pydantic 对响应做**校验 + 序列化 + 过滤多余字段**。
**落点** `backend/app/api/*.py` 有 **83 个 `async def` 路由**，同步活儿（pymilvus ORM、文档解析、embedding）全部 `asyncio.to_thread` 包装（`hybrid_store.py:218-220`、`documents.py:407,418`）—— 完全对得上上面的规则；`main.py:116` 加 CORS 中间件、`main.py:211-221` 启动时预加载 embedding 模型（`EmbeddingService(embedding_config)` 在 `:218`）；`chat.py:274` 的 `response_model=ChatResponse`。**追问**：中间件里 `await call_next(request)` 之后读响应体在 BaseHTTPMiddleware 下有过坑，流式响应尤其要小心别缓冲。

**Q158 Pydantic v2 的校验流程？和 `response_model` 什么关系？** `[新]`
> 输入 dict → `Model.model_validate(obj)` → 按字段注解做**类型校验/转换** → `@field_validator`（`mode="before"/"after"`）→ `@model_validator`（对象级跨字段）→ 得实例；输出用 `model_dump()` / `model_dump_json()`。`ConfigDict` 控制 `extra="forbid"`（拒绝多余字段）、`frozen=True`（不可变，可哈希）、`use_enum_values=True`、`str_strip_whitespace` 等。v2 默认**不再像 v1 那样宽松隐式转类型**，校验失败抛 `ValidationError`，带 `loc / msg / type / input` 便于定位（Q78 讲迁移）。

**Q159 手撕：topK + 二分查找边界** `[新]`
> 求前 K 大：维护 **K 个元素的小顶堆**，堆顶是当前第 K 大，遍历时比堆顶大才替换 → O(n log K) / O(K)，比全排 O(n log n) 省；工程里直接 `heapq.nlargest(k, xs, key=)`。二分边界：`bisect_left` 返回**第一个 ≥ target** 的位置、`bisect_right` 返回**第一个 > target** 的位置，重复值区间就是 `[left, right)`。

```python
import heapq  # bisect_left / bisect_right 是标准库现成的，边界语义见上文

def top_k(xs, k):
    if k <= 0: return []
    heap = []
    for x in xs:
        if len(heap) < k:
            heapq.heappush(heap, x)
        elif x > heap[0]:
            heapq.heapreplace(heap, x)
    return sorted(heap, reverse=True)          # O(n log k)，空间 O(k)

def lower_bound(a, target):                    # 第一个 >= target 的下标
    lo, hi = 0, len(a)
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < target: lo = mid + 1
        else: hi = mid
    return lo                                  # O(log n)，a 必须已排序
```
**边界**：k > len(xs) 时返回全部；空数组返回 0；`bisect` 只定位不插入（list.insert 本身 O(n)）。**项目钩子**：候选从 20 涨到上千时，把 `hybrid_store.py` 的"全排 + `[:top_k]`"换成 `heapq.nlargest`（Q127 那个优化点就落在这里）。

**Q160 手撕：最长无重复子串 + 有效括号** `[新]`
> 滑动窗口用 dict 记每个字符**上次出现的位置**，右指针扩张、遇重复就把左指针跳到 `max(left, last[ch] + 1)`（**必须取 max，否则左指针会倒退**）→ O(n) / O(min(n, 字符集))。有效括号用栈 + 映射，遇右括号检查栈顶是否匹配，最后栈必须为空。

```python
def longest_unique(s: str) -> int:
    last, left, best = {}, 0, 0
    for right, ch in enumerate(s):
        if ch in last and last[ch] >= left:
            left = last[ch] + 1                # 关键：不能让 left 倒退
        last[ch] = right
        best = max(best, right - left + 1)
    return best

def valid_parens(s: str) -> bool:
    pairs, stack = {')': '(', ']': '[', '}': '{'}, []
    for ch in s:
        if ch in pairs:
            if not stack or stack.pop() != pairs[ch]:
                return False
        else:
            stack.append(ch)
    return not stack
```
**边界**：空串返回 0 / True；全是左括号返回 False；`valid_parens` 里非括号字符会被当左括号，严格版应先过滤。**项目钩子**：滑动窗口和「限流时间窗」（Q94）是同一个模板；括号匹配和「JSON/表达式解析」（`llm_judge.py:125` 从 LLM 输出里抠 JSON）是同一类栈问题。

**Q161 手撕：BFS / 层序遍历 + 三数之和** `[新]`
> 树/图的 BFS 用 `deque`（**别用 `list.pop(0)`，那是 O(n)**），层序遍历靠"每轮先记下当前队列长度"来分层。三数之和：先排序 → 固定 `i` → 左右双指针夹逼，和 target 比大小移动指针 → O(n²) / O(1)（不算排序）；**去重是考点**：`i` 跳过重复值、找到一组后左右指针也要跳过重复值。

```python
from collections import deque

def level_order(root):
    if not root: return []
    out, q = [], deque([root])
    while q:
        level = []
        for _ in range(len(q)):               # 先固定本层长度
            node = q.popleft()
            level.append(node.val)
            if node.left:  q.append(node.left)
            if node.right: q.append(node.right)
        out.append(level)
    return out                                # O(n) 时间 / O(w) 空间，w=最大层宽

def three_sum(nums):
    nums.sort(); res = []
    for i in range(len(nums) - 2):
        if nums[i] > 0: break
        if i and nums[i] == nums[i - 1]: continue
        lo, hi = i + 1, len(nums) - 1
        while lo < hi:
            s = nums[i] + nums[lo] + nums[hi]
            if s < 0: lo += 1
            elif s > 0: hi -= 1
            else:
                res.append([nums[i], nums[lo], nums[hi]])
                lo += 1; hi -= 1
                while lo < hi and nums[lo] == nums[lo - 1]: lo += 1
                while lo < hi and nums[hi] == nums[hi + 1]: hi -= 1
    return res                                # O(n^2)
```
**边界**：空树 / 单节点；`nums` 少于 3 个、全正、全零（去重后只出一组 `[0,0,0]`）。**项目钩子**：BFS 模板对应「多跳检索 / 依赖树展开」，双指针夹逼对应「检索分数阈值找组合」（Q90 的两数之和是它的退化版）。

| Q168 | 配置比代码更容易出错，怎么治理？ | dry-run 八项（元模型/引用/hook 白名单/意图流水线/用例回归/入口角色/抽取与 PII/审批链）+ **强制双人发布** + 改版自动灰度 + 快照回滚 + hook 三态下线扫描。核心判断：配置错误影响全体申请人，治理要比代码发布更严 | 「灰度按什么维度」→ 用户组/账号白名单 |
| Q169 | 配置改版了，在途单据怎么办？ | 会话和单据都锁 `definition_version`，运行时按 `get_version()` 快照复现当版字段/规则/卡片；老数据迁移把三张老表改名 `*_legacy`，建同名只读兼容视图，保留 90 天且跨月结/季度结 | 「视图能写吗」→ 只读；写入全部走 flow_* |
| Q170 | 怎么保证 AI 不替你提交、不写库？ | 四个工具全只读；确认卡是「去表单」入口，submit 由本人点；review 强制 admin 级且禁止自审自批；审计只记动作/状态/版本，不记原始 PII。模型只负责整理字段和话术 | 「模型硬要调写接口呢」→ 根本没有注册写工具 |
| ★ Q171 | 讲一个你印象最深的线上 bug | 提交成功后流程状态没退出：`session_keep` 无条件续留，导致「今天天气真好」也被当入园办理、每轮重出核对卡。根因是设计只定义「何时进入」没定义「何时办结」。修法：后端查在途单据（pending/approved）→ 关闭会话兜底；前端 submit 成功清状态；渲染层只留最新一张卡 | 「为什么不用槽位变化判断」→ 会误伤「刚传完附件、字段刚好齐」的正常出卡 |
