# 固定流程（Workflow）设计与实现

本文档说明如何在 LangGraph RAG 项目中落地"公司固定流程"——有状态、有顺序、可能中途需要人工卡点的长事务。

> **更新记录**
> - 2026-10-21 初版：引擎设计 + 实现
> - 2026-10-21 复查修复：闸门边路由、checkpointer API 误用、槽位覆盖（见 §12）
> - 2026-10-22 落地第一个真实业务流：甲烷产品下单（Excel 模拟 ERP）+ 聊天场景意图识别闭环（见 §13）

---

## 一、为什么不能直接往 RAG 图里加节点

现有 RAG 图是**一次性问答图**：

```
query_optimize → [route_intent] → kb_query: vectorize → retrieval → reranker
                 → check_confidence → evidence_judge → [retrieve_more | generate]
                 → END
```

`create_rag_graph()` 里的 `compile()` 不带 checkpointer，`ainvoke()` 一次性跑完，状态即丢弃。

公司固定流程的本质不同：

| 维度 | RAG 问答 | 固定流程 |
|---|---|---|
| 生命周期 | 单轮请求内 | 跨请求、跨天 |
| 状态 | 内存中间产物 | 必须持久化 |
| 中断 | 无 | 可能挂起等人审批 |
| 恢复 | 无 | 从中断点继续，前面的步骤不重跑 |
| 副作用 | 无 | 写库、发通知，必须幂等 |
| 步骤顺序 | 动态路由 | 部分固定 + 条件分支 |

结论：**新增独立的 workflow 图**，与 RAG 图并列，通过共享层（deps / tracer / 权限 / lesson）复用能力。

## 三、YAML 流程定义

流程定义放在 `backend/app/workflows/definitions/*.yaml`，新增流程只加 YAML，不改代码。

```yaml
id: purchase_order
version: 1
name: 采购下单流程
description: 从对话中抽取采购单字段，规则校验，人工审批，写库并通知

slots:                          # 流程级"表单"
  - {name: material_name, type: str, required: true, description: 物料名称}
  - {name: quantity,      type: int, required: true, description: 采购数量}
  - {name: unit_price,    type: float, required: false, description: 单价}
  - {name: supplier,      type: str, required: true, description: 供应商}

steps:
  - id: collect_slots
    type: slot_extract
    prompt: 从用户描述中抽取采购单字段

  - id: check_quantity
    type: rule_check
    rules:
      - {field: quantity, op: gt, value: 0, error: 采购数量必须大于 0}
      - {field: quantity, op: lte, value: 5000, error: 单次采购量超过 5000}
    on_fail: reject

  - id: manager_approve
    type: human_approval
    approver_role: manager
    approver_hint: 请主管确认采购必要性
    on_fail: reject

  - id: finance_approve
    type: human_approval
    approver_role: finance
    when: {field: quantity, op: gte, value: 100}   # 条件生效
    on_fail: reject

  - id: write_order
    type: side_effect
    handler: purchase.write_order

  - id: notify
    type: notify
    handler: purchase.notify

  - id: done
    type: end

  - id: reject
    type: end
```

### 节点类型清单

| type | 实现位置 | 说明 |
|---|---|---|
| `slot_extract` | 通用 | LLM 抽槽位，自动类型转换 |
| `rule_check` | 通用 | 纯规则校验，不调 LLM |
| `branch` | 通用 | 条件跳转（`condition.on_true` / `on_false`） |
| `human_approval` | 通用 | 人工卡点，`interrupt()` 挂起 |
| `llm` | 通用 | 自由生成，结果写入 `step_results[output_key]` |
| `side_effect` | **Python handler** | 写库 / 调业务系统 |
| `notify` | **Python handler** | 企微 / 邮件通知 |
| `end` | 通用 | 终止 |

**只有 `side_effect` 与 `notify` 需要写 Python**，其余全通用。新增流程 90% 是纯 YAML。

### 步骤通用字段

- `when`：条件表达式，条件不满足则跳过本步
- `goto`：显式跳转到指定步骤
- `on_fail`：本步失败时跳转（通常指向 `reject`）

### 规则运算符

`gt` `gte` `lt` `lte` `eq` `ne` `in` `not_in` `contains`
条件额外支持 `truthy` `falsy`。

## 四、状态与持久化

### 4.1 WorkflowState（独立，不继承 RAGState）

```python
class WorkflowState(TypedDict, total=False):
    run_id: str
    flow_id: str
    flow_version: int
    slots: Dict[str, Any]            # 槽位当前值
    step_results: Dict[str, Any]     # 每步产出
    current_step: str
    goto: Optional[str]              # 动态跳转目标
    pending_approval: Optional[Dict]
    status: str
    error: Optional[str]
    metadata: Dict[str, Any]
    user_input: Optional[str]
    pending_question: Optional[str]
```

**为什么不继承 RAGState**：两者生命周期完全不同。`RAGState` 是检索问答的中间产物（`query_vector` / `filtered_results` / `citations`），混进流程状态会让 checkpoint 体积膨胀、语义污染。流程需要检索能力时，**调用**现有 RAG 节点，而不是继承它的状态。

### 4.2 持久化：LangGraph 官方 checkpointer

```python
from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver

saver = AsyncSqliteSaver(conn)
await saver.setup()
graph = workflow.compile(checkpointer=saver)

# thread_id = run_id，流程实例隔离
config = {"configurable": {"thread_id": run_id}}
```

**用 `AsyncSqliteSaver` 而不是 `SqliteSaver`**：后者基于同步 `sqlite3`，在 FastAPI 的 async 事件循环里会阻塞整个 worker。

**依赖**：`langgraph-checkpoint-sqlite>=2.0`（已加入 `pyproject.toml` / `uv.lock`）

生产多实例部署时换成 `langgraph-checkpoint-postgres`（项目已有 PostgreSQL + asyncpg）。

## 五、挂起与恢复

LangGraph 的 `interrupt()` 语义：

- **首次执行**：`interrupt(payload)` 抛 `GraphInterrupt`，图挂起，checkpoint 落盘
- **恢复执行**：`Command(resume=value)` 让图从挂起点继续，`interrupt()` 返回 `value`

两种挂起场景统一用这套机制：

| 场景 | interrupt 载荷 | resume 值 |
|---|---|---|
| 必填槽位缺失 | `{"type": "slot_request", "question": ..., "missing": [...]}` | `{"slots": {...}}` 或 `{"user_input": "..."}` |
| 人工审批 | `{"type": "approval_request", "approver_role": ..., "slots": {...}}` | `{"approved": true, "comment": "..."}` |

### 关键设计：slot_extract 拆成两个节点

`slot_extract` 被拆为**抽取节点**和**闸门节点**（`<step_id>__gate`）：

- 抽取节点：调 LLM 抽槽位，产出写 state（已完成，checkpoint 里有）
- 闸门节点：纯判断必填槽位是否齐备，缺就 `interrupt()` 追问

**为什么不能合在一起**：如果在抽取节点里 interrupt，恢复时该节点会从头重放 → **LLM 被重复调用**。拆开后闸门节点重放只做纯判断，不触发 LLM。

测试 `test_engine_resume_does_not_rerun_llm` 验证了这一点：恢复执行时 LLM 调用次数不增加。

### ⚠️ 更深的坑：节点内多次 interrupt 会丢数据

上面这个"拆两个节点"的方案解决了 LLM 重复调用，但**没有**解决多轮补充槽位时已填值丢失的问题。

LangGraph 官方文档明确：

> The graph resumes from the start of the node, **re-executing all logic**.

恢复时节点**从头重跑**。如果闸门节点里写 `while True` 循环多次调 `interrupt()`，循环内第二次以后写入 state 的中间值**不会被持久化**——节点重跑时又从空 slots 开始。

实测症状：两个必填槽位 a/b，补完 a 后 checkpoint 里 `slots` 仍是 `{}`，且 a 被重复追问。

**正确解法：单次 interrupt + 边路由**

```
抽取节点 → 闸门节点 → (条件边)
                   ├─ _gate_retry=True  → 回到闸门节点（再问一次）
                   └─ _gate_retry=False → 走向后继
```

闸门节点每次执行只调一次 `interrupt()`，把判断结果写进 state 的 `_gate_retry` 标记，条件边读这个标记决定去向：

```python
async def gate(state):
    slots = dict(state.get("slots", {}) or {})
    missing = [s for s in required if slots.get(s.name) in (None, "")]

    if not missing:
        return {"slots": slots, "pending_question": None,
                "status": "running", "goto": None,
                "_gate_retry": False}      # 必须显式置 False

    answer = interrupt(payload)           # 单次
    ...合并...
    still_missing = [s.name for s in required if slots.get(s.name) in (None, "")]
    return {"slots": slots, ..., "_gate_retry": bool(still_missing)}
```

**两个容易漏的点**：

1. 放行时**必须显式写 `_gate_retry=False`**。LangGraph 的 state 是合并语义，上一轮的 `True` 会残留 → 原地死循环。
2. 自环方案（`while True` + 条件边回自己）会触发 `GraphRecursionError`。必须配合"节点内只 interrupt 一次"。

回归测试 `test_gate_keeps_slots_across_multiple_rounds` 覆盖。反证方式：把边路由改成总是放行，测试如期失败。

### 控制流异常必须穿透

`GraphInterrupt` 继承自 `Exception`，会被 `except Exception` 吞掉。引擎里显式处理：

```python
_CONTROL_FLOW_EXCEPTIONS = (GraphInterrupt, KeyboardInterrupt, SystemExit)

try:
    updates = await self._execute(...)
except _CONTROL_FLOW_EXCEPTIONS:
    raise          # 挂起是控制流，不是错误
except Exception as e:
    return {"status": "failed", "error": str(e)}
```

## 七、必须付的三笔"税"

流程化特有的坑，纯 RAG 项目里不存在：

### 7.1 幂等

`side_effect` 重试一次就多一张单。**必须带幂等键 `run_id + step_id`**：

```python
idempotency_key = f"{run_id}:{step_id}"
# INSERT ... ON CONFLICT (idempotency_key) DO NOTHING
```

恢复执行时尤其危险——checkpointer 恢复 + 节点重入都可能触发。

### 7.2 事务边界

"写订单表 + 写明细表 + 扣库存"是**一个事务**，不能拆成三个 `side_effect` 步骤。要么一个 handler 里用 `async with db.begin()` 包完，要么设计成 saga（每步独立事务 + 补偿步骤）。

建议先做前者，简单且符合现状。

### 7.3 通知失败不回滚业务

通知属于 best-effort。**失败只记日志**，绝不能因为发不出企微消息就让采购单回滚。所以 `notify` 必须和 `side_effect` 分成两个步骤。

## 九、为什么删除自研 Checkpointer 而不是改造它

原 `app/tracing/checkpointer.py`（178 行）实现了 `create_task` / `start_step` / `pause_task` / `rollback_to_step` / `get_task_timeline`。查证结果：

- **零调用点**：全项目无任何代码读取 `deps["checkpointer"]`
- **API 是空壳**：`app/api/checkpoints.py` 全部 `raise 404` / `return {}`
- **前端未接入**：无任何 `/api/checkpoints/*` 调用

而它想干的活，tracer 已经做得更好：

| 能力 | 自研 Checkpointer | tracer |
|---|---|---|
| 步骤耗时 | `duration_ms` 写死 `0` | 真实计算 |
| 层级关系 | 平铺 list | 父子 span 树 |
| 前端展示 | 无 | 已有火焰图 |
| 落盘 | 同步覆写单个 JSON | 异步 JSONL + 摘要/详情分离 |

**结论**：不是"改造成 LangGraph 的"，而是删除——因为 tracer 已经是更好的实现。LangGraph 官方 checkpointer 负责它不可替代的职责（驱动图恢复执行），两者分工清晰、互不重叠。

## 十二、复查发现的坑（2026-10-21）

引擎实现完成后做了一轮复查，发现 4 个真实缺陷。这一节记录它们，因为**每一个都是"看起来能跑、实际会错"的那类问题**。

### 坑 1：多轮补充槽位时已补值丢失（严重）

见 §5「节点内多次 interrupt 会丢数据」。这是本项目最值得记住的一个坑。

### 坑 2：`graph.aget_list()` 这个 API 不存在

`GET /workflows/runs` 和 `GET /checkpoints/threads` 一调就 `AttributeError`。正确 API 是 `checkpointer.alist(config, filter=, before=, limit=)`，返回 `AsyncIterator[CheckpointTuple]`。

但 `alist` **不支持 `thread_id="*"` 通配**——`search_where()` 生成的 SQL 是 `thread_id = ?` 精确匹配，传 `"*"` 只会去查名字真叫 `*` 的线程。最终解法是新增 `list_thread_checkpoints()`：

```python
# 先 GROUP BY 拿 thread_id 列表，再逐个 aget_tuple
SELECT thread_id, MAX(checkpoint_id) FROM checkpoints GROUP BY thread_id
```

同时有两个位置认知错误：

- 状态在 `t.checkpoint["channel_values"]`，**不是** `.values`（`.values` 是 `StateSnapshot` 的属性）
- 中断在 `t.pending_writes` 的 `__interrupt__` 通道里，形如 `(task_id, '__interrupt__', [Interrupt(value={...})])`，**不在** `tasks` 里

两种形态统一到 `extract_interrupt_payloads()`。

另：`aget_state_history` 是**异步生成器**，`await graph.aget_state_history(...)` 会失败，必须 `[h async for h in ...]`。

### 坑 3：闸门重抽取覆盖用户已确认的值

补槽位时会再调一次 LLM，模型常复读旧值（把用户填的 88 覆盖成 999）。修法：`_reextract` 增加 `filled` 参数，在 prompt 里明确告知"已确认字段不可重复输出/修改"且只需抽剩余字段；合并时跳过已有值的键。

### 坑 4：`_snapshot` 读一个引擎从不写入的 key

`state.get("__interrupts__")` —— 引擎从不写这个键，导致**所有 workflow 接口返回的 `interrupts` 恒为空**，前端拿不到追问内容。interrupt 本就不在 state 里，而在 LangGraph 快照结构中。改为调用方显式填充。

### 附：零调用点的模块最危险

`handlers/__init__.py` 里 `from ..workflows.nodes import ...` 层级错误（handlers 已在 workflows 下，应是 `..nodes`）。此前从未被调用所以没暴露，一旦真的调 `register_builtin_handlers()` 就 `ModuleNotFoundError`。

**教训**：新写的模块如果没有任何调用点，第一次被调用时才会暴露问题。写完就手动调一次。

## 十三、第一个真实业务流：甲烷产品下单（2026-10-22）

### 13.1 业务链路

```
用户："下一个 11.30 号发货的体积 5 吨的甲烷订单"
  ↓ LLM 识别下单意图 → create_order 工具 → 启动 methane_order 流程
  ↓ 抽取槽位：product=甲烷  volume_ton=5  delivery_date=11.30号→2026-11-30
  ↓ 闸门发现缺 customer → 挂起追问
  ↓ "还需要补充以下信息：customer。"
用户："客户是 X 化工厂"
  ↓ resume_order 工具 → 校验通过 → 写 ERP 待排产池 → 通知用户
  ↓ status=completed，单号 MO202610220001
  ↓
【20:00 定时任务】拉取 pending 订单 → 按交期排产 → 生产计划.xlsx
```

### 13.2 关键设计：workflow 只做"接单并落库"

**"等 20:00 排产"没有做成 workflow 步骤**。

LangGraph 的挂起是**等人**，不是**等时间**。如果流程里写"等到晚上 8 点再排产"，这个实例要在 checkpoint 里躺十几个小时——服务重启、SQLite 锁、实例堆积全出问题。

所以拆成两段：

| | 归属 | 触发方式 |
|---|---|---|
| 接单、校验、落库、通知 | workflow | 用户对话（秒级） |
| 拉取 pending、按交期排产 | 定时任务 | `nightly_scheduling()`，建议 APScheduler / cron 每天 20:00 |

### 13.3 聊天场景的意图识别闭环

下单**不需要新前端页面**——在对话框里聊，LLM 识别出意图就自动走流程。实现是给 LLM 注册两个 function calling 工具：

```
create_order(user_input, flow_id?)   → 启动流程
resume_order(run_id, user_input/slots/approved) → 继续挂起的流程
```

实测的 3 轮工具调用闭环：

```
轮1  create_order → awaiting_input, need_more_info=true, question="还需要补充以下信息：customer。"
轮2  resume_order → completed, order_no=MO202610220001
轮3  "订单已提交，单号 MOxxx，已进入待排产池"
```

**关键：`create_order` 只能启动，`resume_order` 才能继续。** 最初只做了前者，流程挂起后没有任何工具能恢复——用户在对话框里补充的信息永远进不了流程。工具返回的 JSON 里必须回传 `run_id` 和 `next_action`，明确告诉 LLM 下一步调什么。

防误触发两道闸（误建单的代价远大于漏建单）：

1. 工具描述明确排除只读请求：「查询订单状态、查库存、问价格、问交期等只读请求不要使用本工具」
2. 后置拦截 `_looks_like_read_only()`，命中只读词直接拒绝启动流程

### 13.4 中文相对日期归一化

业务上"11.30 号"必须落成绝对日期。新增 `date` 槽位类型：

```yaml
- {name: delivery_date, type: date, required: true, description: 交期}
```

`normalize_date()` 支持：

| 输入 | 输出 | 规则 |
|---|---|---|
| `11.30号` / `11月30日` / `11/30` | `2026-11-30` | 当年，已过则取明年 |
| `下个月底` | `2026-11-30` | 下月最后一天 |
| `本月底` | `2026-10-31` | 本月最后一天 |
| `下个月15号` / `下月20号` | `2026-11-15` | 月份由"下月"限定 |
| `下下个月10号` | `2026-12-10` | **必须先判"下下个月"再判"下个月"** |
| `明天` / `后天` | `2026-10-22` | 相对今天 |
| `1.5号` | `2027-01-05` | 已过日期视为明年 |
| 解析不了的值 | 原样保留 | 交给 `rule_check` 报错 |

匹配顺序有坑：先判"下下个月"再判"下个月"，否则"下下个月10号"会被"下个月"先命中变成 11 月。

### 13.5 Excel 模拟 ERP

`handlers/erp.py` 用 openpyxl 模拟，两个文件：

```
data/ERP待排产池.xlsx    字段：单号 幂等键 产品 数量(吨) 交期 客户 联系人 备注
                         状态 来源run_id 创建时间 排产日期 产线
data/生产计划.xlsx       字段：排产序号 单号 产品 数量(吨) 交期 客户 排产日期 产线
```

- 单号规则：`MO{YYYYMMDD}{4位序号}`，按当天已有最大值递增
- **幂等键 `run_id:step_id`**（LangGraph 恢复时节点重入，没幂等键会重复建单）。幂等命中时**不覆盖原记录**，直接返回已有单号
- 接口层统一用英文字段，落表时才映射成中文表头（混用会静默写成 None）

**接真 ERP 时只改 `erp.py` 里 4 个函数**：`append_pending_order` / `list_pending_orders` / `write_production_plan` / `mark_scheduled`。YAML 和其他代码不用动。但字段名、单号规则、状态枚举要先跟 ERP 那边对齐。

### 13.6 槽位类型清单（更新）

| 类型 | 说明 |
|---|---|
| `str` / `int` / `float` / `bool` | 基础类型转换 |
| `date` | 中文相对日期 → `YYYY-MM-DD`（§13.4） |
