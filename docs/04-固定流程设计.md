# 固定流程（Workflow）设计与实现

本文档说明如何在 LangGraph RAG 项目中落地"公司固定流程"——有状态、有顺序、可能中途需要人工卡点的长事务。

---

## 一、为什么不能直接往 RAG 图里加节点

现有 RAG 图是**一次性问答图**：

```
query_optimize → [route_intent] → kb_query: vectorize → retrieval → reranker
                 → check_confidence → evidence_judge → [retrieve_more | generate]
                 → END
```

`create_rag_graph()` 里的 `compile()` 不带 checkpointer，`ainvoke()` 一次性跑完，状态即丢弃。

公司固定流程的本质不同：

| 维度 | RAG 问答 | 固定流程 |
|---|---|---|
| 生命周期 | 单轮请求内 | 跨请求、跨天 |
| 状态 | 内存中间产物 | 必须持久化 |
| 中断 | 无 | 可能挂起等人审批 |
| 恢复 | 无 | 从中断点继续，前面的步骤不重跑 |
| 副作用 | 无 | 写库、发通知，必须幂等 |
| 步骤顺序 | 动态路由 | 部分固定 + 条件分支 |

结论：**新增独立的 workflow 图**，与 RAG 图并列，通过共享层（deps / tracer / 权限 / lesson）复用能力。

## 三、YAML 流程定义

流程定义放在 `backend/app/workflows/definitions/*.yaml`，新增流程只加 YAML，不改代码。

```yaml
id: purchase_order
version: 1
name: 采购下单流程
description: 从对话中抽取采购单字段，规则校验，人工审批，写库并通知

slots:                          # 流程级"表单"
  - {name: material_name, type: str, required: true, description: 物料名称}
  - {name: quantity,      type: int, required: true, description: 采购数量}
  - {name: unit_price,    type: float, required: false, description: 单价}
  - {name: supplier,      type: str, required: true, description: 供应商}

steps:
  - id: collect_slots
    type: slot_extract
    prompt: 从用户描述中抽取采购单字段

  - id: check_quantity
    type: rule_check
    rules:
      - {field: quantity, op: gt, value: 0, error: 采购数量必须大于 0}
      - {field: quantity, op: lte, value: 5000, error: 单次采购量超过 5000}
    on_fail: reject

  - id: manager_approve
    type: human_approval
    approver_role: manager
    approver_hint: 请主管确认采购必要性
    on_fail: reject

  - id: finance_approve
    type: human_approval
    approver_role: finance
    when: {field: quantity, op: gte, value: 100}   # 条件生效
    on_fail: reject

  - id: write_order
    type: side_effect
    handler: purchase.write_order

  - id: notify
    type: notify
    handler: purchase.notify

  - id: done
    type: end

  - id: reject
    type: end
```

### 节点类型清单

| type | 实现位置 | 说明 |
|---|---|---|
| `slot_extract` | 通用 | LLM 抽槽位，自动类型转换 |
| `rule_check` | 通用 | 纯规则校验，不调 LLM |
| `branch` | 通用 | 条件跳转（`condition.on_true` / `on_false`） |
| `human_approval` | 通用 | 人工卡点，`interrupt()` 挂起 |
| `llm` | 通用 | 自由生成，结果写入 `step_results[output_key]` |
| `side_effect` | **Python handler** | 写库 / 调业务系统 |
| `notify` | **Python handler** | 企微 / 邮件通知 |
| `end` | 通用 | 终止 |

**只有 `side_effect` 与 `notify` 需要写 Python**，其余全通用。新增流程 90% 是纯 YAML。

### 步骤通用字段

- `when`：条件表达式，条件不满足则跳过本步
- `goto`：显式跳转到指定步骤
- `on_fail`：本步失败时跳转（通常指向 `reject`）

### 规则运算符

`gt` `gte` `lt` `lte` `eq` `ne` `in` `not_in` `contains`
条件额外支持 `truthy` `falsy`。

## 四、状态与持久化

### 4.1 WorkflowState（独立，不继承 RAGState）

```python
class WorkflowState(TypedDict, total=False):
    run_id: str
    flow_id: str
    flow_version: int
    slots: Dict[str, Any]            # 槽位当前值
    step_results: Dict[str, Any]     # 每步产出
    current_step: str
    goto: Optional[str]              # 动态跳转目标
    pending_approval: Optional[Dict]
    status: str
    error: Optional[str]
    metadata: Dict[str, Any]
    user_input: Optional[str]
    pending_question: Optional[str]
```

**为什么不继承 RAGState**：两者生命周期完全不同。`RAGState` 是检索问答的中间产物（`query_vector` / `filtered_results` / `citations`），混进流程状态会让 checkpoint 体积膨胀、语义污染。流程需要检索能力时，**调用**现有 RAG 节点，而不是继承它的状态。

### 4.2 持久化：LangGraph 官方 checkpointer

```python
from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver

saver = AsyncSqliteSaver(conn)
await saver.setup()
graph = workflow.compile(checkpointer=saver)

# thread_id = run_id，流程实例隔离
config = {"configurable": {"thread_id": run_id}}
```

**用 `AsyncSqliteSaver` 而不是 `SqliteSaver`**：后者基于同步 `sqlite3`，在 FastAPI 的 async 事件循环里会阻塞整个 worker。

**依赖**：`langgraph-checkpoint-sqlite>=2.0`（已加入 `pyproject.toml` / `uv.lock`）

生产多实例部署时换成 `langgraph-checkpoint-postgres`（项目已有 PostgreSQL + asyncpg）。

## 五、挂起与恢复

LangGraph 的 `interrupt()` 语义：

- **首次执行**：`interrupt(payload)` 抛 `GraphInterrupt`，图挂起，checkpoint 落盘
- **恢复执行**：`Command(resume=value)` 让图从挂起点继续，`interrupt()` 返回 `value`

两种挂起场景统一用这套机制：

| 场景 | interrupt 载荷 | resume 值 |
|---|---|---|
| 必填槽位缺失 | `{"type": "slot_request", "question": ..., "missing": [...]}` | `{"slots": {...}}` 或 `{"user_input": "..."}` |
| 人工审批 | `{"type": "approval_request", "approver_role": ..., "slots": {...}}` | `{"approved": true, "comment": "..."}` |

### 关键设计：slot_extract 拆成两个节点

`slot_extract` 被拆为**抽取节点**和**闸门节点**（`<step_id>__gate`）：

- 抽取节点：调 LLM 抽槽位，产出写 state（已完成，checkpoint 里有）
- 闸门节点：纯判断必填槽位是否齐备，缺就 `interrupt()` 追问

**为什么不能合在一起**：如果在抽取节点里 interrupt，恢复时该节点会从头重放 → **LLM 被重复调用**。拆开后闸门节点重放只做纯判断，不触发 LLM。

测试 `test_engine_resume_does_not_rerun_llm` 验证了这一点：恢复执行时 LLM 调用次数不增加。

### 控制流异常必须穿透

`GraphInterrupt` 继承自 `Exception`，会被 `except Exception` 吞掉。引擎里显式处理：

```python
_CONTROL_FLOW_EXCEPTIONS = (GraphInterrupt, KeyboardInterrupt, SystemExit)

try:
    updates = await self._execute(...)
except _CONTROL_FLOW_EXCEPTIONS:
    raise          # 挂起是控制流，不是错误
except Exception as e:
    return {"status": "failed", "error": str(e)}
```

## 七、必须付的三笔"税"

流程化特有的坑，纯 RAG 项目里不存在：

### 7.1 幂等

`side_effect` 重试一次就多一张单。**必须带幂等键 `run_id + step_id`**：

```python
idempotency_key = f"{run_id}:{step_id}"
# INSERT ... ON CONFLICT (idempotency_key) DO NOTHING
```

恢复执行时尤其危险——checkpointer 恢复 + 节点重入都可能触发。

### 7.2 事务边界

"写订单表 + 写明细表 + 扣库存"是**一个事务**，不能拆成三个 `side_effect` 步骤。要么一个 handler 里用 `async with db.begin()` 包完，要么设计成 saga（每步独立事务 + 补偿步骤）。

建议先做前者，简单且符合现状。

### 7.3 通知失败不回滚业务

通知属于 best-effort。**失败只记日志**，绝不能因为发不出企微消息就让采购单回滚。所以 `notify` 必须和 `side_effect` 分成两个步骤。

## 九、为什么删除自研 Checkpointer 而不是改造它

原 `app/tracing/checkpointer.py`（178 行）实现了 `create_task` / `start_step` / `pause_task` / `rollback_to_step` / `get_task_timeline`。查证结果：

- **零调用点**：全项目无任何代码读取 `deps["checkpointer"]`
- **API 是空壳**：`app/api/checkpoints.py` 全部 `raise 404` / `return {}`
- **前端未接入**：无任何 `/api/checkpoints/*` 调用

而它想干的活，tracer 已经做得更好：

| 能力 | 自研 Checkpointer | tracer |
|---|---|---|
| 步骤耗时 | `duration_ms` 写死 `0` | 真实计算 |
| 层级关系 | 平铺 list | 父子 span 树 |
| 前端展示 | 无 | 已有火焰图 |
| 落盘 | 同步覆写单个 JSON | 异步 JSONL + 摘要/详情分离 |

**结论**：不是"改造成 LangGraph 的"，而是删除——因为 tracer 已经是更好的实现。LangGraph 官方 checkpointer 负责它不可替代的职责（驱动图恢复执行），两者分工清晰、互不重叠。

## 十、扩展方向

- **`retrieve_and_check` 节点**：调现有 vectorize/retrieval/reranker，让流程能查库存/查制度
- **并行分支**：`parallel` 节点类型，多个步骤同时跑
- **流程版本灰度**：`FlowDef.version` 已支持多版本共存，可按用户/租户路由
- **流程定义热更新**：`FlowRegistry.load(force=True)` + `engine.invalidate(flow_id)` 已就绪
- **审批超时**：`StepDef.timeout_hours` 字段已定义，配合定时任务扫描
- **多租户隔离**：`thread_id` 建议改为 `tenant_id:run_id`
