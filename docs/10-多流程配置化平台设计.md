| **D14** | Git 备份 | **每次发布后异步导出只读 JSON 快照**；DB 是唯一权威，Git 不参与运行时、不反向同步（§6.2） |

## 1. 目标边界（必须提前对齐）

### 1.1 配置可覆盖（业务同事可改，无需开发）

依据 D8「全部可配」，新增一个同类流程时，下列内容都必须能在后台配出来：

- **字段**：key / label / 类型 / 必填 / 正则 / 范围 / 枚举 / 联动显隐 / PII 标记 / 分组与排序
- **字段抽取规则**：正则、日期格式、归一化、打码、高置信原文一致性校正（见 §3.3）
- **意图**：有序规则流水线、否定词、只读问法、歧义提示、判定器选择、意图用例表
- **附件**：类别、是否必交、数量上限、格式、**跨流程复用策略**
- **状态机**：显示名、允许的流转组合、流转前置 hook（状态 key 固定，见 §3.6；**必须保留人工审批流转**）
- **展示**：确认卡字段与布局、列表列、预填行为
- **话术**：system prompt、追问提示、示例、只读规则文案（轻量 Skill 包，随配置版本走）
- **入口**：菜单项、快捷按钮、可见角色、路由路径（见 §3.8）
- **会话**：多轮保持、中途切换、选择卡防死循环、版本锁定（见 §3.7）
- **编号规则**、审批角色（受角色白名单约束，见 §7.4）

### 1.2 必须留代码（开发者预先注册，业务只能「选」）

- 跨字段复杂校验、时间冲突、库存 / 额度校验
- ERP 等外部系统接口适配器
- 自定义表单 / 确认卡组件
- 特殊计算（编号、二维码生成）
- 权限框架、PII 脱敏、审计、附件归属隔离

> **与 D8 不矛盾**：这些能力由开发者**一次性**注册成命名 hook / 组件插槽，之后所有新流程都从白名单里「选」。判定「零改动」的口径是**新增第 N 个流程时开发者改动文件数 = 0**，不是「平台首次建设零代码」。

### 1.3 明确不在本设计范围

- 对接 ERP 的实时写入与跨系统事务（预留 hook + MCP 适配位，阶段 4 再做）
- 配置里写任意表达式 / 脚本（**禁止**，见 §7.3）
- 替换现有 RAG 主链与知识库问答能力
- 外部通知（短信 / 企微等，当前需求已排除）
- 本版接入外部意图判定模型（只留接口，见 §10.1）

> **真话**：「不改代码」能覆盖的是**同类的表单型申请审批流程**（字段、材料、审批链不同的申请单）。对接实时库存、跨系统事务、复杂计算仍需开发者写适配器。需提前与业务方书面对齐这个边界，避免期望落空。

## 2. 总体架构

```
① 配置层      业务同事在后台编辑流程定义
              （字段 / 抽取规则 / 意图流水线 + 用例 / 附件 / 状态显示名 / 卡片 /
                话术 / hooks / 权限 / 会话 / 入口）
      ↓
② 治理层      dry-run 校验 → 预览 → 双人发布 → 灰度 → 回滚；版本 diff + 操作审计
      ↓
③ 运行时注册表 已发布配置编译成：路由流水线 / 工具 schema / 卡片 schema /
              权限 / 状态机 / 菜单入口；按版本号缓存
      ↓
④ 通用内核    单 Agent 工具循环 + 通用四件套 + 通用确认卡 + 通用提交 API
      ├─ 通用数据表（form_data JSONB，新增流程零 DDL）
      └─ 扩展点白名单（复杂校验 / ERP 适配，开发者预留）
      ↓
⑤ 前端        零规则：只渲染后端下发的候选卡、确认卡、动态菜单

框架强制（配置不可关闭）：PII 脱敏 · 权限 · 审计 · 附件归属隔离 · 确认前零写库 · 人工审批流转
```

### 2.1 一次请求的链路

1. **意图路由（后端权威）**：后端按所有已发布配置的 `intent.rule_pipeline` 做确定性判定，输出 `flow_id` + 动作（只读咨询 / 办理 / 查状态 / 补材料）；低置信或歧义时通过 SSE `intent_choice` 下发候选流程，由用户点选。前端**不持有任何判定规则**
2. **注册表按 `flow_id` 裁剪工具集** → 只挂该流程的通用四件套，其余流程工具不可见
3. **单 Agent 工具循环** → 槽位抽取、多轮追问、组装 payload、推确认卡（SSE `flow_payload`）
4. **用户点确认** → 前端调通用业务 API → 写库 → 状态机 → 有权限的审核人审批
5. 返回「已提交」结果（**模型只产出到第 3 步，不写库**）

> `force` 只用于把用户在选择卡上的决定回传给后端以放宽歧义，**不绕过后端权限与最终判定**。

### 2.2 两套状态机的权威划分

评审发现 v1 同时保留了「配置里的 `workflow` 状态机」和 `workflows/` YAML 引擎，未说明谁权威。v2 明确：

| 组件 | 职责 | 权威范围 |
|---|---|---|
| **配置 `workflow` 段** | 申请单状态、流转、守卫 hook、审核角色 | **所有新流程的唯一权威** |
| `workflows/` YAML 引擎 | 既有 `methane_order` / `purchase_order` 的确定性节点编排 | 只服务这两个既有流程，不读取配置、不参与新流程 |
| 对话内核 | 确认之前的抽取 / 追问 / 确认卡 | 不产生状态、不落库 |

阶段 0–3 不需要编译配置成 YAML；若将来出现「提交后多步补偿 / 跨系统事务」，可在配置流转的 `guard_hook` 里调用 YAML 引擎，但状态回写仍以配置状态机为准。

## 3. 配置元模型（核心）

一份 `FlowDefinition` 由以下 **11 个段**组成。除 `meta` 外均可由后台表单编辑。

### 3.1 顶层段

| 段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `meta` | object | 是 | flow_id、名称、版本、状态、负责人 |
| `fields` | array | 是 | 表单字段（单一来源，派生工具参数 / 卡片 / 校验 / 抽取规则） |
| `intent` | object | 是 | 有序规则流水线、否定词、只读问法、判定器、用例表 |
| `attachments` | array | 否 | 附件类别与跨流程复用策略 |
| `workflow` | object | 是 | 状态显示名、流转组合、守卫 hook（状态 key 固定） |
| `session` | object | 是 | 多轮保持、切换、防死循环、版本锁定 |
| `entry_points` | array | 是 | 菜单 / 快捷按钮 / 可见角色 / 路径 |
| `card` | object | 是 | 确认卡字段与布局 |
| `prompts` | object | 否 | 话术 / SOP（Skill 包） |
| `hooks` | array | 否 | 引用的扩展点（仅白名单内名字） |
| `permissions` | object | 是 | 申请 / 审核角色与 scope |

### 3.2 `meta`

| 字段 | 类型 | 说明 |
|---|---|---|
| `flow_id` | string | 唯一标识，如 `driver_entry`，发布后不可改 |
| `name` / `description` | string | 后台展示名、用途说明 |
| `version` | int | 由发布动作递增，编辑态不递增 |
| `status` | enum | `draft` / `published` / `archived` |
| `owner` | string | 业务负责人 |
| `effective_at` | datetime | 生效时间（可选，配合灰度） |

### 3.3 `fields[]`（最重要，单一来源）

| 字段 | 类型 | 说明 |
|---|---|---|
| `key` | string | 字段键，须唯一；对应 `form_data` 的键 |
| `label` | string | 中文标签，用于表单、确认卡、追问、缺失提示 |
| `group` | string | 分组 key（配合 `groups[]`） |
| `type` | enum | `string` / `number` / `date` / `datetime` / `enum` / `phone` / `idcard` / `plate` / `file` / `ref` |
| `required` | bool | 提交时必填；用于 `missing` 判定与追问 |
| `options` | array | `enum` 类型的可选项 |
| `placeholder` | string | 输入提示，也会给模型作抽取参考 |
| `validation` | object | `regex` / `min` / `max` / `max_length` / `custom_hook` |
| `visible_when` | object | 联动显隐，如 `{field: "chemical_type", eq: "危化品"}` |
| `pii` | bool | 标记 PII；**框架强制在确认卡 / trace / 日志中打码，配置不能关闭** |
| `source` | enum | `user` / `attachment` / `system`，决定抽取来源 |
| **`extract`** | object | **新增段：确定性抽取规则**，见下表 |
| `order` | int | 表单与卡片展示顺序 |

**`fields[].extract`（v2 补齐，对应现有 `entry_schema.py` 的确定性逻辑）**

| 子字段 | 说明 | 现有对应 |
|---|---|---|
| `regex` | 从用户原话抽该字段的正则与捕获组 | `extract_by_rules()`（手机号 / 证件 / 车牌 / 时间） |
| `date_formats[]` | 日期 / 时间可接受的格式串 | `parse_dt()` 的多格式解析 |
| `normalize` | 归一化（全角数字、去空格、大小写、补年份） | `normalize_intent_text()` 思路的字段版 |
| `mask` | 打码规则（保留前 N 后 M） | `mask_value()`；`pii=true` 时由框架强制启用 |
| `reconcile` | 模型高置信值是否必须在原文独立出现，否则用规则值校正 / 剔除 | `reconcile_high_confidence()` |
| `from_attachment` | 是否由某类附件人工核对回填（不接 OCR 时仅占位） | 预留 |

> 这一段是 AI 辅助申请准确率和 PII 打码的核心。v1 只列了 `validate / missing_labels / llm_slots_schema` 作派生物，换流程后这批确定性逻辑会全部丢失、模型只能裸抽，属于评审中最实质的遗漏。

**派生物（运行时自动生成，不需配置）**：

- LLM 工具参数 JSON Schema（对应现有 `entry_schema.llm_slots_schema()`）
- 提交校验器（对应 `validate()` / `missing_labels()`）
- **确定性抽取器**（由上表 `extract` 编译，对应 `extract_by_rules()` / `parse_dt()`）
- 确认卡字段清单（对应 `FORM_FIELDS` / `FIELD_GROUPS`）
- 表单页渲染描述

### 3.4 `intent`（v2 重构）

v1 用散装 `triggers[] / negative_patterns[] / priority`，会丢掉现有 `ENTRY_INTENT_RULES` 的 **P0 → P1 → P2 短路顺序语义**（句首办理优先、只读次之、通用办理最后）。v2 改为**有序规则流水线**，业务同事在后台按行编辑，顺序即语义。

| 字段 | 类型 | 说明 |
|---|---|---|
| `rule_pipeline` | array | **有序**规则行：`{id, phase, when, patterns[], outcome, stop_on_match}`，`phase ∈ p0_head_request / p1_readonly / p2_general`；命中 P0 直接短路，不再被只读负例误伤 |
| `domain_words` | string[] | 场景词（用于补材料 / 附件语境，不单独触发办理） |
| `ambiguous_hint` | string | 弹通用候选卡时的提示文案 |
| `tie_breaker` | int | 多流程打分相同时的优先级 |
| **`classifier`** | object | **新增**：`{mode: rules\|hybrid, provider?, fallback: rules}`；默认 `rules`，本版不接外部 provider（D11） |
| **`test_cases`** | array | **新增**：意图用例表入库，形如 `{text, expect_flow_id, expect_action, expect_choice?}`；后台维护、dry-run 与发布前由后端跑（D8 / 矛盾 4） |

`rule_pipeline` 的每一行都带稳定 `id`，便于版本 diff 与用例失败定位；`patterns[]` 只接受**字面量或正则字符串**，不接受脚本 / 表达式（§7.3 同样约束）。

### 3.5 `attachments[]`

`key` / `label` / `required` / `max_count` / `accept` / `max_size_mb`，另加：

| 字段 | 说明 |
|---|---|
| `reuse_policy` | `per_application`（默认，延续现状：一个附件只能绑一张单，防串图）/ `per_flow_reusable` / `global_reusable` |

附件一律用**显式 ID + `application_id` 绑定**，禁止「自动取最新图片」。`flow_attachments` 带 `flow_id`，工具查询时按当前流程过滤；`global_reusable` 可由业务选择，但**归属校验与 PII 打码仍由框架强制**，配置不能关闭。默认 `per_application` 保证入园现有行为不变。

### 3.6 `workflow`（v2 收紧，D9）

**状态 key 是框架保留枚举，配置不能新增、不能改名 key**：`draft` / `pending` / `approved` / `rejected` / `cancelled`。现有入园的 `reopen` 是**动作**（`rejected → draft`），不是独立状态；`cancel` 动作落到 `cancelled`。阶段 0 需与 `entry_service.py` 的 `VALID_STATUSES` 逐项核对。

| 字段 | 说明 |
|---|---|
| `state_labels` | 5 个固定 key 的显示名覆盖，如 `pending: "待园区审核"` |
| `allowed_transitions[]` | 从框架允许的流转集合中**选子集**：`{from, to, action, actor_role?, guard_hook?}`；`from/to` 必须属于保留枚举 |
| `pass` | 审核通过后是否生成编号 / 二维码，及所用 hook；产出写入 `result JSONB` |

> **v3 硬约束（补评审后新发现的漏洞）**：`allowed_transitions` **必须包含至少一条 `pending → approved` 或 `pending → rejected` 的 `review` 流转**，且其 `actor_role` 由框架强制为 admin 级。这是框架级要求，**配置里不提供「跳过审批」开关**，缺失时 dry-run 直接拒绝发布（§6）。理由：v2 允许流转任选子集，理论上业务同事能配出「提交即完成、无人审批」的流程，把 D7「审批权限在人工手上」架空。

**为什么状态 key 固定**：现有 `submit` / `review` / `reopen` / `cancel` 里都是 `if row["status"] != "draft"` 这类硬编码，列表筛选、审核按钮、二维码条件、审计 action 也都依赖固定状态。放开自定义状态等于把内核也配置化，通用 API 与前端按钮都要动态生成，阶段 2 的风险不可控。这**不违背 D8**——流程差异本来就在字段、材料、审批链，不在状态 key。

### 3.7 `session`（v2 新增）

现有 `_derive_entry_action` 依赖 `ENTRY_SESSION_PREFIX`、`slots` 非空、`force`、`intentResolved`、`bind_session` TTL（`api/chat.py`）。v1 只写了 `ChatRequest` 加 `flow_id / flow_slots / force`，没写上下文怎么保持。

| 字段 | 说明 |
|---|---|
| `session_prefix` | 该流程的会话前缀（现状 `entry-` 的泛化） |
| `keep_flow_on_followup` | 同一会话内后续轮次保持 `flow_id`；空槽位不因此误判 |
| `switch_policy` | `confirm`（中途换流程先弹确认）/ `explicit_only`（只允许从显式入口切）/ `allow` |
| `choice_loop_guard` | 选择卡结果一次性标记（现状 `intentResolved` 的泛化），防「选完又弹卡」死循环 |
| `ttl_hours` | 会话绑定 / 槽位留存时长（现状入园通道 2h） |
| `version_pin` | 会话一旦开始，锁定当时的 `definition_version`，直到该会话结束或显式切换 |

**版本锁定的两层**（评审点出的关键遗漏，见 §5.4）：**会话级** `version_pin` + **单据级** `flow_applications.definition_version`。配置中途发布新版时，进行中的会话和已建草稿仍按旧版字段与规则运行，否则「填到一半字段变了」「驳回重提按新规则校验」都会出错。

### 3.8 `entry_points`（v2 新增）

现有 `Sidebar.tsx` 的三个入园菜单是硬编码，业务配了新流程却没有入口，D8 的零改动验收就落空。

`{type: menu|shortcut, key, label, path, visible_roles[], icon?, order}`；路径由通用页面接管（如 `/flows/{flow_id}/apply`、`/flows/{flow_id}/my`、`/flows/{flow_id}/review`）。前端启动时拉 `/api/flows/entry-points` 渲染菜单与快捷按钮，**不硬编码任何 flow_id**。显式快捷入口（如「AI 入园申请」）同时是路由层故障时的兜底，必须保留。

### 3.9 `card` / `prompts` / `hooks` / `permissions`

- `card`：`title`、`field_keys[]`、`masked_fields`（由 `pii` 自动派生）、`prefill_target`、`custom_component`（可选，须在白名单内）
- `prompts`：`system_prompt`、`ask_hints[]`、`examples[]`、只读规则文案引用
- `hooks[]`：`{name, phase, params}`，`phase ∈ before_parse / after_parse / before_validate / before_submit / on_review`；`params` 值域由注册时 `params_schema` 校验（§7.1）
- `permissions`：`applicant_roles[]`、`reviewer_roles[]`、`scope`（对应现有 `entry_public`）；取值受 §7.4 角色白名单约束

## 4. 数据模型（D1 = 1A，**新增流程**零 DDL）

| 表 | 关键列 | 说明 |
|---|---|---|
| `flow_definitions` | `flow_id PK`, `published_version`, `draft JSONB`, `draft_revision`, `status`, `updated_by`, `updated_at` | 每流程一行，指向当前发布版 |
| `flow_definition_versions` | `(flow_id, version) PK`, `definition JSONB`, `diff JSONB`, `published_by`, `published_at`, `note` | 每次发布的**完整快照**，可回滚 / 追溯 |
| `flow_applications` | `id PK`, `flow_id`, `definition_version`, `status`, `applicant_username`, `source`, `assisted_by_ai`, `form_data JSONB`, `attachments JSONB`, `review_*`, **`result JSONB`**, 时间戳 | 所有流程共用一张表 |
| `flow_attachments` | `id PK`, `flow_id`, `owner_username`, `application_id`, `kind`, `filename`, `storage_path`, `created_at` | 沿用现有防串图绑定 |
| `flow_audit_log` | `id`, `flow_id`, `application_id`, `action`, `actor`, `detail JSONB`, `created_at` | 申请流转 + 配置变更留痕 |

**关键约束**

1. `flow_applications.definition_version` **必填**。配置改版后，老单据仍按当时字段与规则复现；否则驳回重提、审计追溯会错乱。
2. 字段校验全部在应用层按对应发布版配置执行；JSONB 不建字段级约束。
3. 索引：`(flow_id, status)`、`(applicant_username, created_at DESC)`；可选 `form_data` GIN。报表吃力时再出宽表 / 物化视图，不因此回退到「每流程建表」。
4. **新增流程零 DDL**：新增流程只写配置数据，不执行任何迁移。注意 §9.1 的兼容视图属于**一次性老数据迁移 DDL**，与新增流程无关，v1「零 DDL」的绝对措辞已收紧。
5. `pass_no` / 二维码 payload 是入园专属，v2 从通用表列移到 **`result JSONB`**（审核产出），不混进用户填写的 `form_data`。
6. 框架强制项（PII 打码、权限、审计、附件绑定、确认前零写库、**人工审批流转**）不写入配置开关。

### 4.1 草稿并发（v2 补齐）

`flow_definitions.draft` 是单行 JSONB，多人同时编辑会相互覆盖。保存草稿走**乐观锁**：PUT 带 `expect_draft_revision`，不一致返回 409 并附当前草稿与差异，由后提交者决定合并或二次确认覆盖；同时记录 `updated_by / updated_at`。发布时另带期望 `published_version` 防并发切换（两层锁互不替代）。

## 5. 运行时设计

### 5.1 通用四件套（替代 `entry_tools.py`）

| 工具 | 作用 | 参数来源 |
|---|---|---|
| `parse_flow_materials` | 抽取本轮新字段、与已有槽位合并，禁止编造；**先跑 `fields[].extract` 确定性抽取，再交给模型补缺** | `fields[]` 动态生成 JSON Schema + `extract` |
| `get_my_attachments` | 查本人已上传、按 `flow_id` 与 `reuse_policy` 过滤、且未被占用的附件 | `attachments[]` |
| `check_flow_rules` | **确定性校验器**：调用配置派生 `validate()` 查出 `missing` 与字段错误，`push_flow_confirm_card` 前置调用 | `fields[].validation` + `required` |
| `push_flow_confirm_card` | 信息齐备才生成 payload；缺字段返回 `missing` | `card` + `fields[]` |

> **评审更正**：现有 `tool_check_entry_rules` 实际调 `schema.validate()`，根本不查知识库。v1 写成「查规则与文案」是错的。**只读问答（入园规定、要带什么材料）另走 RAG 主链**，并按 `permissions.scope` 隔离知识库（§5.5），不占用四件套。

四个工具**全部只读，无 submit**。工具清单由 `flow_id` 从注册表裁剪，普通知识库问答看不到任何流程工具。

### 5.2 意图路由（后端权威，D10）

- **判定只发生在后端**：按所有已发布配置的 `intent.rule_pipeline` 编译成有序规则链，逐条短路，输出 `flow_id` + 动作；低置信 / 歧义 / 多流程撞车时，通过 **SSE `intent_choice` 事件**下发候选清单（`{flow_id, name, action, hint}`），前端只渲染通用候选卡
- 用户选择结果回传 `{flow_id, force: true, intent_resolved: true}`；`force` 只放宽歧义，后端仍做权限与最终判定
- **前端 `utils/entryIntent.ts` 删除**，`/api/flows/config` 只下发渲染必需的元数据（显示名、卡片字段、菜单、PII 布尔标记），**不下发判定规则、否定词、用例表或任何 PII 值**
- `intent.classifier`：默认 `rules`；`hybrid` 与本版不接的 provider 见 §10.1
- **用例回归迁移**：`intent.test_cases[]` 存 DB，由 dry-run / 发布接口在后端跑；仓库里 `shared/entry_intent_cases.json` 与「双端各写一份规则、靠用例表锁死漂移」的做法**整体退役**。前端只保留选择卡 / 确认卡的组件交互测试
- 发布前跑意图冲突检测 + 本流程用例回归；显式快捷按钮（`entry_points` 里的 `shortcut`）作为路由层故障兜底必须保留

### 5.3 提交链路与 SSE

- `ChatRequest`：`flow_id?` / `flow_slots?` / `force?` / `intent_resolved?` 取代 `entry_slots` / `entry_force`
- SSE 事件：`intent_choice`（新增，后端下发候选）、`flow_payload`（取代 `entry_payload`）、`done`
- 通用确认卡渲染器按 `card` + `fields[]` 渲染；动态明细行 / 级联字段走**已注册自定义组件插槽**
- 用户确认 → 通用 `/api/flows/{flow_id}/applications/{id}/submit` → 状态机 → 有权限的审核人审批 → `on_review` hook 把编号 / 二维码写入 `result JSONB`
- **不存在「提交即通过」路径**：`submit` 只能到 `pending`，`pending` 只能由 `review` 流转离开（§3.6）

### 5.4 会话与版本锁定（v2 新增）

| 场景 | 策略 |
|---|---|
| 多轮补材料 | 会话前缀 + `keep_flow_on_followup` 保持 `flow_id`；槽位随每轮请求回传，后端按 `session.version_pin` 指定的版本解释 |
| 中途换流程 | 按 `switch_policy` 处理；`confirm` 时先弹确认，旧槽位隔离不复用（防止把入园的身份证带进入库单） |
| 选择卡结果 | `choice_loop_guard` 一次性标记，防「选完又弹卡」 |
| 配置中途发布 | 进行中会话按 `session.version_pin` 锁旧版；**新会话按 D13 灰度命中结果决定版本**；已建草稿按单据 `definition_version` 锁旧版 |
| 老单据驳回重提 | 强制按单据 `definition_version` 校验与渲染，不套用新版字段 |

### 5.5 附件复用与知识库隔离（v2 新增）

- 附件库所有流程共用一张表，但 `get_my_attachments` 必须同时按 `flow_id` 与 `reuse_policy` 过滤；`per_application` 为默认，保持现有防串图语义
- 同一张行驶证能否同时用于入园与入库，由业务在该流程配置里选 `reuse_policy`，**不写死在内核**
- 多流程知识库按 `permissions.scope` 隔离：只读问答只检索该流程 scope 下的文档，不允许一个流程的配置把另一个流程的知识库挂进来；scope 由框架校验归属

## 6. 配置治理与发布（D2 = 2A）

**配置自身状态机**：`draft → validating → published → archived`；运行时**只读 `published` 版**，草稿写错不影响线上。

**发布链**

1. 保存草稿（不递增 `version`，递增 `draft_revision`，带期望 revision 防覆盖，见 §4.1）
2. **dry-run 校验**（`POST /validate`），至少检查：
   - 元模型自校验（类型、必填、key 唯一、枚举合法、`workflow` 状态 key 属于保留枚举）
   - 引用一致性（`card.field_keys`、`allowed_transitions.guard_hook`、附件 key 是否都存在）
   - hook 名在白名单内、**phase 匹配、`params` 符合注册时的 `params_schema` 值域**（§7.1）
   - `rule_pipeline` 的 phase 顺序合法、正则可编译、与其他已发布流程的意图词冲突、只读词是否被办理词覆盖
   - **`intent.test_cases[]` 在当前 `classifier` 下全绿**（用例在 DB，后端跑）
   - `entry_points` 路径 / 角色合法、`permissions` 角色在白名单内（§7.4）
   - `fields[].extract` 正则可编译、日期格式可解析、PII 字段的 `mask` 未被关闭
   - **审批链完整性（v3 补）**：`allowed_transitions` 必须含至少一条 `pending → approved` 或 `pending → rejected` 的 `review` 流转，且其 `actor_role` 由框架强制为 admin 级；缺失、写成低权限角色、或存在任何 `draft → approved` 直连流转，**一律拒绝发布**
3. **预览**：渲染模拟确认卡 + 模拟工具 schema + 模拟一段对话 + 模拟菜单入口
4. **发布**：原子切换 `published_version`（带期望版本号防并发），写完整快照 + diff + 操作审计；**草稿最后提交者与发布者必须为不同账号**（D12）；发布成功后**异步导出 Git 只读快照**（D14）
5. **灰度**（D13）：新流程首次发布可直接全量；**配置改版必须按用户组灰度**，观察期结束再全量，异常一键回滚
6. **回滚**：把 `published_version` 切回上一版本，无需改代码 / 回滚数据；已在途会话与单据仍按各自锁定的版本运行

**缓存**：进程内注册表按版本号缓存，发布时失效热加载；可参考 `workflows/loader.py` 的 `FlowRegistry` 线程安全单例 + `load(force=True)`，以及「单个定义加载失败只跳过该文件」的容错思路 —— 配置文件加载失败时**保留上一版可用配置**并告警，绝不让全站路由失效。

### 6.1 配置后台自身权限（v2 补齐）

现有 role + scope 体系没有「配置管理员」，且 `transitions[].actor_role` 由配置决定，存在业务同事把自己配成审批人、自审自批的风险。v2 强制：

| 项 | 规则 |
|---|---|
| 角色 | 新增 `config_editor`（编辑草稿）与 `config_publisher`（发布 / 回滚）；**「谁能发布配置」由框架角色决定，配置里不提供开关** |
| 编辑 / 发布分离 | **强制双人（D12）**：草稿最后提交者与发布者必须为不同账号，发布者持 `config_publisher`；细则见 §6.2 |
| 审批动作 | `review` 类动作**强制高权限角色**，配置不可覆盖（§7.4） |
| 自审自批 | 框架硬校验：同一账号不能既是该单申请人又是审核人；与配置无关 |
| 留痕 | 草稿保存、dry-run、发布、回滚、用例回归结果全部写 `flow_audit_log` |

### 6.2 五项治理决策定稿（v3，D12–D16）

| 编号 | 决策 | 推荐值（本文采纳） |
|---|---|---|
| D12 | 发布是否双人审批 | **强制双人**。发布接口校验 `draft.updated_by != publisher`；团队只有一名业务编辑时，由 IT 在系统级白名单里指定第二名发布者（不由业务配置修改），仍走双人。发布动作写 `flow_audit_log`，记录提交者 / 发布者 / 版本号 |
| D13 | 灰度维度 | **按用户组 / 账号白名单**，不按 flow_id（新流程首次发布本就没有存量流量，按 flow_id 灰度等于全量）。新流程首次发布可直接全量；**配置改版必须灰度**：先放试点组，观察期 ≥ 1 个工作日且用例回归与错误率正常，再全量。版本解析顺序为「会话 / 单据锁定版本 > 灰度命中版本 > 当前 published」，与 §5.4 一致 |
| D14 | 是否导出 Git 备份 | **导出，但只做异步只读灾备**。每次发布成功后把完整配置快照 + diff + 发布人导出到独立 Git 仓库；DB 是**唯一运行时权威**，Git 不参与发布链、不反向同步、不允许从 Git 改配置；导出失败只告警不阻断发布；导出前过滤 PII 值与内部密钥字段，key 一律不入库 |
| D15 | 兼容视图保留周期 | **90 天且至少跨一次月结 / 季度结**（取更长者）。期间视图只读、继续双跑校验；到期删除需单独审批并确认备份可用，删除动作写审计。见 §9.1 第 9 步 |
| D16 | hook 下线的版本兼容 | **三态生命周期**：`active`（可新引用）→ `deprecated`（禁止新配置 / 新版发布引用，存量已发布配置继续运行）→ `retired`（允许删代码）。进入 `retired` 必须同时满足：① 全量扫描 `flow_definition_versions`，所有引用它的已发布版本均已 `archived`；② 关联单据超过保留期或已转只读归档；③ dry-run 扫描通过 + 变更审计。历史单据**只读查看不执行 hook**；若 `reopen` 依赖已 retired 的 hook，则拒绝重提并提示人工处理。代码删除后版本快照仍保留供审计 |

> 这五项都属于**治理策略**，不改变架构分层，也不影响 D8「新增流程零改动」验收指标。

## 7. 扩展点白名单（D3 = 3A）

### 7.1 注册方式

开发者在代码中注册 `register_hook(name, fn, params_schema, phase, description)`；配置里只能写 `{name, phase, params}`。发布时校验名字存在、phase 匹配、**`params` 符合 `params_schema` 的类型与值域**，白名单外一律拒绝发布。

v2 补齐参数值域：`params_schema` 是 JSON Schema + 显式上下界（例如 `validate_weight_limit.max` 允许 `0 < max ≤ 1000`），防止把上限配成 `99999` 这类合法类型但业务荒谬的值。`params` 只允许**字面量**，不允许引用运行时变量、表达式或脚本。

### 7.2 首批 hook（均来自入园现有逻辑）

| name | phase | 作用 | 现有对应 |
|---|---|---|---|
| `reconcile_high_confidence` | after_parse | 模型高置信值须在原文独立出现，否则校正 / 剔除 | `entry_schema.reconcile_high_confidence` |
| `validate_time_window` | before_validate | 入园 / 出园时间先后与合理性 | `entry_schema.parse_dt` + 时间规则 |
| `validate_weight_limit` | before_validate | 重量上限 | `MAX_WEIGHT_TON = 100.0` |
| `validate_attachment_binding` | before_submit | 附件归属与 `application_id` 绑定 | `entry_service._check_and_bind_attachments` |
| `generate_pass_no_and_qr` | on_review | 审核通过生成编号 + 二维码，写入 `result JSONB` | `new_pass_no` / `make_qr_data_uri` |
| `erp_read_stock`（预留） | before_validate | 查 ERP 库存 | 阶段 4 + MCP 适配 |

### 7.3 安全底线

- **禁止**配置中出现表达式、脚本、模板代码，后端绝不 `eval` / `exec` 配置内容（含 `rule_pipeline.patterns[]` 与 `hooks[].params`）
- 正则必须有长度上限与编译期校验，防 ReDoS；不接受的正则直接拒绝发布
- hook 只能返回结构化结果，**不能直接写库**
- hook 下线时：存在引用它的已发布配置则拒绝下线；老单据按 `definition_version` 仍可复现；**三态生命周期与 retired 条件见 §6.2（D16）**
- 新增 hook 属于开发者工作，业务同事不能自行新增

### 7.4 审批动作与角色白名单（v2 新增，v3 收紧）

- `permissions.applicant_roles` / `reviewer_roles` / `allowed_transitions[].actor_role` 的取值只能来自**框架角色白名单**（现有 `admin` / `driver` / `finance_user` 等，不含 `config_*`）
- `action ∈ {review, approve, reject}` 的流转由框架**强制 `admin` 级角色**，配置写别的角色直接拒绝发布
- **任何已发布配置必须含 `review` 流转**（§3.6 / §6 dry-run）；缺失即拒绝发布，**不提供「跳过审批」开关**
- 配置管理员角色不能出现在申请人 / 审核人列表里（避免后台配单自审自批）
- PII 脱敏、附件归属、审计、确认前零写库仍是框架硬约束，配置里**连开关都不给**

### 10.1 意图判定器的演进位（本版不接）

`intent.classifier` 预留 `hybrid` 模式与可插拔 provider。候选形态之一是「封闭选择题」类判定模型（例如 Jev 这类只对给定候选集打分、返回 choice + 置信度的模型；厂商称比通用 LLM 更快更便宜，**均为厂商口径，需实测**）。它与配置化天然契合：候选集就是已发布流程列表，新增流程自动多一个选项，不用改 prompt、不用训练。

**但本版明确不接（D11）**，若将来评估需先解决三条硬约束：

1. **PII 合规**：司机原话含身份证号、手机号，境外 API 外发等于给刚加固完的 PII 体系开新口子。要接必须先脱敏 / 只发句式特征，或改用本地轻量分类器。
2. **已知弱项**：该类模型在「否定」「日期」上表现偏弱，而本项目的难点恰恰是疑问句与「明天上午八点到门口」。必须保留规则层处理否定与日期，并用 `intent.test_cases[]` 实测通过率。
3. **不能当安全边界**：判定决定「挂不挂办理工具集」，存在提示注入空间。后端权威 + 用户确认 + 权限校验仍是最终闸门；provider 只能是建议者，且必须能**一键降级回纯规则**、可用例回归。

推荐演进姿态：**三层漏斗** —— 规则前置（明确句 / 疑问句 / 显式按钮，零成本可回归）→ 规则低置信才调判定模型 → 模型也低置信就出候选卡让用户点。不做「每轮都问一次模型」。

## 11. 总验收标准

1. 新增第二个流程：**开发者改动文件数 = 0**，仅新增配置数据（含字段与抽取规则、意图用例、菜单入口、附件策略）
2. 阶段 0 / 1 完成后，既有 pytest / vitest / E2E 回归全绿（按 §8.4 重写后的基线），入园体验不变
3. **确认前零写库**（AI 只读），附件显式 ID 绑定、PII 打码、权限与审计由框架强制，配置不提供关闭开关
4. 配置草稿写错不影响线上；草稿并发不覆盖；发布失败可一键回滚；所有变更有 diff 与操作人
5. 老单据按 `definition_version` 可复现当时的字段与规则；进行中会话按 `version_pin` 不被中途发布打断
6. 意图路由可回归：用例表在 DB、后台可维护、发布前由后端在当前 `classifier` 下自动跑
7. 判定完全在后端，前端不持有任何意图规则；`entry_points` 由配置驱动，新增流程自动出现菜单与快捷入口
8. **任何已发布流程都必须含至少一条人工 `review` 流转**（`pending → approved/rejected`，actor 为 admin 级）；不存在「提交即完成、无人审批」的流程，也不存在 `draft → approved` 直连
9. D12–D16 全部可验证：双人发布、改版按用户组灰度、Git 只读备份、兼容视图 90 天 + 跨结、hook 三态下线

## 附录 A · 新流程接入 SOP（业务同事版）

> 面向配置者（`config_editor`）与发布者（`config_publisher`），不要求读代码。开发者只需在需要**新的确定性校验**或**新的出证逻辑**时注册 hook。

### A.1 前置条件

| 项 | 要求 |
|---|---|
| 编辑权限 | `config_editor`（或 `admin`） |
| 发布权限 | `config_publisher`（或 `admin`）；**发布者必须与草稿最后提交者不同账号** |
| 审批人 | 该流程的 `review` 流转 actor 必须是 admin 级角色 |
| 申请人角色 | 在 `permissions.applicant_roles` 里显式声明（如 `driver`） |

### A.2 五步接入

1. **新建流程**：`/flows/config` → 「新建流程」，填 `flow_id`（小写字母开头，只含小写/数字/下划线，2–64 位）、名称、意图关键词。
2. **取模板**：后台调用 `GET /api/flows/template`，得到一份最小可发布配置（3 个基础字段、完整 submit/review/reopen/cancel 流转、动态菜单、确认卡）。
3. **改配置**：按业务改 `fields`（字段/分组/必填/抽取）、`attachments`（附件类型/必填/大小）、`workflow`（状态标签/允许流转）、`prompts`（话术）、`entry_points`（菜单/快捷入口/可见角色）。
4. **跑 dry-run**：`POST /api/flows/{flow_id}/validate`，八项全绿再存草稿；有错按 A.4 对照修。
5. **双人发布**：存草稿（`PUT /draft`，带 `expect_draft_revision` 乐观锁）→ 换发布账号 `POST /publish`，带 `expect_version`。首次发布可全量，后续自动进灰度。

发布后：`/flows/entry-points` 自动下发新菜单，前端无需改代码；申请人可对话办理，admin 在 `/flows/{flow_id}/review` 审核。

### A.3 字段配置速查

| 配置 | 可选值 / 写法 | 说明 |
|---|---|---|
| `type` | `string` / `number` / `date` / `datetime` / `enum` / `phone` / `idcard` / `plate` / `file` / `ref` | `enum` 必须给 `options`；`phone`/`idcard`/`plate` 有内置格式校验与打码 |
| `required` | `true` / `false` | 提交时强校验；确认卡会标出缺失项 |
| `group` | 分组 key（顶层 `groups[]` 定义标签） | 决定表单与确认卡分组，建议不超过 4 组 |
| `extract` | `{builtin, regex, date_formats, mask, reconcile, from_attachment}` | 内置抽取器：`phone` / `idcard` / `plate` / `weight` / `datetime_range` / `name` / `company`；`regex` 只接受安全正则 |
| `validation` | `min` / `max` / `max_length` / `regex` | 确定性校验，不写表达式；时间先后由 `validate_time_window` hook 负责 |
| `label` / `placeholder` / `help` | 文案 | 直接进表单与确认卡 |
| `visible_when` | `{field, eq}` 或 `{field, in}` | 条件显示；不支持级联计算 |

> 顶层 `groups[]` 是 11 段之外的可选展示段（只影响表单与确认卡的分组标题），不参与运行时校验。

附件单独配在 `attachments[]`：`key` / `label` / `required` / `max_count` / `accept` / `max_size_mb` / `reuse_policy`。`reuse_policy` 三选一：`per_application`（默认，禁止串图）/ `per_flow_reusable` / `global_reusable`。

### A.4 dry-run 八项常见报错

| 项 | 典型报错 | 修法 |
|---|---|---|
| 1 元模型自校验 | 「缺少配置段 workflow」「字段 key 非法」「type 不合法」 | 补齐 11 段；key 用小写+下划线；type 从白名单选 |
| 2 引用一致性 | 「card.field_keys 引用了不存在的字段」「extract.targets 引用了不存在的字段」「extract.from_attachment 引用了不存在的附件」「guard_hook / pass.hook 未注册」 | 检查确认卡字段、抽取目标、来源附件类型、流转守卫与通行证 hook |
| 3 扩展点白名单 | 「未注册的扩展点 xxx」「phase 不合法」「params 含非法字符」 | 只能选 `/api/flows/hooks` 返回的 hook；phase 必须与注册时一致；params 只能是字面量 |
| 4 意图流水线 | 「规则正则编译失败」「when 不合法」「与其它流程关键词冲突」 | 缩短/简化正则；`when` 用框架支持的类型；换更具体的领域词 |
| 5 用例回归 | 「N 条意图用例未通过」 | 看 `test_cases.failed` 的 expect/got，调规则或改用例 |
| 6 入口与角色 | 「entry_point 可见角色不在白名单」「applicant_roles 含配置角色」 | 角色只能从框架白名单选；配置角色不能出现在业务权限里 |
| 7 抽取与 PII | 「extract 正则非法」「sensitive 字段未打码」 | 用内置抽取器或安全正则；身份证/手机号标 `sensitive` |
| 8 审批链完整性 | 「缺少 pending→approved/rejected 的 review 流转」「review actor 必须是 admin 级」「禁止 draft→approved 直连」 | 补 review 流转，actor 改 `admin`，删直连 |

### A.5 上线验证清单

- [ ] dry-run 八项全绿，且用例覆盖「办理 / 只读 / 两可 / 无关」四类说法。
- [ ] 发布后 `/flows/entry-points` 能看到新菜单，且只对配置的角色可见。
- [ ] 申请人走一遍：对话办理 → 上传附件 → 确认卡 → 本人提交。
- [ ] admin 审核通过：能生成编号/二维码（若 `workflow.pass.enabled=true`）。
- [ ] 驳回后申请人能 reopen 修改重提。
- [ ] 重复提交返回 409，不会产生两张 pending 单。
- [ ] 附件不能跨申请单复用（`per_application`），串图返回 409。
- [ ] 配置审计里能看到 create / save_draft / publish 记录。

### A.6 不要做的事

1. 不要在 `prompts` 里写「直接帮用户提交」「跳过审核」——写操作不在模型能力范围内，写了也不会生效，只会让话术与系统行为不一致。
2. 不要为了省事把 `review` 的 actor 配成 `driver` 或配置角色——dry-run 会直接拒绝。
3. 不要在 `extract` 里写复杂正则或表达式——只允许安全正则与内置抽取器。
4. 不要绕过双人发布找同一个账号「先存后发」——会返回 409。
5. 不要在流程上线后直接改已发布版本——所有修改都走草稿 + 发布，在途单据按旧版本快照执行。
