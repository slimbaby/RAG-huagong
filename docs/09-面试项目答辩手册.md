## 一、项目概览

**Q1. 介绍下这个项目。**
A：这是我们给化工园区做的知识库问答平台。园区里安全规程、应急预案、操作手册这些文档又厚又散，同事查个流程经常找不到入口，所以我们做了个能溯源到原文页码的问答系统，答案里每句话都能点回原文。

**Q2. 具体解决谁的什么问题？**
A：主要给园区和下属企业的安全、生产、行政人员用，高频场景三类：安全规程查询、事故应急处置、应急物资和流程问答。核心诉求不只是"答得上"，而是"答案有依据、能拿去执行"。

**Q3. 为什么不让大模型直接答？**
A：三个原因。一是私域，园区内部规程模型没见过；二是时效，文件每年修订，权重更新不了；三是可追溯，安全场景不能接受"大概是这样"。RAG 正好补这三块。

**Q4. 知识库规模多大？流量多少？**
A：架构按百万级切片留了余量，但我不背死数字——交付时才几十份文档，之后园区和文档陆续接入一直在涨，报固定值当场就不准。被问就讲量级和增长方式：按文档增量入库，更新时按 `doc_id` 删旧切片再写新的，不用全库重建，评测基线跟着增量更新。流量单园区日均不到 1000 次、峰值并发个位数，瓶颈在单次检索加重排的延迟，不在 QPS；提前留容量就是为了后面涨上来不用动架构。

**Q5. 效果怎么衡量？**
A：离线看评测集，线上看赞踩和转人工率。评测集不是一次攒齐的：驻场高频场景做种子、业务方确认标注，上线后 badcase 按归因回流成新用例，所以一直在涨；被追问就说"百条量级，按事实型、比较型、边界拒答分层，每次迭代补一批"，业界私有知识库也是百条起步、发布前两三百条，覆盖度比堆量重要。看 RAGAS 三指标加六维 judge 的趋势，综合分提到越过 7 分门禁线；门禁拦回归，线上 badcase 补进评测集就是闭环。

**Q6. 你在项目里负责什么？**
A：7 年开发、前端 5 年，主导过保险中后台和园区可视化大屏。化工园区驻场两年，客户最高频的是查规程、查事故、应急问答，页面解决不了，我 2025 年 5 月起主导 RAG 平台设计落地：检索链路、评测体系、问答前端都我推进，2025 年底核心链路完成，2026 年 5 月交付上线交团队迭代，目前多个园区在用。前端经验让我能一个人端到端推到上线。

## 二、整体链路

**Q7. 一次提问从进来到出答案，经过哪些环节？**
A：先做意图识别和改写，知识库类走混合检索——向量和 BM25 各召回 20 条，RRF 融合去重后截到 10 条，再用交叉编码器重排取 top5 进 prompt；然后做置信度门禁，分数太低降级成通用回答、结果为空就回环补检索一次；够了才交给大模型生成带引用的答案。

**Q8. 七个节点分别做什么？**
A：一 `query_optimize` 改写并判意图，比较类拆子查询；二 `vectorize` 向量化；三 `retrieval` 两路各 20 条、RRF 融合去重截 10；四 `reranker` 精排取 top5；五 `check_confidence` 对阈值出置信标记；六 `evidence_judge` 只看空不空，空就补检索一轮；七 `generate` 出带引用答案，低置信转通用模式。前四个找对材料，后三个判够不够、怎么答。

**Q9. 节点之间怎么连？**
A：入口是改写，改写后按意图分三路：知识库类进向量化，通用闲聊直接进生成，业务查询也进生成、但走生成节点内部的 Function Calling 工具循环（不进检索，避免把实时业务数据当文档召回）。知识库这一路顺序执行到证据裁判，裁判再分叉——需要补证据就回到向量化，否则进生成。所以图上有两条条件边，一条在改写后，一条在裁判后。

**Q10. 为什么拆成七个节点，一个大 prompt 不行吗？**
A：三个东西会失去。可定位——出错时分不清是改写偏了、检索没命中还是模型瞎编；可短路——置信度不够想中途退出，大 prompt 没有中间态可以退；可替换——换 reranker 就得动整条 prompt。而且这七个节点不是一开始就设计好的，是踩了坑以后一步步拆出来的。

**Q11. 拆这么细，延迟不是更高吗？**
A：只有改写和生成调 LLM，改写用的还是便宜的快模型；向量化是 embedding，检索两路并行，重排是本地交叉编码器，置信度和裁判是纯规则。所以比单次大调用多出来的只是几段百毫秒级的检索，不是多几次大模型调用。

**Q12. 状态在节点之间怎么传？**
A：用 `StateGraph` 绑 TypedDict 做状态，节点只返回自己的增量，框架负责合并。早期绑的是裸 dict，节点写错键名不报错、调试很痛苦，后来改成 TypedDict 并接上 mypy/IDE 静态检查，键名或字段类型写错在跑之前就报出来——这是一次真实返工。注意 TypedDict 运行时还是普通 dict、不做校验，挡错靠的是静态检查那一层，不是框架在运行时拒绝。

**Q13. 补检索会不会死循环？**
A：不会，最多补一次。裁判第一次判定需要补证据时把迭代计数置 1，第二轮进来看到计数大于 0 就直接放行。没有可配的最大轮数，因为空两次就说明知识库确实没有，再补是浪费。

## 三、检索与重排

**Q14. 为什么有了向量检索还要 BM25？**
A：向量对低频专有名词不敏感。园区里大量是标准编号、化学品名、设备位号、缩写——GB 30871-2022、HAZOP、SIS、动火作业票，这些在 embedding 空间里容易跟同领域其他词挤在一起，BM25 的精确词项匹配反而一击即中。反过来 BM25 怕同义改写，"实习期请假"和"试用期休假"它匹配不上，那正是向量的强项。

**Q15. RRF 是怎么算的？**
A：对每一路结果，用 `1 / (k + 名次)` 算分，同一篇文档在所有路的分相加，按总分排。名次从 1 开始，k 取 60。所以一篇文档如果两路都在前面，分数会明显高于只在一路靠前的。

**Q16. k 为什么取 60？**
A：k 是平滑项。k 太小，第 1 名和后面差一倍，某一路的偶然 top1 就能决定结果；k 太大，各名次趋于平均，融合退化成"谁被召回得多谁赢"。60 是 RRF 原论文实验里用的经验值，不是数学上的最优解；我们也在自己的评测集上扫过 10、30、60、100，60 的引用准确率最稳就沿用了。k 本质是在调"名次靠前该占多大优势"，候选集规模变了就值得重扫一遍。

**Q17. 为什么不直接把两路分数加权？**
A：量纲和分布都不可比。余弦理论上是 −1 到 1，BM25 是随词频、文档长度、IDF 变的实数，换个 query 分布就漂移。直接加权得先归一化，可最大值归一化会被离群值拉偏、min-max 又依赖这批候选，等于换了个不可比问题。名次天然可比，RRF 只看名次不看分数，这是它最大的好处。

**Q18. 重排用的是什么？和向量检索有什么本质区别？**
A：用的是 `bge-reranker-base` 交叉编码器。区别在编码方式：向量检索是 bi-encoder，问题和文档各自独立编码，编码时互相看不见，最后只比距离；交叉编码器把问题和文档拼在一起送进模型，做逐 token 的交叉注意力，能看出"相关但答非所问"。

**Q19. 那为什么不直接全库用交叉编码器？**
A：成本不可行。百万切片每条都要过一次模型，全库就是百万次前向。所以是两段式：两路各召回 20 条、RRF 融合去重后把候选从百万压到 10 条以内，负责别漏；精排在这 10 条里排准、最终取 top5 进 prompt。重排是有明确上限的，5 条也是按上下文预算和延迟倒推出来的。

**Q20. 置信度阈值 0.10 是不是太低了？**
A：实测调的。交叉编码器对表格行、短文本打分天然偏低，卡高了大面积误杀——库里有内容却判低置信。所以放宽门禁加两个例外：问题带指代词、或实体词在结果里逐字命中，就直接放行按知识库答。这里不硬拒答，剩下真判低置信的才转通用模式：不注入检索上下文、不带引用，但照常回答。证据裁判只管一件事，空集就补检索一轮，补完还空也转通用。唯一明确拒绝的是权限不足，会提示去找谁申请。

**Q21. reranker 挂了会怎样？**
A：只跳过精排，不报错。置信度检查会看有没有重排分数，没有就回退用向量分，阈值换成 0.40。整条链路继续跑，只是排序质量下降。

**Q22. 配置里的 0.6 和 0.4 是什么？**
A：那是加权融合模式的向量和 BM25 权重。当前用的是 RRF 名次融合，不走分数加权。留这个配置是为了能一键切回加权模式做对比实验。

**Q23. 切片多大？怎么切的？**
A：本地是 512 字符、重叠 50，按标题层级优先切，标题不行再按段落、句子边界退。走 RAGFlow 时用它自己的 token 配置，注意两边口径不同——字符和 token 不可直接比较，评测对比时 chunk 数会明显不一样。

**Q24. 表格怎么处理？**
A：表格转成 markdown 当正文，同时额外生成一份自然语言描述塞进 BM25——因为 markdown 的竖线和空格会干扰分词，纯符号匹配效果差。

**Q25. 权限怎么控制的？**
A：每篇文档绑 scope，检索时按用户可见范围过滤。还额外做了一次越权探测：如果答案其实存在、只是被权限挡住，会明确告诉用户去找谁申请，而不是假装不知道。

## 四、路由与工具调用

**Q26. 三路意图怎么判？**
A：在改写节点里让快模型做分类，输出知识库查询、通用闲聊、业务查询之一，条件边按这个值分叉。

**Q27. 业务查询为什么不走检索？工具又是怎么调的？**
A：业务查询不进知识库检索——那是查文档，答不了"我这个单子现在到哪一步了"这类实时状态；它进生成节点里的 Function Calling 工具循环，按工具注册表调后台业务接口，注册表已经接进主链，不是预留位。设计上权限边界守得比较紧：问答侧只调白名单里的只读接口，参数带用户 scope，写操作一律不开放——避免问答系统变成万能入口，带来越权和数据一致性问题。

**Q28. Function Calling 的多轮循环在哪实现的？**
A：在生成节点内部，通过 `_chat_with_tools` 函数，`max_rounds=2`，即最多 3 次模型调用（2 轮工具循环 + 1 次最终回答），但模型一旦不再返回 `tool_calls` 就提前结束。流程是：模型返回工具调用 → 按工具注册表分发执行（async 用 `inspect.iscoroutinefunction` 判断后 await、同步直接调）→ 结果以 `tool` 角色拼回消息 → 再让模型继续；轮次用尽则强制无工具 `chat` 一次拿最终文本。工具执行出错或未知工具，会以 `{"error": ...}` 回喂给模型让它自己纠错，而不是崩溃。没拆成图节点，是因为工具调用需要拿模型原始的 `tool_calls` 结构，在边上来回序列化反而更绕。

**Q29. 为什么有两张图？**
A：一张是问答主链，一张是给 ERP、CRM 集成准备的扩展图，多一个显式的工具调用节点。当前入口是主链，业务查询在生成节点内部走工具循环；扩展图是把这段循环从节点里提出来、变成图上可观测的独立节点，用于需要审计和人工中断的集成场景，拓扑和主链一致，属于演进版本而不是空预留。

## 五、记忆

**Q30. 三层记忆分别是什么？**
A：三层都落地了。短期在 Redis 存最近 60 条、TTL 24 小时，管多轮指代；长期在 Milvus 独立集合，跨会话记偏好和确认过的结论；工作记忆是请求内拼 system prompt，按 1000 token 预算裁。注意存和注入是两回事：存 60 条但只取最近 6 轮，单条截 200 字、长期召回 5 条，超了按排序分裁。裁剪只作用于送模型的 prompt，原始全量落盘。

**Q31. 短期为什么是 60 条？**
A：60 条等于 30 轮对话，能覆盖正常一次业务的追问深度；再多就是成本换不回来的边际收益，而且超长上下文本身会让模型注意力涣散。

**Q32. 长期记忆为什么要两级去重？**
A：先算内容指纹做 MD5 比对，撞了就 O(1) 判重，连向量都不用算；指纹没撞上再走向量相似度，超过 0.85 判为同义重复，更新旧记录而不是新增。只用向量的话，每次写入都要编码加检索，成本高；只用指纹的话，换个说法就识别不出来。

**Q33. 召回怎么排序？**
A：相关性乘时间衰减乘重要性。相关性是向量分，时间衰减让旧记忆退场，重要性是写入时打的标签——避免上周问过的闲聊压过上个月确认的关键结论。

**Q34. 为什么要 token 预算？**
A：记忆无上限地塞 prompt，既涨成本又会挤掉真正重要的检索内容，所以我们给记忆注入留了 1000 token 的预算上限。做法就是"保最近的、截最长的、控总量"：短期历史只取最近 6 轮、单条消息截 200 字、长期记忆召回 5 条，还超就按排序分从低往高裁。裁剪只作用在送模型的 prompt 上，trace 和日志里仍是全量，关键报错不会被删掉。

## 六、评测与稳定性

**Q35. 怎么证明这套系统变好了？**
A：离线跑评测集，看三个指标和 judge 分的趋势；线上看赞踩和转人工率；badcase 回流成新用例。而且发布前有质量门禁：拿上一版基线逐条用例比，任意一条掉超过 0.5 分就判为回归、拦下不发——防的正是"总体分没掉、但某一类问题悄悄变差了"。

**Q36. RAGAS 三个指标各衡量什么？**
A：忠实度看答案有没有被检索内容支持，衡量幻觉；上下文精确率看召回段落里多少真相关，衡量检索的准；上下文召回率看该召回的有没有漏，衡量检索的全。三个都是 0 到 1，先 ×10 到 0–10 和 judge 分同量纲再加权，对外再 ×10 换百分制——简历的 70 / 60 / 5 和门禁的 7 / 6 / −0.5 是同一条线，不是两套标准。

**Q37. LLM-as-Judge 评哪六维？**
A：准确性、完整性、相关性、清晰度、引用规范、幻觉。每条按评分细则打 0 到 10，输出结构化 JSON。

**Q38. 自己评自己怎么保证可信？**
A：三层约束。一是评测集有标准答案和来源标注，业务方确认过，不是模型生成的；二是判分模型和生成模型不同源，prompt 也不同；三是不看单次绝对分，看回归趋势——单次分数可以争议，劣化是客观的。

**Q39. 熔断参数是多少？**
A：连续 5 次失败打开熔断，60 秒后进半开态，半开期最多放 3 个探针请求，成功就恢复，失败重新计时，统计窗口 300 秒。

**Q40. 为什么要熔断，直接重试不行吗？**
A：重试解决偶发抖动，熔断解决持续故障。下游已经挂了还猛重试，会把线程池和连接池占满，把自己也拖死。所以是外层熔断快速失败、内层指数退避重试，两者串联。

**Q41. 降级策略有哪些？**
A：重排不可用就跳过精排、用向量分兜底；向量检索异常就退回纯 BM25 单路；置信度不够就降级成通用回答，不硬套检索内容。

**Q42. 线上出问题怎么排查？**
A：用 contextvars 在整条链路传请求 ID 和追踪 ID，日志自动带上，不用每层手动透传。每个节点由包装器自动开 span，记录输入输出摘要、耗时和状态，节点内部的关键动作再开子 span，形成树状调用链——慢请求能直接看出时间花在重排还是生成。

**Q44. 大模型怎么部署的？**

**Q45. 遇到过最难的一个 bug？**

**Q46. 如果重做会改什么？**

### 9.1 熔断

**Q50. 什么是熔断？三个状态怎么流转？**
A：熔断是给下游依赖装的一个开关，防止一个依赖挂了把整条链路拖死。三个状态：CLOSED 正常放行；连续失败到阈值转 OPEN，之后请求直接快速失败、根本不发出去；OPEN 撑过恢复时间进 HALF_OPEN，放几个探针去试，成功回 CLOSED，失败立刻回 OPEN 重新计时。

**Q51. 三个熔断器分别管什么？为什么按依赖拆，不做一个全局的？**
A：`llm` 管大模型调用，`milvus` 管向量检索，`bm25` 管倒排检索。按依赖拆是因为故障域不同——大模型限流不该影响本地 BM25 检索，全局熔断会把局部故障放大成整体不可用。三个都收口在同一个执行器里，全局单例，保证运维接口看到的状态和主流程用的是同一批实例。

**Q52. 熔断打开之后，请求走什么路径？用户会收到什么？**
A：不会再发到下游，执行器直接抛一个带 `retry_after` 的熔断异常，这个异常被上层节点的 `except` 接住走降级——检索那路返回空、生成那路给兜底话术。所以用户看到的是"答案质量下降"，不是报错页。

**Q53. 什么样的异常才计入熔断？业务报错算吗？**
A：不算。只有瞬态异常计入，判定方式是按异常的 MRO 类名去匹配名单——`TimeoutError`、`ConnectionError`、`RateLimitError`、`ServiceUnavailableError`，这样内置异常和 openai 的限流类能一起命中。参数错误、解析失败这类业务异常立即抛出，既不重试也不记失败，因为它们不代表依赖不健康。任务取消也直接抛，不计数。

**Q54. 半开态的探针配额怎么实现的？**
A：`can_execute()` 里，半开状态每放行一个就把计数器加一，加到 3 就不再放行；任意一个成功立刻转 CLOSED 并清零；半开期任意失败立刻回 OPEN、清零、重新计时。整个过程在一把锁里完成。

**Q55. 重试的具体参数是什么？退避曲线长什么样？**
A：总尝试次数 3 次（含首次），策略是指数退避，基础延迟 1 秒、因子 2、上限 30 秒，也就是大约 1 秒、2 秒，再乘 0.5 到 1.5 的随机抖动。抖动是必须的——多个请求同时失败时，没有抖动它们会在同一毫秒一起重试，形成重试风暴。

**Q56. 半开态的并发会出什么问题？你怎么修的？**
A：探针配额之前是坏的——只在转状态时把计数器清零，从来没在放行时递增过，等于半开期不限流，下游刚恢复就被全量流量打回去，二次雪崩。修法是放行前真实占用配额。还有个坑是锁：`threading.Lock` 不可重入，`state` 属性和 `can_execute()` 都要读状态，各自加锁会死锁，所以抽了一个内部方法要求调用方已持锁、两处共用。

**Q57. 为什么同步检索路径只熔断，不加重试和超时？**
A：因为同步路径跑在线程池里，Python 没法安全中断一个正在执行的线程。加超时只是让调用方提前返回，线程还在后台跑、连接还占着，比不加更糟。所以同步入口只做熔断快速失败，不提供 timeout、默认不重试。LLM 是异步的，超时交给 SDK 显式配的 60 秒——SDK 默认 600 秒，慢供应商能把一个请求挂十分钟。

**Q58. 熔断状态怎么观测和干预？多实例部署怎么办？**
A：有运维接口：查整体状态、查每个熔断器的统计和最近 10 次状态变迁、按名字重置或强制打开、全量重置，还能在线改配置。多实例这块我如实说——熔断器是进程内内存状态，每个副本各自统计、重启清零、没有共享，要做严谨得把状态放 Redis 或接 Sentinel。还有个细节：在线改配置只影响之后新建的熔断器，已创建的实例保留老阈值。

### 9.2 降级

**Q59. 下游挂了，用户会看到什么？**
A：多数情况看到"一个不那么好但能用的答案"，不是报错页。检索挂了还有另一路召回，重排挂了只是排序差一点，大模型彻底不可用才会退成一句提示话术。设计目标就是让单点故障不表现为整体不可用。

**Q60. 降级一共有几层？Q41 只说了三条。**
A：完整是四层。一是检索降级，向量和 BM25 互为备份；二是重排降级，交叉编码器不可用就跳过精排、保留粗排顺序；三是生成降级，置信度不够就不拿检索内容约束模型，转通用问答；四是解析降级，RAGFlow 解析失败回退本地解析器。Q41 说的那三条是前三层里的简化说法。

**Q61. 降级和熔断的区别？**
A：熔断是"决定不再调用"，降级是"调用不了之后拿什么顶上"。熔断是触发器，降级是兜底方案。真实链路是一串：熔断打开 → 抛快速失败异常 → 上层 `except` 接住 → 走降级分支。

**Q62. 向量库挂了会怎样？为什么返回空列表而不是抛异常？**
A：向量那一路返回空列表，混合检索退化成 BM25 单路，答案照出，只是丢了语义召回。返回空而不是抛异常，是因为两路召回本来就是并行执行、设计上互为备份，一路空另一路还能出结果；抛异常会把"部分能力下降"放大成"完全不可用"。代价是这次质量下降是静默的，只能靠日志和熔断统计发现。

**Q63. 向量和 BM25 同时挂了呢？**
A：检索节点返回空结果，证据裁判看到空集会触发一轮补检索，补检索还是空就放行给生成。生成看到既没有检索上下文、也没有可用的工具结果，就走通用模式直接答，但不会假装有依据、也不带引用。也就是说两路全挂的时候，系统退化成"没有知识库的普通问答"。

**Q64. 大模型挂了，改写和生成分别怎么处理？**
A：改写节点捕获异常后回退成用户原句、意图默认按知识库类走，整条检索链路照常。生成节点捕获异常后返回一句兜底文案并把错误写进状态。差别在于改写挂了是无损降级（原句也能检索），生成挂了没有替代品，只能给话术。

**Q65. 降级会不会把故障藏起来？怎么发现？**
A：会，这是降级最大的代价。所以配了三样东西：降级分支全部记 warning 或 error 日志，不是静默 return；熔断器的失败计数全局可见，会体现在运维接口的统计和状态变迁里；评测侧能间接发现——降级期间引用准确率会掉。诚实的说法是：单次降级不可见，持续降级能被发现。

**Q66. 置信度不够为什么降级成通用模式，而不是直接拒答？**
A：因为"检索不到"和"答不了"不是一回事。园区很多问题是通用常识或流程性描述，知识库没有对应片段不代表模型答不了，硬拒答会把可用问题一起挡掉。所以低置信时转通用模式：不注入检索上下文、不让模型假装有依据，但仍然回答。真正该拒的是权限不足，那种情况会明确提示"内容属于某部门、当前账号无权限"。

**Q67. 降级是局部替换还是整条重做？代价是什么？**
A：分两种。检索和重排是局部替换，只换一路或跳过一步，其他环节不动，代价只是质量下降。解析降级是整条重做——RAGFlow 失败后本地从头再解析一遍，RAGFlow 那边已经上传和解析的部分不会清理，等于白跑一次调用，而且降级期间不写页级进度，前端看起来像卡住。

### 9.3 追踪

**Q68. 链路追踪解决什么问题？一条 trace 里有什么？**
A：解决"这次请求到底慢在哪、错在哪"。一条 trace 记录一次完整问答：trace_id、用户原问、改写后的问句、会话 ID、总耗时、状态、答案、引用条数、token 用量，以及挂在下面的所有 span。

**Q69. 一次问答会产出哪些 span？**
A：span 类型有十种，实际跑出来是树状：根是 request，下面挂 query_optimize（里面再套一个 llm_call 记改写耗时）、retrieval（里面套 vector_search 和 bm25_search，融合时还有 hybrid_fusion）、rerank_inference、llm_call 记生成。每个 span 有起止时间、耗时、状态、输入输出摘要。

**Q70. trace_id 怎么在异步链路里传下去？为什么用 contextvars？**
A：用 `contextvars`，不是全局变量也不是参数透传。全局变量在并发下互相覆盖；参数透传要改穿每一层签名，侵入太大。`contextvars` 按 asyncio Task 隔离，每个请求一个 Task，天然互不干扰，业务函数签名也不用动。

**Q71. span 的父子关系怎么建立？**
A：维护一个 span 栈。进 `start_span` 时把栈顶当父节点、深度取栈长度，然后把自己压栈；退出时在 `finally` 里结算耗时并弹栈。栈用不可变 tuple——子 Task 里压栈弹栈只产生新 tuple，不会污染父 Task 的栈。

**Q72. trace 落盘会不会拖慢请求？**
A：不会。落盘放在单线程的后台执行器里，请求结束只把 trace 交给队列就返回。副作用是进程退出时执行器可能已经关了，所以那里做了兜底：捕获 RuntimeError 就降级成同步落盘，保证数据不丢。这两条都有测试。

**Q73. 并发下 trace 上下文为什么会串？你怎么防的？有测试吗？**
A：用全局变量存 trace_id 和 span 栈的话，两个并发请求会互相覆盖，A 的 span 挂到 B 的 trace 上，火焰图就乱了。防法就是 `contextvars` 加不可变栈。测试直接验证这件事：并发跑多个请求，断言每个 trace 的 span 只属于自己；另外单独测了 span 成树、异常时 span 标 error 并继续抛、落盘写两个文件、执行器关闭后仍能落盘。

**Q74. 摘要和详情为什么拆成两个文件？**
A：解决列表页的读放大。每天一个 jsonl 存摘要（不含 span，答案截 200 字），列表接口顺序读就行；详情单独一个文件存全量 span，按 ID 直接打开。早期版本摘要和详情混在一个大文件里，查一条详情要全量扫，trace 一多列表页就卡。旧格式还留着扫描兜底做兼容。

**Q75. 没接 OpenTelemetry，算不算硬伤？**
A：不算硬伤，算取舍。自建的好处是零外部依赖、span 能直接喂给前端火焰图、字段按业务定制（比如把 rerank 单独拆出来看瓶颈）。代价是没有跨服务传播、没有标准协议、告警得自己做。要说清边界：拆成多服务就该换 OTel 加 Jaeger，现在是单体单进程，自建性价比更高。

### 9.4 质量门禁

**Q76. 什么是质量门禁？**
A：发布前的一道自动闸门。跑一遍离线评测集，把各项分数和阈值比、和上一版基线比，任意一条不达标就不许发。目的是把"感觉变好了"变成"数据证明没变差"。

**Q77. 门禁什么时候跑？不通过会怎样？**
A：流程是跑评测、生成报告、门禁检查、结果落库。检查函数返回是否通过加未通过原因列表。不通过不会自动回滚，但报告里带 `gate_passed=False` 和逐条原因，谁能发、该不该发就有据可依；也可以按需把阈值全置零临时关掉门禁，只跳过判断、不跳过评测。

**Q78. 门禁卡哪几条线？**
A：五条。总分不低于 7；幻觉分不低于 7；引用准确率不低于 6；失败用例数必须为 0；和基线比不能出现单条回归。这套线是 10 分制，简历上的 70 / 70 / 60 / 5 是同一条线 ×10 后的百分制写法，被问到就这么换算，别说成两套标准。前四条是绝对标准，第五条是相对标准——防的是"总体没掉但某类问题变差了"。

**Q79. 单条用例的总分怎么算？**
A：加权平均，不是简单平均。规则检查 1.0，幻觉 1.5，多轮一致性 0.8，引用准确率 1.0，LLM 裁判 1.2，RAGAS 三项分别 1.0 / 0.5 / 0.5。幻觉给最高权重，因为化工场景答错比答不出危险得多。加权和除以总权重得到 0 到 10 分。

**Q80. 回归检测怎么做的？**
A：传入一份基线报告，逐条用例比分数，找出下降的那些；配置里的回归阈值是 -0.5，掉超过这个幅度就写进未通过原因，连用例 ID、旧分、新分、差值一起列出来，方便直接定位是哪条退化。

**Q81. 门禁和线上监控是什么关系？**
A：离线门禁管"发布前不许变差"，线上监控管"发布后有没有变差"。线上看三样：赞踩比、转人工率、trace 里的错误率和耗时分布。badcase 回流成新用例补进评测集，下一轮门禁就覆盖到——这条回流是两套体系之间唯一的连接点。

**Q82. LLM 评分指标自己失败了，分数怎么算？**
A：不能当 0 分，也不能当满分，正确做法是整个维度剔除。实现上指标内部先给一个占位分并打 failed 标记，汇总时看到 failed 就跳过、不写进权重表，最后用剩余维度的权重重新归一化。这样一次评分服务抖动不会把合格用例误判成失败，也不会悄悄放水。失败原因同时记进报告的指标失败列表。

**Q83. 门禁阈值 7.0 / 6.0 怎么定的？定错了会怎样？**
A：按评测集分布定的——先跑一批人工认可的回答看分数落在哪，再把线卡在"明显不合格"和"勉强合格"之间。引用阈值放到 6，是因为引用正确性是纯规则检查、对格式敏感，卡 7 会频繁误杀。定太高的后果是每次都被拦、最后大家习惯性关掉门禁，门禁就死了；定太低等于没有。所以阈值要跟着评测集一起演进，不能一次定死。

**Q84. 门禁通过但线上效果变差，怎么定位？**
A：用 trace 从结果倒推链路。先按时间筛出变差时段，看错误率和耗时的分布有没有拐点；再抽具体的差评请求看火焰图，哪一段突然变长、哪个 span 标了 error；然后看 span 上的输入输出——是改写给改跑了、检索召回为空、还是重排分数整体偏低。定位到节点后把这类 badcase 补进评测集，让离线也能复现，否则下次发布还会踩同一个坑。

## 十、Python 语言特性与工程实践

> 这一章和前面不同，考的是 **Python 基础 + 工程方法论**，不是业务链路。面试官会顺着"你这个项目用了什么"往下问语言细节。每题的 A 都是可以直接念的口语稿，代码落点都在本项目真实文件里。

### 10.0 Python 基础概念速答

**Q-P1. Python 里怎么实现一个异步任务？**
A：分三层。基础层 asyncio，`async def` 定义协程，多任务用 `gather()` 并发，适合 I/O 密集；Web 层 FastAPI 里发邮件、写日志这类轻任务用 `BackgroundTasks`；大文件、模型推理这类重任务会阻塞事件循环，要上 Celery + Redis，Web 发消息、Worker 消费。避坑：async 里调同步阻塞库得用 `asyncio.to_thread()` 丢线程池。

**Q-P2. 多线程（threading）和多进程（multiprocessing）怎么选？**
A：CPython 的 GIL 让同一进程同一时刻只有一个线程跑字节码，所以多线程适合 I/O 密集，共享可变数据要加锁；多进程各自有独立 GIL、内存隔离，能真正多核并行，适合 CPU 密集，但 IPC 进程间通信开销更高。

**Q-P3. 可变对象和不可变对象有什么区别？**
A：可变对象是 list、dict、set，能原地改内容；int、str、tuple 不可变，不能原地改，"修改"其实是生成新对象。tuple 的不可变是指它存的引用不能换，如果里面放了个 list，那个 list 内部依然能改。

**Q-P4. 函数传参是值传递还是引用传递？**
A：传的是对象的引用地址。如果在函数里原地修改可变对象的内容，外部变量能看到变化；如果只是对参数变量重新赋值，只是让局部变量指向新对象，外部不受影响。

**Q-P5. `def f(lst=[])` 为什么是 bug？**
A：默认参数在函数定义阶段只求值一次，不是每次调用都创建。`lst=[]` 会让多次无参调用共用同一个列表，上次的数据残留下来造成污染。标准解法是默认值设 `None`，函数内部判断再新建列表。

**Q-P6. 深浅拷贝的区别？**
A：浅拷贝 `copy.copy()` 只复制最外层，内部嵌套的可变子对象仍共享引用，改内层会互相影响；深拷贝 `copy.deepcopy()` 递归拷贝所有层级，嵌套对象全新、互不干扰。赋值不是拷贝，只是加一个引用；另外元组里如果全是不可变元素，深浅拷贝都不会新建，这是 Python 的优化。

**Q-P7. `*args` 和 `**kwargs` 是什么？**
A：`*args` 接收多余的位置参数、打包成元组；`**kwargs` 接收多余的关键字参数、打包成字典。定义顺序有要求：必填参数、默认参数、`*args`、仅关键字参数、`**kwargs`，不能调换。

**Q-P8. list / tuple / set / dict 的区别与复杂度？**
A：list 有序可变、允许重复，append 均摊 O(1)、按值查找 O(n)；tuple 有序不可变，但只有当元素全都可哈希时它才可哈希、才能当 dict 的 key（里面塞了 list 就不行）；set 元素不重复、底层哈希表、成员查找 O(1)；dict 在 3.7+ 保留插入顺序、key 查找 O(1)。set 和 dict 底层都是哈希表，所以 key 必须是可哈希对象。

**Q-P9. 什么是闭包？**
A：函数里再定义内部函数，内部函数用到了外层函数的局部变量；外层函数执行完 return 之后，这个变量不会被销毁，被内部函数"留住了"。正常外层局部变量函数跑完就回收，但闭包会把这些变量打包存起来，放在 `__closure__` 属性里。

**Q-P10. 装饰器的本质是什么？怎么识别？**
A：本质是"不改原函数代码，给函数包一层加功能"，`@something` 完全等价于 `my_func = something(my_func)`。识别三个特征：①`@` 在行首（这一行只有 `@xxx` 内容）；②紧跟着 `def` 或 `class` 定义；③中间没有空行、没有别的语句。只要满足这三条，`@something` 就是装饰器。

**Q-P11. GIL 是什么？多线程能不能并行？怎么绕？**
A：GIL 是 CPython 每进程一把的锁，同一时刻只允许一个线程跑字节码，好处是简化引用计数和 C 扩展的线程安全，代价是 CPU 密集多线程用不上多核。线程执行阻塞 IO 会释放 GIL，所以 IO 密集多线程照常有效。绕开：CPU 密集用 multiprocessing，或下沉到 numpy、PyTorch 这类在 C 层主动放锁的库；3.13 有无 GIL 实验构建，短期生产主流不变。

**Q-P12. 协程、事件循环、async/await 的原理？**
A：`async def` 返回协程对象，不调用就不执行；`await` 把控制权交还事件循环，事件循环在 IO 就绪时恢复。是单线程协作式并发、不是并行，切换点在 await，所以协程里绝不能有同步阻塞调用——会卡死整个 loop。

**Q-P13. `asyncio.create_task` 有什么坑？**
A：两个坑：`create_task` 后事件循环只持弱引用，不存强引用任务可能跑完前被 GC；没被 await 的任务抛异常会静默丢失，只在 GC 时打一行 "Task exception was never retrieved"。做法是用模块级 set 存引用，在 `add_done_callback` 里 discard 并读 `t.exception()` 记日志。项目 `chat.py` 的 `_spawn_background` 就是这个设计。

### 10.1 单例模式

**Q85. 什么是单例模式？这个项目里有几种实现？**
A：单例就是全局只创建一份。项目里三种：模块级全局变量（`get_deps()`），模块只导入一次天然单例；`@lru_cache` 做同步单例，`get_settings()` 无参所以缓存永远命中；`asyncio.Lock` 做异步单例，`checkpointer.py` 里锁住"检查→创建→setup"临界区，防并发造出多个 `AsyncSqliteSaver`。

**Q86. 三种单例怎么选？核心判断是什么？**
A：核心看一点——**初始化这个单例要不要 `await`**。不用 await（同步）就用模块级变量或 `@lru_cache`；要 await（异步建连接）就必须用 `asyncio.Lock` 锁住，否则多个协程并发首次调用会各造一个实例。一句话：单例的实现方式取决于初始化是不是 async。

**Q87. `@lru_cache()` 为什么能当单例用？**
A：`lru_cache` 会把"入参 → 返回值"记进缓存，下次同样的入参直接返回缓存结果、不再执行函数体。`get_settings()` 没有参数，入参永远相同，所以缓存永远命中，`Settings()` 只创建一次，之后所有人拿到的都是同一个对象。这里能用 `lru_cache`，是因为 `Settings()` 的初始化是同步的，不需要 await。

**Q88. `asyncio.Lock` 单例那一段（checkpointer.py）在防什么？**
A：防并发首次调用造出多个连接。两个协程同时第一次来，没锁都会"检查发现没有→各自新建"，而 `AsyncSqliteSaver` 每个连接会起后台线程，多了既浪费又可能状态不一致。所以一把 `asyncio.Lock` 包住"查 → 建 → setup"这段临界区。还有个细节：路径变化时复用旧连接，避免已编译 graph 持有的 saver 被提前关掉。

### 10.2 contextvars 与并发隔离

**Q89. `threading.local` 和 `ContextVar` 有什么区别？**
A：都是全局变量、每个执行单元各看各的一份，差别在隔离单位：`threading.local` 按线程，`ContextVar` 按 Task 一份上下文副本。异步里多协程挤同一线程轮流跑，前者会互相覆盖，后者每 Task 一份、而且 `create_task` 会复制当前上下文，天然适合请求级 trace_id 不串号，所以项目异步链路全用 `ContextVar`。

**Q90. 项目里 ContextVar 具体用在哪？**
A：两处：`logging_context.py` 里 `request_id`、`trace_id`、`task_id` 负责请求链路传播；`tracer.py` 里两个变量存当前 trace 和 span 栈。早期用 `threading.local` 并发会串号，换成 `ContextVar` 才解决，测试里留了并发用例防再犯。

**Q91. `ContextVar.set()` 为什么返回 token？**
A：token 不是防并发的——并发隔离靠 ContextVar 绑在当前 Task 的 Context 上，别的协程 set 的值根本进不来。它是同一上下文里的"层级回滚凭证"：外层设了值、内层又覆盖，用完要精确退回外层而不是清掉，`reset(token)` 就干这个，配 try/finally 异常路径也退得干净。tracer 的 span 栈正是这样，进 span 压一层、出 span 退回上一层。

**Q92. 100 个请求进来，是不是就有 100 个空盒子？**
A：ContextVar 对象全局只有一个，但它不存值，只是一把公用的 key；值放在每个 Task 各自的 `Context` 里。`set/get` 操作的都是当前 Task 的 Context，所以 100 个请求是 100 份 Context 查同一把 key，互不干扰。子任务会浅拷贝父 Context，能读到 `request_id` 但 set 不写回父级——这也说明 token 管的是同一 Context 内的回滚，不是跨 Task。

### 10.3 装饰器 / 生成器 / 上下文管理器

**Q93. 分享一个装饰器、生成器、上下文管理器的实际用法。**
A：装饰器是 `@lru_cache` 做配置单例；生成器是 LLM 流式输出，token 一个个 `yield`，前端才有打字机效果；上下文管理器是 `tracer.py` 里 `@contextmanager` 的 `start_span`，配 `with` 保证 span 无论成败都关闭。三个能串起来讲：`@contextmanager` 本身就是用生成器加装饰器实现的上下文管理器，一个 `start_span` 全体现了。

**Q94. 生成器的 `return` 值，调用方怎么拿到？**
A：普通迭代拿不到。生成器执行到 `return value` 时会抛 `StopIteration`，那个值藏在 `StopIteration.value` 里，要手动 `next()` 循环、捕获异常才能拿到。不过纯流式场景（比如 `generate_stream` 只 yield token 不 return）根本用不到 return 值，调用方只关心一个个 token。

**Q95. 日志送给模型前怎么裁剪？关键报错被删了怎么找回？**
A：原则是保最近的、截最长的、控总量：短期只取最近 6 轮 `messages[-12:]`，单条 `content[:200]` 截断，长期召回 5 条，整体 1000 token 兜底。关键报错不会丢，因为裁剪只发生在送模型的 prompt 这一层，trace 把完整输入输出写进 JSONL，全文在 details 文件里，报错从原始 trace 捞。

### 10.4 asyncio 与并发

**Q96. 什么时候适合用 asyncio？协程里调阻塞接口会怎样？**
A：适合 I/O 密集高并发，调 LLM、查 Milvus、读写 Redis 全是 I/O，单线程能并发跑成百上千任务。最大的坑是协程里调同步阻塞接口，它不让出控制权，会卡死整个事件循环、并发退化成串行；项目里用 `asyncio.to_thread` 把同步的 Milvus 删除丢线程池就是防这个。

### 10.5 工程方法论（排查 / 回归 / 协作）

**Q97. 补丁怎么验收？原测试过了，怎么确认没引入回归？**
A：分三层：改动相关单测 → 全量回归（项目 183 passed）→ 定向回归。但"原测试过了"不等于"没回归"，因为原测试只覆盖它自己写的场景。补充手段：review diff 只看改动范围、新增针对性测试覆盖改动点、跑影响面测试、盯覆盖率。回归最容易藏在并发、边界、异常路径里——项目里 `test_tracing.py` 那句"异步场景易回归点"注释就是典型，这几类要专门盯。

**Q98. 定位和修复用不同模型时，两边怎么交接？输出对不上怎么办？**
A：交接靠结构化上下文加可验证交付物，不是自然语言描述：复现步骤、根因到文件行字段、修复方案、验收标准四样。输出对不上多半是上下文传递中被压缩丢了，手段是 JSON 或补丁 diff 交接、让修复模型先复述定位结论再动手、修完跑测试回填验收。本质就是多 Agent 的状态传递问题，和 LangGraph 用 state 传数据同一思路。

**Q99. 故障没打日志时，从哪里找线索？**
A：从本来就会落盘的东西找：trace 的输入输出和 span 耗时、持久化的中间产物（记忆 JSONL、checkpoint、教训文件）、LangGraph 每步的 state 快照、外部依赖自己的日志，以及拿 query 和 session 重跑复现。日志没打不等于没留痕迹，所以可观测性要前置设计，trace 和 checkpoint 就是兜底线索。

**Q100. 补丁能跑但不符合代码规范，在哪一步拦？**
A：越前置越便宜。分层拦：静态检查（ruff/flake8/mypy）→ pre-commit hook 本地提交时跑 → CI 合并前跑 lint+测试+覆盖率 → Code Review 最后一道。理想是"规范前置到生成补丁那一步"——先读项目约定（CLAUDE.md、配置），生成时就符合规范，而不是事后拦。

**Q101. 常见的内部问题怎么答？什么时候值得单独做个问答模型？**
A：先看能不能用检索解决。内部问题答案通常固定且已有文档，最适合 RAG，成本低、更新快，文档改了重新切片就行。只有检索兜不住才考虑微调或专属模型：需要深度领域推理、固定合规口径、召回率长期上不去，或高频问题要低延迟高可控。判断标准一句话：先 RAG 兜底，等召回质量或可控性成为瓶颈且有足够标注数据，才值得上微调。

**Q102. 只给你一周优化这个系统，先改哪里？怎么验证？**
A：按先诊断、再止血、后提质，优先动影响大、见效快、风险低的。第一是检索质量，RAG 的命门，看 20/20→10→5 漏斗哪层掉得多，再调改写、融合权重和重排；第二是教训闭环，核对置信度门槛和注入上限；第三是用 trace 找最慢节点，该缓存缓存、该并发并发。总前提是先建评测集，每改一处跑一遍，用答案准确率、引用准确率、延迟量化，否则一周优化就是瞎改。

**Q103. 你怎么理解 Harness？这个项目里模型和外层程序各管什么？**
A：Harness 是套在 LLM 外面负责调度编排的框架，我们项目就是 LangGraph。模型管认知生成——改写 query、按召回内容生成答案；Harness 管编排控制——StateGraph 定节点和边、RAGState 传数据、条件边决定要不要重查，还管流式和 trace。一句话：模型只是图里的一个节点，什么时候调、调几次、结果怎么流转，全是 Harness 说了算。

**Q104. 线上有没有修失败过？举个例子，说说怎么排查的？**
A：早期用 `threading.local` 存 trace_id，并发请求日志串号，`test_tracing.py` 里留了注释。排查五步：看 trace 发现多个请求同 ID → 压测稳定复现 → 定位到 asyncio 下多协程挤同一线程、按线程隔离会互相覆盖 → 换成 `ContextVar` 按 Task 隔离 → 补并发测试防再犯。关键不是有没有失败，而是有没有沉淀成注释加测试，同样的错不犯第二次。

**Q105. 你了解 Claude Code 的沙箱吗？放到这个项目里，文件和命令权限怎么划？**
A：了解，Claude Code 对文件读写、命令执行、网络访问这类有副作用的操作默认先请求授权。这个项目按最小权限划：源码目录可读写，个人目录和 `.git` 默认只读、删除单独确认；ls/grep/pytest 放行，`rm -rf`、`reset --hard`、`git push` 要显式授权；调 LLM API 放行，上传陌生地址要确认；密钥脱敏不落日志。和项目 RBAC 的 `allowed_doc_ids` 是同一个思路。

### 10.6 RAG 基础与幻觉

**Q106. 什么是 RAG？相比纯生成模型有什么优势？**
A：RAG 是回答前先到外部知识库检索相关内容，把问题和材料一起喂给模型，让它基于材料答而不是只靠训练记忆。相比纯生成三个优势：私域文档能接入、文档更新重新切片入库就行不用重训、答案能标出来自哪段原文——最后这点在安全法规场景是刚需。

**Q107. 主流向量数据库 Faiss / Pinecone / Milvus 各有什么特点？怎么选型？**
A：Faiss 是检索库不是数据库，只管索引和算距离，服务化得自己搭；持久化有 `write_index`、按 ID 过滤有 `IDSelector`、分片有 `IndexShards`，但都靠手工，缺声明式标量过滤和事务。Pinecone 全托管但要上云；Milvus 是分布式向量数据库，原生支持标量过滤、混合查询和水平扩展。选 Milvus 不是"Faiss 做不了过滤"，而是 RBAC 要按 `doc_id in [...]` 过滤，外加持久化和多人共享，Faiss 得在库外拼一整套。口诀：单机实验 Faiss、快速上云 Pinecone、企业级可控 Milvus。

**Q108. 大模型幻觉有哪些常见类型？举例说明。**
A：四类。事实性幻觉是编造不存在的事实，比如原文没写"动火作业票有效期 72 小时"却答出来；忠实性幻觉是检索到了正确片段却答非所问；来源幻觉是给了引用标记，但那段原文并不支持结论，我们评测里专门盯这个；第四是忽略边界，库里没有还硬编一个看似合理的答案。化工安全场景最危险的是第一和第四类，答错比答不出代价高得多。

**Q109. 设计一个多源知识库的 RAG 系统，核心组件和架构怎么考虑？**
A：多源意味着格式、类型、权限都不同，我会拆统一接入层（各源 connector 转标准文档对象）、解析切分层（按源选解析器，表格语义分组和 heading-aware 切分已经做了）、索引层（向量库加倒排，带源标识和权限字段）、检索层（多路召回、融合、精排，还要处理跨源权重）、权限层（按 scope 过滤，对应 `allowed_doc_ids`）、生成层和评测治理，每个源的召回质量单独评。难点不是能接多源，是权限隔离、源间一致性和跨源去重。

### 10.7 手写算法

**Q110. 手写：无重复字符的最长子串长度。**
A：滑动窗口 + 哈希表，O(n)。用双指针维护一个不含重复字符的窗口，右指针不断右移，遇到重复就左移左指针收缩窗口，过程中记录最大长度。

```python
def length_of_longest_substring(s: str) -> int:
    char_index = {}   # 字符 -> 最近一次出现的位置
    left = 0
    ans = 0
    for right, ch in enumerate(s):
        if ch in char_index and char_index[ch] >= left:
            left = char_index[ch] + 1   # 收缩左边界，跳过重复字符
        char_index[ch] = right
        ans = max(ans, right - left + 1)
    return ans
```

核心：窗口内始终无重复，`left` 只前进不后退，所以整体 O(n)。可以举 `"abcabcbb"` → 3（`"abc"`）验证。

**Q111. 手写：m×n 网格最小路径和（左上到右下）。**
A：经典动态规划。`dp[i][j]` 表示从左上到 `(i,j)` 的最小路径和，只能向右或向下走，所以 `dp[i][j] = grid[i][j] + min(dp[i-1][j], dp[i][j-1])`。第一行、第一列只能单向累加。

```python
def min_path_sum(grid) -> int:
    m, n = len(grid), len(grid[0])
    dp = [[0] * n for _ in range(m)]
    dp[0][0] = grid[0][0]
    for i in range(1, m):        # 第一列只能从上往下
        dp[i][0] = dp[i-1][0] + grid[i][0]
    for j in range(1, n):        # 第一行只能从左往右
        dp[0][j] = dp[0][j-1] + grid[0][j]
    for i in range(1, m):
        for j in range(1, n):
            dp[i][j] = grid[i][j] + min(dp[i-1][j], dp[i][j-1])
    return dp[m-1][n-1]
```

时空复杂度 O(m×n)，如果要优化空间可以只用一维数组滚动（O(n)），因为每行只依赖上一行。讲的时候点一句"这是最短路/DP 的经典入门，和最长公共子序列、背包同一套递推思想"。

### 10.8 Agent 架构与多智能体

**Q112. 一个典型的 Agent 架构包含哪些核心组件？各组件的作用和交互？**
A：五个组件：大模型是大脑，工具通过 Function Calling 当手脚，记忆分短期上下文和长期偏好，规划调度决定调什么工具、循环几轮、何时停，状态编排由 LangGraph 负责流转和条件分支。交互就是个循环：模型说要调工具 → 框架执行 → 结果回喂 → 模型判断继续还是结束。项目里五个都有对应：网关、生成节点的 FC、MemoryManager、条件边加循环上限、RAGState。

**Q113. 多 Agent 协同会遇到哪些挑战？怎么解决冲突或循环依赖？**
A：四个挑战：状态一致性靠单一数据源加明确的消息协议，谁写哪些字段约定清楚；循环依赖靠 DAG 化、超时和最大轮次，必要时加仲裁 Agent；上下文在传递中被压缩丢失，靠结构化中间产物加校验闭环；职责重叠或结论矛盾，靠明确边界加仲裁/投票和置信度打分。核心思路和单 Agent 的 state 传递是一回事：交接靠明确的结构化产物，靠超时和上限兜底，不让 Agent 自由博弈。

**Q114. LangGraph 相比 LangChain 的传统链，在状态管理和记忆方面有什么优势？**
A：传统链是固定流水线，状态隐式、靠参数传递，加循环和中断恢复很别扭。LangGraph 三点优势：显式状态，`StateGraph` 绑 TypedDict、节点只返回增量；图结构，条件边、循环、并行都能声明；原生 checkpoint 能把执行到哪一步持久化，配 `interrupt()` 挂起、`Command(resume)` 恢复做断点续跑，项目里"挂起等人审批、跨天恢复"就是用它。一句话：传统链是流水线，LangGraph 是状态机加图。

**Q115. Agent 开发中如何对底层大模型调优？微调、Prompt 工程、RAG 怎么结合？**
A：三者是叠加不是二选一。Prompt 管怎么说，靠指令和 few-shot 约束行为，最轻最快，首选；RAG 管给什么材料，补私域和时效，不改模型；微调管改行为习惯，学会特定格式和风格，要标注数据，只有前两者都兜不住表达和推理方式时才上。顺序是 Prompt 迭代 → RAG 补知识 → 稳定后用真实问答做微调。我们目前 Prompt + RAG 为主，瓶颈在检索质量不在表达风格，微调性价比不高。

### 10.9 缓存、消息队列与项目管理

**Q116. 如何用 Redis 缓存频繁访问的 prompt 模板或中间结果？注意什么？**
A：模板是静态配置，本地或 Redis 都行，key 用模板名加版本号，改了必须失效，项目 `@lru_cache` 配置单例就是同类思路。中间结果要更小心：key 用 query 的 hash，知识库会更新所以要短 TTL、文档入库删除要主动失效，大对象注意序列化，还要防失效瞬间的穿透击穿。一句话：模板缓存重版本，中间结果重 TTL 和失效。

**Q117. 如何评估技术风险并保证 Agent 项目的进度和质量？**
A：技术风险靠风险清单加提前 POC，检索质量、幻觉率、关键依赖可用性第一时间验证，别等开发完才发现走不通；进度靠里程碑加可验收的小步交付，用评测集当"完成的定义"；质量靠评测先行加门禁，改一处跑一次、分数降超阈值就拦。一句话：Agent 最怕不可度量，把效果变成数字、把里程碑绑在评测上，三者才有解。

## 十一、简历专项追问（前端经历 + 链路深挖）

> 这一章专补简历上写了、前十章却没成题的内容：11.1 对应 2023.05–2025.04 的园区信息化平台前端（简历 title 是「前端负责人」，被追问概率高）；11.2 是 RAG 主线里只被一句话带过、但简历明确列了的能力。A 都可以直接念，口径和前面各章一致。题号用 Q-F / Q-D 独立编号，避免和 07 题库的 Q118+ 混。

### 11.1 前端与可视化（简历前两年）

**Q-F1. 简历写 Vue3，现在这个项目用 React，怎么讲？**
A：不是重构替换，是两个时期、两个子项目。园区信息化平台 2023 年起步，存量组件库和中台都是 Vue，Composition API 加 TS 够用、交付紧没必要换；后来 RAG 问答前端单独起项目，用 React 18 加 TS、AntD、Zustand，为了流式输出和火焰图这类高频局部更新。两边共用后端接口和权限体系，我不会讲成"从 Vue 迁到 React"，如实讲按项目选栈更稳。

**Q-F2. 可视化大屏怎么做的？ECharts 组件和主题配色怎么设计？**
A：不是每张图各写一份 option，而是抽了一层配置化组件：业务只给数据、图表类型和少量覆盖项，组件统一管 resize、loading、空态和销毁；配色抽成主题 token 用 `registerTheme` 全局注册，换主题不动业务代码。多分辨率按基准画布等比缩放配 rem/vw，图表监听容器调 `resize()`。踩过的坑是缩放后 tooltip 会偏，得按缩放比换算坐标。

**Q-F3. OpenLayers 资源上图怎么做的？点位聚合、图层切换、热力图各解决什么？**
A：装置、监测点位、应急物资用独立 VectorLayer 分层管，开关只切 visible，塞一层会让样式和命中查询互相干扰。点位上千后直接渲染又卡又压盖，用 Cluster 聚合、随缩放级别按密度重算，点开再下钻。热力图是密度视角，把告警或风险值当权重看哪片区域集中，和精确点位不能互相替代。还有个坑：底图瓦片和 GPS 坐标系不一样，必须先做投影转换。

**Q-F4. WebSocket 实时推送怎么做的？断线、心跳、消息堆积怎么处理？**
A：告警和设备状态轮询不行，延迟和无效请求都吃不消，服务端走 WebSocket 推。工程上四件事：心跳加客户端指数退避重连、重连带上次序号做增量补发；按园区和区域订阅，只推当前视野和权限范围内的点位；高频更新在前端节流批量合并，一帧只渲染一次；切后台暂停渲染但保留连接。关键是 WebSocket 只管变化通知，首屏仍走 HTTP 拉全量，所以连接断了页面也不是空的。

**Q-F5. 后台管理模块承担什么？和权限、应急指挥怎么打通？**
A：后台管理给园区安全员用，管台账、点位物资、角色和告警规则。前端按 RBAC 收菜单按钮，真正的边界在后端，接口每次独立校验，否则改个请求就能越权。大屏告警点位能一键跳到台账和处置预案，两边共用一套园区/装置/点位 ID；但 RAG 做可见范围过滤复用的是按角色加范围分层的权限思路，过滤键是文档 `doc_id`，两套主键不是一回事。

**Q-F6. 前端做了两年，为什么转去做 Agent？这段经历对 RAG 项目有什么用？**
A：不是转行，是被业务逼过去的。驻场两年客户最高频的就是查规程、查事故处置、应急问答，页面能展示但答不了"该按哪条规程执行"。前端经验给我两个优势：知道答案最终怎么落地——引用点回原文、流式输出、火焰图；也能一个人把方案从调研推到上线。所以简历这两段是同一条线，不是割裂的经历。

### 11.2 链路深挖（简历点了名、前面只一句话带过）

**Q-D1. 前端火焰图具体怎么画？怎么区分"自己慢"还是"下游慢"？**
A：trace 落的是带父子关系和起止时间的 span 树，前端按 depth 分行、按 start_time 算 left 和 width 画横条。最有用的是自身耗时 = 总耗时减直接子 span 耗时之和：总耗时高但自身耗时低，时间花在下游，该往里钻；接近 100% 就是瓶颈在这一步，reranker 这种纯推理节点就是这样。老数据没 depth 就从父子关系反推，推不出来退化成第 0 层。

**Q-D2. 比较类问题怎么拆子查询？并行检索的结果怎么合并？**
A：改写那次 LLM 调用顺带判断是不是比较类，是就拆 2–3 个实体子查询，和主查询一起 `asyncio.gather` 并发检索，避免串行叠延迟。这是特殊分支：常规仍是两路各 20 → 截 10 → 精排 5，比较类是主查询 top8、子查询各 top5。回来按 chunk_id 去重，一起进融合重排，不是各出一份答案再拼；子查询也先去重。生成用比较类 prompt，先列实体、再对比、最后给结论。

**Q-D3. 长期记忆里的"关键信息"怎么提取？什么时候触发、成本怎么控？**
A：不是每轮都写，成本高还会把闲聊沉淀成事实。会话结束或累计若干轮后异步抽一次，让模型判断有没有值得留的——身份角色、确认过的设备或规程口径、明确偏好，没有就返回空；抽取写入都走后台任务，不占链路延迟。写入前 MD5 指纹判重，撞了跳过；没撞再算向量相似度，超过 0.85 就合并进旧记录而不是新增，否则换个说法就堆一堆近似向量。

**Q-D4. 从驻场调研到输出技术方案，中间做了什么？为什么选 RAG 不选微调？**
A：先跟安全、生产两个岗位各走一段流程，把高频问题归成查规程、查事故处置先例、应急物资流程三类；再看数据环境——PDF、Word、Excel 混着、每年修订、还有部门可见范围，这三点定了方案。微调否掉三条：没标注问答对、文档每年改训完就过期、安全场景必须能点回原文。评审时我重点讲检索错了怎么兜、答案错了怎么被发现，也就是后来的置信度门禁和评测体系。

**Q-D5. 上线后客户反馈怎么变成系统改进？知识库扩充和 Prompt 调优怎么做的？**
A：反馈来自培训现场、赞踩和转人工、trace 里能回查的差评。不拿一句"答得不好"直接改 prompt，先归因：改写跑偏、召回为空、重排排错，还是生成没按引用答，归因错了越调越坏。知识缺口就补文件重新切片，表达格式问题才动 prompt；每改一处跑评测加门禁，看整体分也看单条回归。badcase 沉淀成新用例进评测集，闭环才成立。

## 十二、多流程配置化平台（2026-11-26 新增）

> 如果面试官问「你最近做的、最能体现架构判断的项目」，讲这一章；如果只问「RAG 怎么答得准」，仍讲第三、四章。设计与验收细节见 [10-多流程配置化平台设计.md](./10-多流程配置化平台设计.md)。

### 12.1 一句话定位

> 把「对话」从问答入口扩成业务办理入口：司机在对话里说一句话就能发起入园预约，AI 只负责收集和核对，提交和审批仍由人完成；同时把这类申请审批流程抽象成配置，业务方在后台就能接入新流程，不改代码、不动表结构。

### 12.2 业务闭环（30 秒讲完）

```
对话说「帮我申请入园，我叫张三，手机号…」
  → AI 抽 13 个字段、一次性追问缺项
  → 上传五类证件（车头/车尾/行驶证/驾驶证/危化品运输证）
  → 信息齐全 → 确认卡（身份证/手机号打码）
  → 本人点「去表单核对并提交」→ pending
  → admin 审核 → approved 生成通行编号 + 二维码
  → 驳回可 reopen 修改重提；pending 可撤回
```

**关键边界**：AI 全程只读，四个工具都是查询/校验/推卡；`submit` 只能本人在表单页点；`review` 强制 admin 级且禁止自审自批。

### 12.3 架构决策：为什么不是 N 个工作流 / N 个 Agent

| 方案 | 为什么不选 |
|---|---|
| 每个流程一个工作流 | 工作流是确定性编排，让它参与意图猜测会把不确定性带进状态机；每加流程还要改对话入口路由 |
| 每个流程一个 Agent | N 套提示词/工具/权限，跨流程协同成本指数上升；当前没有独立知识域/权限域的硬需求 |
| **一个内核 + 路由 + N 份配置** | 对话/记忆/权限/观测只有一份，流程差异收敛到数据；新流程零代码接入 |

三层职责：

1. **对话内核**：单 Agent + function calling + 槽位追问 + 确认闸门；
2. **意图路由**：后端权威，P0 句首办理 > P1 只读 > P2 通用，歧义下发候选卡（0 秒、不调模型）；
3. **配置注册表**：11 段元模型，按 `flow_id` 裁剪只读工具与提示词。

| 数字 | 含义 |
|---|---|
| 13 / 4 / 5 | 入园 13 个字段、4 个分组、5 类必传附件 |
| 5 | 固定状态骨架：draft / pending / approved / rejected / cancelled |
| 11 | 配置元模型段数（meta/fields/intent/attachments/workflow/session/entry_points/card/prompts/hooks/permissions） |
| 8 | dry-run 校验项（含审批链完整性硬约束） |
| 6 | 首批命名扩展点（时间窗、重量上限、附件绑定、高置信校正、通行证、ERP 预留） |
| 5 | 通用表（definitions / versions / applications / attachments / audit） |
| 36 + 15 | 通用平台路由 + 旧入园兼容路由 |
| 40 | 入园意图回归用例（入 DB，发布前跑） |
| 24 / 216 | 平台专项 pytest 用例 / 后端全量用例 |
| 27 | 前端 vitest 用例 |
| 43 / 12 / 7 | HTTP 端到端：通用链路 / 旧接口兼容 / 提交后办结收敛 |

### 12.5 三个现场问题与定位方法（体现工程能力，不是背结论）

**① 上传图片后「之前填的信息全没了」**

- 现象：上传第一张图时跳到空会话，AI 重新要姓名/身份证。
- 定位：Redis 里有两个会话，新会话创建时间正好等于第一张图上传时刻；`setFlowAttachment()` 在非 `flow-` 会话里调 `startFlowSession()`，后者把 `flowSlots`/`messages`/版本全清零。
- 修法：上传只累加附件 ID；同流程切会话带走槽位与版本；切回原会话合并未绑定附件。

**② 提交后每轮回答都挂核对卡**

- 现象：申请已 pending，聊「今天天气真好」也被当入园办理，AI 反复催提交。
- 定位：后端日志显示后续每轮 `flow_action=action`、`flow_payload.card` 非空；`session_keep` 无条件续留，`_generate_flow()` 见槽位完整就重出卡。
- 根因：设计只定义「何时进入流程」，没定义「何时算办结退出」。
- 修法：后端查在途单据（pending/approved）→ 关闭会话兜底；前端 submit 成功清状态；渲染层只保留最新一张卡。

**③ 前端意图规则与后端不一致**

- 现象：同一句话两端判定不同，E2E 偶发失败。
- 根因：两套正则各自维护。
- 修法：删除前端 `entryIntent.ts`，40 条用例迁入 DB，发布前回归，前端只渲染后端候选卡。

### 12.6 高频追问

**Q：配置里能写业务逻辑吗？**
A：不能。只能引用已注册的命名 hook，参数是字面量；配置里禁止表达式/脚本，hook 有 `active→deprecated→retired` 三态，下线前扫描引用。

**Q：新增流程真的零代码？**
A：业务配置层面是：取模板 → 改 11 段 → dry-run → 双人发布。只有需要新的确定性校验或出证逻辑时，工程注册一个 hook。这是刻意保留的边界。

**Q：配置比代码危险，怎么防？**
A：dry-run 八项 + 强制双人发布 + 改版自动灰度 + 快照回滚 + 版本锁定。核心判断是配置错误影响全体申请人，治理要比代码发布更严。

**Q：在途单据遇到改版怎么办？**
A：会话和单据都锁 `definition_version`，按快照复现当版字段/规则/卡片；老数据 `*_legacy` + 只读兼容视图保留 90 天。

**Q：为什么不用模型做意图分类？**
A：高风险判定要可解释、可回归、零延迟；规则流水线能做到，模型做不到稳定。`hybrid` 预留但这一版不接。

**Q：多 Agent 什么时候拆？**
A：出现跨流程协同、知识域互相干扰、权限域不能靠 RBAC 收敛，三个信号再拆。

### 12.7 诚实短板

- 动态明细行、级联字段一期未支持；配置后台「显式切换新版」交互还没做。
- 纯陈述句（「我拉了一车甲醇到门口了」）仍按知识库问答处理，需要明确办理动词或点 AI 快捷入口。
- 意图用例没有硬性数量门槛，不配只告警不阻断；高风险流程靠团队自觉。
- 兼容视图 90 天到期删除是运维动作，需要单独审批。
