## Trace 链路调研（问答）

核实并评估 `backend/app/tracing/tracer.py` 的自研 Trace 实现：

- **结论：非 OpenTelemetry**，纯自研（240 行）。`pyproject.toml` 无 opentelemetry / langfuse / langsmith / phoenix 依赖。
- 埋点路径：`api/chat.py:243 start_trace` → `agents/graph.py:124` 每个 LangGraph 节点包一层 `start_span`；`nodes.py` 记录 token。
- 存储：`logs/traces/traces_YYYY-MM-DD.jsonl`（摘要）+ `details/<trace_id>.json`（含 spans）。已累积 199 条详情。
- 前端：RecordPage 列表 + 详情抽屉；`getFlamegraph` 接口已实现但**前端未接入**。

### 实测有效（有价值）
- 能定位瓶颈：trace `8d3e17f1` 总 11516ms，reranker 10308ms 占 **89.5%**，印证 CLAUDE.md 中 reranker 是性能瓶颈的判断。
- 业务化 span 输出：`extract_span_outputs()` 记录 vector/bm25/hybrid 分数、source_file、page_number、prompt/response preview，对 RAG 召回调试比通用 OTel 更贴合。
- token 统计可用：199 条中 176 条（88%）有非零 token。

### 已识别缺陷（可修复项）
1. `parent_span_id` 恒为 None → span 扁平，火焰图退化成甘特条，无父子嵌套。
2. 埋点只到 LangGraph 节点粒度，节点内部（Milvus / BM25 / embedding / LLM HTTP / reranker 推理）是黑盒。例：`query_optimize` 9401ms 无法拆出是 LLM 慢还是网络慢。
3. `_persist_trace()` 在 `end_trace()` 里同步 open/write，阻塞 event loop（API 层的 `_load_*` 已用 `asyncio.to_thread`，落盘侧没做）。
4. `threading.local` 存 trace_id，FastAPI async 并发下多请求会互相覆盖 → span 记到别人的 trace。`core/logging_context.py` 已有 contextvar 可复用，改成 contextvar 成本低。
5. 无聚合分析：只有 list + detail 两个接口，无 P95/P99、错误率趋势、按 operation_name 聚合。
6. 无采样/背压、无跨服务传播（无 traceparent）、多副本各写本地文件。

## /documents 与 trace 耗时诊断（只定位未改代码）

- `/documents/?page=1&page_size=20` 首调 28s、稳态 113ms：根因是 docker-compose backend 用 `--reload`（`docker/docker-compose.yml:208`），worker 冷启动 import 重型模块 + `startup_event` 预加载 Embedding 模型吃掉首请求；handler 体本身极轻、verify_token 仅 JWT 验签无 IO。详见 `docker logs backend` 的 Application startup 间隔。
- **trace 数据质量审计**：
  - 用户质疑「整体历时 70.80s」。实测 `5de9c4fd`（70.92s, 王聪今年多大了）子 span 首尾相接累加 = 70.9s，与 total 吻合 → **70s 是真的**，但慢在业务：reranker 中位 39.2s（60~80s 的 53 条 trace 里 reranker 占 56%）、query_optimize ~15s、generate ~9.6s。印证 CLAUDE.md 待优化项 #2 reranker 瓶颈。
  - **真 bug**：4 条小时级脏数据（592/123/119/118 分钟 = 9.88h/2.05h/2.0h/1.97h），如 `01c7a8d7` 单 span start=1787756848 end=1787792412。是老 threading.local 时代并发串扰残留导致 end_time 写错，或 end_trace 未正常收尾。前端列表会显示离谱数字，需清理（删除对应 detail json + jsonl 行，或前端过滤 duration>阈值）。
  - 结论：火焰图顶部"整体历时"= trace 总 duration_ms；新数据流式根 span 含 SSE 推送时间（已标注 includes_sse_flush），分析时长时需注意。
  - **4 条小时级脏数据已清理**：删 `details/{01c7a8d7,a81e3376,ec1c3161,1c661954}.json` + 过滤 `traces_2026-08-27.jsonl` 4 行；备份 `traces_2026-08-27.jsonl.bak`，验证无残留。

## Reranker 性能瓶颈与优化设计（诊断，待实施）

**现状根因**（已读 `services/reranker_service.py` + `nodes.py:415`）：
- 模型 `BAAI/bge-reranker-base`（cross-encoder，~278M 参数）；`_resolve_device()` 自动 cuda 否则 cpu。
- `rerank()` 用 `asyncio.to_thread(model.predict, pairs, batch_size=16)` —— 只保证不阻塞事件循环，但 CPU 推理本身慢。
- `reranker_node` 对 **全部 filtered_results（hybrid 返回 20 条）** 全量打分，最后只取 top_k=5 → 15 条白算。
- `doc[:4000]` 截断无效（CrossEncoder `max_length=512` token 会再截）。

**优化优先级**（性价比排序）：
1. 降候选：rerank 前先按 hybrid_score 粗取 top 10 再精排（config 加 `RERANKER_CANDIDATE_TOP_K=10`），砍 50% 耗时、零风险。
2. 确认 GPU：`nvidia-smi` 看 cuda 是否可用；若有 GPU 未用上，45s→2s（代码已支持自动检测）。
3. 换轻模型/量化：base→MiniLM/ONNX int8，或 `max_length` 384 A/B。
4. 语义缓存/早退：命中率低，不优先。
→ 优化后看火焰图 reranker span 回归 <5s 即达标。
